# 前端静态产物发布与回退

## 发布方式

前端在开发机使用仓库锁定的 Node.js 24.21.0 和 `package-lock.json` 构建。服务器只接收带 SHA256 校验的静态归档，由 Nginx 读取 `current` 指向的 release。服务器不执行 npm、Webpack 或前端 Docker build。

发布器设置 `VUE_APP_BASE_API=/`，REST API 继续经 Nginx 转发；`VUE_APP_WS_API` 保留 `.env.production` 当前的公开地址。本方案不改变 WebSocket 路由。

服务器默认目录：

```text
/data/meals/frontend/
  releases/<release-id>/
  current -> releases/<release-id>
  previous -> releases/<release-id>
  incoming/
  staging/
  lock/
```

`current`、`previous`、`releases` 和 `staging` 必须位于同一文件系统。安装时目录权限归一化为 `0755`、普通文件为 `0644`，Nginx worker 通过只读挂载读取内容。

## 服务器要求

- Linux 服务器提供 Bash、GNU tar/coreutils（包括 `mv -T`）、`sha256sum`、`flock`、Python 3、Docker Compose v2（支持 `config --format json`）和 `curl`。
- 服务器不需要安装 Node.js、npm 或前端构建工具；Node.js 24.21.0 只安装在运行本地发布器的开发机上。
- 发布账号可以使用 Docker Compose，并且能读写 `/data/meals/frontend` 与部署仓库。
- Compose 环境文件保存在 `/data/meals/.env`。保留其中数据库、Redis、JWT、RSA 和其他私有配置；不要用仓库中的示例文件覆盖它。
- `/data/meals/frontend` 不得是部署仓库、仓库的父目录或符号链接。`releases`、`current` 位于同一文件系统。
- 本机提供 Git、curl、tar、shasum、rsync、ssh 和 Bash。发布器首次运行时会从 nodejs.org 下载 Node.js 24.21.0，校验官方 SHA256，并缓存到 `eladmin-web/.node-runtime/`；只为这次发布进程设置 PATH，不更改系统默认 Node。后续复用缓存。发布器拒绝相关路径有未提交改动的工作区。

仓库的 `docker/.env.example` 展示新增变量：

```dotenv
BACKEND_IMAGE_TAG=latest
FRONTEND_RELEASE_ROOT=/data/meals/frontend
FRONTEND_RELEASE_KEEP=5
```

生产 Compose 环境文件应将 `BACKEND_IMAGE_TAG` 设为当前后端镜像 tag 作为直接 Compose 操作的默认值，并配置实际的 `FRONTEND_RELEASE_ROOT`。日常后端发布/回退脚本会显式传入目标 tag。Nginx 健康检查默认访问 `http://127.0.0.1:18080/release.json`。

## 首次切换

首次切换会改变 frontend 的 Compose 运行方式。完成预发演练后，再在生产执行。首次部署前还没有静态 `current`，此时健康检查失败不能自动恢复到旧 Docker 镜像，必须按本节准备旧架构恢复信息。

1. 检查 `deploy-from-github.sh`、`rollback.sh`、`deploy-bootstrap.sh` 的计划任务和外部调用方，确定切换窗口。仓库内由 `deploy-bootstrap.sh` 更新仓库并调用部署脚本；服务器 crontab、面板任务和外部系统需要在目标服务器确认。
2. 记录旧部署仓库 Git commit、正在运行的 `mealserver`/`mealweb` 镜像 tag 和 image ID、容器 ID、对外 URL 与业务冒烟结果。确认旧 `mealweb` 镜像仍在本机。
3. 为旧 `mealserver` tag 记录**已确认的构建 commit**。新版镜像在 Docker label 中记录 commit；切换前的旧镜像没有该 label 时，将确认的 40 位 commit 写入：

   ```bash
   mkdir -p /data/meals/meal-manage/.deploy/mealserver/revisions
   printf '%s\n' '<已核实的40位commit>' \
     > /data/meals/meal-manage/.deploy/mealserver/revisions/<旧mealserver-tag>.commit
   chmod 600 /data/meals/meal-manage/.deploy/mealserver/revisions/<旧mealserver-tag>.commit
   ```

   不要从镜像时间戳推测 commit。无法核实旧镜像对应 commit 时，先补齐部署记录，否则新版后端回退会拒绝猜测。
4. 在 `/data/meals/.env` 中加入或更新 `BACKEND_IMAGE_TAG` 为当前运行的后端 tag，并配置 `FRONTEND_RELEASE_ROOT` 与 `FRONTEND_RELEASE_KEEP`。编辑时保留文件内其余私有配置。
5. 确认部署仓库没有 tracked 改动，记下当前 commit 后，仅更新服务器仓库文件。这个步骤不运行旧部署脚本、不启动或停止容器：

   ```bash
   git -C /data/meals/meal-manage status --porcelain --untracked-files=no
   git -C /data/meals/meal-manage rev-parse HEAD
   git -C /data/meals/meal-manage fetch origin master
   git -C /data/meals/meal-manage checkout master
   git -C /data/meals/meal-manage reset --hard origin/master
   ```

   上例分支名按实际部署配置替换。`reset --hard` 只可在确认仓库干净、已记录旧 commit 后执行。
6. 在服务器检查 Compose 配置；该检查不重启容器：

   ```bash
   cd /data/meals/meal-manage
   docker compose -f docker/docker-compose.yml --env-file /data/meals/.env config --quiet
   mkdir -p /data/meals/frontend/releases /data/meals/frontend/incoming \
     /data/meals/frontend/staging /data/meals/frontend/lock
   ```

7. 在开发机按下节发布首个 release。成功后首页、登录、REST API 代理、静态资源与 `release.json` 均应通过验证。再完成一次默认回退、指定版本回退、恢复新版本和后续版本自动回退演练。旧 mealweb 镜像至少保留一个完整发布周期。

## 日常前端发布

在干净且已提交的工作区，从仓库根目录运行：

```bash
export DEPLOY_TARGET=deploy@example-host
export DEPLOY_BASE_DIR=/data/meals/meal-manage
export ENV_FILE=/data/meals/.env
export FRONTEND_RELEASE_ROOT=/data/meals/frontend
export FRONTEND_RELEASE_KEEP=5
bash scripts/deploy-frontend-local.sh
```

发布器会检查 Node 与 lock 文件指纹，必要时执行 `npm ci --legacy-peer-deps`；然后设置 `VUE_APP_BASE_API=/` 构建、生成 `release.json`、归档和 SHA256，上传至服务器，原子更新远端管理脚本并调用 `install`。成功时打印 release ID、Git commit 和回退命令。

release ID 格式为 `YYYYMMDDHHMMSS-<7位Git短提交号>`。相同 ID 不可覆盖。服务器先校验 SHA256、tar 路径、成员类型、`index.html` 和 `release.json`，再解压至同文件系统 staging 目录。符号链接、硬链接、设备文件、路径穿越和重复归档成员会被拒绝。

管理脚本从传入的 `ENV_FILE` 读取 `FRONTEND_RELEASE_KEEP`（默认 5）；本地发布器设置同名环境变量时会显式覆盖。所有安装、切换、回退和清理操作使用 `flock` 串行执行。健康检查最多等待 90 秒。成功激活后保留最近配置数量的版本；`current`、`previous` 总会保留。`index.html` 和 `release.json` 不缓存，`/static/` 下构建资源使用一年 immutable 缓存。

## 查看和回退前端

在服务器执行，必要时把默认路径替换为实际配置：

```bash
/data/meals/meal-manage/scripts/manage-frontend-release.sh \
  --root /data/meals/frontend \
  --base-dir /data/meals/meal-manage \
  --env-file /data/meals/.env list

# 回退到 previous
/data/meals/meal-manage/scripts/manage-frontend-release.sh \
  --root /data/meals/frontend \
  --base-dir /data/meals/meal-manage \
  --env-file /data/meals/.env rollback

# 回退到指定 release
/data/meals/meal-manage/scripts/manage-frontend-release.sh \
  --root /data/meals/frontend \
  --base-dir /data/meals/meal-manage \
  --env-file /data/meals/.env rollback 20260922190000-a1b2c3d
```

回退同样重建 frontend 并检查 `release.json` 与首个 JS/CSS。目标检查失败时恢复原 `current` 和 `previous`；恢复失败时返回非零并保留现场。

## 后端独立发布与回退

服务器的 `/data/meals/deploy-bootstrap.sh` 继续更新仓库并调用新版 `deploy-from-github.sh`。后端源码变化时，该脚本先准备构建镜像，再只停止 backend 来释放构建内存；frontend 和 MySQL 保持运行，因此 Maven 构建期间后端 API 暂不可用。构建或新 backend 健康检查失败时会尝试恢复旧 backend tag。前端源码或运行配置变化时提示从开发机发布静态产物。它不再执行 `docker compose down`、不构建前端、不重建 frontend，也不清理旧 `mealweb` 镜像。

后端镜像通过 `org.opencontainers.image.revision` label 保存完整 Git commit。后端默认回退到当前 tag 的前一个镜像，也可指定 tag：

```bash
bash /data/meals/meal-manage/scripts/rollback.sh
bash /data/meals/meal-manage/scripts/rollback.sh 20260922190000
```

后端回退只重建 backend，并打印保持不变的前端 release ID。找不到已验证 commit 的旧镜像时，脚本会停止并要求补充 `.deploy/mealserver/revisions/<tag>.commit`，不会按镜像时间戳猜测。

## 首次切换失败时恢复旧前端

只有在首次切换还没有 `current` 的情况下需要执行此步骤。后续静态发布失败由管理脚本自动恢复旧 release。

1. 停止继续调用前端发布器，保留 `/data/meals/frontend` 中的 staging 和日志供排查。
2. 将部署仓库恢复到切换前记录的旧 Git commit。
3. 用切换前记录的 `mealweb` image tag 恢复旧 Compose 配置，并只重建 frontend，不影响 backend：

   ```bash
   cd /data/meals/meal-manage
   git reset --hard '<切换前Git commit>'
   IMAGE_TAG='<旧mealweb镜像tag>' docker compose \
     -f docker/docker-compose.yml --env-file /data/meals/.env \
     up -d --no-build --no-deps frontend
   ```

4. 确认旧首页和 API 代理恢复后，保留旧镜像及记录，修复原因后重新安排切换。

首次自动回退和人工回退演练成功前，不清理旧 `mealweb` 镜像、旧部署 commit 或回退信息。
