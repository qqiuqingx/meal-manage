# Agent 客户/订单表单草稿与页面预填设计

> 日期：2026-08-12
>
> 状态：已完成方案讨论，待书面规格复核
>
> 适用范围：`agent-service`、`eladmin-system`、`eladmin-web`
>
> 核心原则：Agent 只生成辅助草稿，不新增客户或订单；最终提交必须由客服在现有业务表单中完成。

## 1. 背景与目标

当前智能客服 Agent 以只读查询和排餐诊断为主，前端已经支持从对话结果跳转到客户档案、客户订单和排餐页面，但只携带受控查询条件，不能辅助新增业务数据。

本功能希望支持客服通过自然语言表达“新增客户”或“给客户新增订单”。Agent 解析资料、解决关键歧义并生成结构化表单草稿，客服确认草稿摘要后跳转到客户或订单页面。页面自动打开现有新增表单并预填数据，最终仍由客服核对、补充并点击“确认新增”。

目标包括：

- 降低客户建档及订单录入的重复手工填写成本。
- 尽量覆盖所有可由文本可靠表达和校验的客户、首单及新增订单字段。
- 复用现有客户和订单表单、权限、字典、复杂控件及业务校验。
- 保持 Agent 不直接写入客户、订单、排餐、核销等正式业务数据的边界。
- 通过固定草稿协议和固定页面动作，禁止模型控制任意前端路由。

## 2. 已确认的产品决策

### 2.1 对话追问策略

采用“关键歧义必须问，普通缺失项交给表单补充”的策略：

- 客户身份、套餐、换菜菜品、试餐关联等歧义可能造成对象关联错误时，Agent 必须继续追问。
- 普通必填项缺失时不逐项盘问。草稿卡片列出缺失项，跳转后由表单高亮提示。
- 客服可在跳转前通过自然语言纠正草稿，例如“手机号改成……”或“不是 A 套餐，是 B 套餐”。

### 2.2 新增客户语义

“新增客户”沿用当前业务的一体化流程，表示“新增客户档案 + 首单”。草稿同时包含客户资料和首单资料，跳转到现有客户新增表单。

### 2.3 新增订单的客户匹配

- 新增订单必须先关联当前客服数据范围内的已有客户。
- 没有匹配客户时不生成订单草稿，提示未找到，并提供“转为新增客户 + 首单”动作，复用已解析资料。
- 匹配到多个客户时展示脱敏候选列表，由客服明确选择后再生成订单草稿。
- 不允许按第一条、最近下单或其他启发式规则自动选定客户。

### 2.4 跳转时机与提交边界

- Agent 先展示草稿摘要、缺失字段和风险提示。
- 只有客服点击“去新建客户”或“去新增订单”后才跳转。
- 页面自动打开新增表单并预填，但不会自动提交。
- Agent 永远不调用客户或订单新增接口，也不声称已经完成新增。

### 2.5 页面形态

采用跳转客户/订单业务页面的方式，不在对话页复制正式新增弹窗或侧边编辑抽屉。

原因：现有表单包含套餐、指定配送日期日历、换菜规则、试餐关联、过敏及排除菜品等复杂控件。跳转业务页面可以保持唯一正式编辑入口，避免两套表单逻辑和校验规则分叉。

### 2.6 敏感信息决策

按产品决策，客服在对话中输入的完整手机号、详细地址等资料：

- 可以发送给当前配置的模型服务商参与解析。
- 原始客服消息继续按现有会话机制长期保存，恢复历史会话时仍可查看。
- 可以保存在服务端表单草稿的完整 `payload` 中，供正式表单领取。
- 不得写入普通应用日志、工具追踪、卡片摘要、运营指标明细或错误详情。
- Agent 的助手回答和草稿摘要默认脱敏，避免重复扩散敏感值。

该选择改变了现有“完整手机号和地址不得进入 Agent 模型”的安全基线。上线前必须在模型服务商数据处理约定、会话访问权限和数据保留制度层面完成内部确认；本设计不通过技术实现隐瞒这一数据流。

### 2.7 首期范围

- 文本可表达且能够可靠解析、校验的字段尽量覆盖。
- 首期不支持图片上传、图片识别或图片字段预填。
- 不支持 Agent 自动提交、对话卡片内逐字段编辑、草稿转交其他客服。
- 首期不建设独立草稿审计模块、审计表、审计接口或审计页面。

## 3. 总体架构

```text
客服输入新增意图和资料
  ↓
eladmin-system 保存会话消息并签发可信访问上下文
  ↓
agent-service 识别意图、调用受控只读工具解决关键关联、生成结构化草稿候选
  ↓
eladmin-system 校验权限、字段白名单、关联对象和草稿版本，并保存服务端草稿
  ↓
对话页展示脱敏草稿摘要、缺失项、风险提示和固定动作按钮
  ↓ 客服点击“去新建”
固定业务路由仅携带 draftId
  ↓
客户/订单页面领取草稿，自动打开现有新增表单并预填
  ↓
客服核对、修改、补齐并手动确认
  ↓
现有新增接口执行全部权限与业务校验，在成功事务中标记草稿已提交
```

### 3.1 `agent-service` 职责

- 识别 `CREATE_CUSTOMER_WITH_ORDER` 和 `CREATE_ORDER` 意图。
- 从对话上下文提取字段，区分已识别、缺失和存在风险的字段。
- 通过受控只读工具解析客户、套餐、菜品和试餐订单等关联对象。
- 对关键歧义发起追问，处理候选选择和跳转前的自然语言纠正。
- 返回结构化草稿候选和受控 UI 动作建议。
- 不连接数据库，不调用客户或订单新增接口，不返回任意 URL。

草稿保存不注册为允许模型自由调用的业务写工具。模型只返回类型化草稿候选；`agent-service` 的应用层校验该候选后，通过主系统内部草稿接口执行 `saveFormDraft`。该操作只写辅助草稿，不改变 12 个正式只读业务工具的既有边界。

### 3.2 `eladmin-system` 职责

- 校验 Agent 入口权限、目标新增权限和当前数据范围。
- 对草稿字段执行类型、长度、枚举、关联对象和目标表单白名单校验。
- 创建、修订、领取、过期和提交服务端草稿。
- 为前端返回固定动作类型和不可猜测的 `draftId`。
- 正式新增时继续调用现有客户/订单 Service，并在同一事务中关联草稿提交状态。

### 3.3 `eladmin-web` 职责

- 展示草稿摘要、缺失字段、风险提示和固定动作按钮。
- 只按本地动作白名单映射业务路由，不读取服务端提供的 `route`、`path`、URL 或任意 query。
- 跳转后领取草稿、加载真实关联选项并打开现有新增表单。
- 用黄色提示缺失或待复核字段，用现有红色规则提示非法字段。
- 只由客服点击现有表单按钮触发正式新增。

## 4. 独立表单草稿协议

### 4.1 草稿类型

首期定义：

| 类型 | 含义 | 目标页面 |
| --- | --- | --- |
| `CREATE_CUSTOMER_WITH_ORDER` | 新增客户档案及首单 | 客户档案页面 |
| `CREATE_ORDER` | 给已匹配客户新增订单 | 客户订单页面 |

`CONVERT_TO_CUSTOMER_WITH_ORDER` 是对话动作，表示“新增订单未找到客户后转为新增客户 + 首单”。执行该动作后，持久化草稿统一规范为 `CREATE_CUSTOMER_WITH_ORDER`，同时保留非敏感的来源类型字段，避免正式表单支持冗余草稿类型。

### 4.2 草稿结构

```json
{
  "draftId": "afd_不可猜测随机值",
  "draftType": "CREATE_CUSTOMER_WITH_ORDER",
  "schemaVersion": "v1",
  "status": "READY",
  "revision": 3,
  "sourceSessionId": "会话ID",
  "sourceMessageId": "消息ID",
  "payload": {
    "customer": {},
    "order": {}
  },
  "recognizedFields": [],
  "missingFields": [],
  "warnings": [],
  "expiresAt": "2026-08-13T18:00:00+08:00"
}
```

约束：

- `payload` 必须按草稿类型使用明确 DTO，不接受任意 Map 直接进入业务表单。
- `recognizedFields`、`missingFields` 使用登记的字段路径，不能由模型生成任意前端选择器。
- `warnings` 使用稳定告警码和安全展示文本，不包含完整手机号、地址或对话原文。
- `schemaVersion` 用于主系统和前端兼容判断，不匹配时禁止静默套用全部字段。

### 4.3 生命周期

```text
EDITABLE → READY → CLAIMED → SUBMITTED
    │         │        │
    └─────────┴────────┴→ EXPIRED / CANCELLED
```

- `EDITABLE`：关键歧义未全部解决，允许对话修订，不显示“去新建”。
- `READY`：关键歧义已解决，可以跳转和领取。
- `CLAIMED`：目标页面已经领取；表单仍由客服编辑，领取本身不产生业务写入。
- `SUBMITTED`：正式客户或订单新增成功，草稿不能再次提交。
- `EXPIRED`：默认创建或最后一次有效修订后 24 小时过期。
- `CANCELLED`：客服显式放弃，或草稿被新草稿替代。

跳转前的对话纠正更新同一 `draftId` 并通过乐观锁递增 `revision`。首次领取后，客服应在正式表单内继续修改；如返回对话重新生成资料，应创建新修订并要求业务页面重新领取，不能静默覆盖已打开页面中的本地编辑。

刷新目标页面可以重新领取同一 `READY/CLAIMED` 草稿，但不会自动调用新增接口。`SUBMITTED` 草稿只能查看状态，不能再次预填成可提交的新表单。

## 5. 对话处理设计

### 5.1 意图与关键歧义

以下情况必须在对话中解决：

- 新增订单所关联的客户没有唯一匹配。
- 父套餐或子套餐名称匹配多条有效记录。
- 换菜规则中的原菜或目标菜不能唯一匹配。
- 试餐成单关联订单不能唯一确定或不满足现有试餐订单规则。
- 用户表达包含互相冲突的日期、餐次、餐数或对象身份。

普通字段缺失、可由正式表单默认值处理的字段，以及不影响对象归属的非关键字段，不阻塞草稿进入 `READY`，但必须出现在 `missingFields` 或 `warnings` 中。

### 5.2 客户候选与转换

- 客户候选卡片仅展示当前客服可见范围内的脱敏信息和受控 `customerCode`。
- 选择候选后，主系统重新校验客户数据范围，不能把候选卡片本身当作授权依据。
- 找不到客户时显示“转为新增客户 + 首单”，复用对话中已解析的客户及订单字段。
- 转换后重新执行客户建档必填项、套餐编号池和首单规则检查。

### 5.3 草稿卡片

草稿卡片展示：

- 草稿类型和当前版本。
- 客户及订单的脱敏关键摘要。
- 已识别字段数、待补充字段名和风险提示。
- `继续对话修改` 的提示。
- 草稿为 `READY` 时显示固定“去新建客户”或“去新增订单”按钮。
- 草稿已提交、过期或取消后，按钮转为只读状态并显示明确原因。

## 6. 字段覆盖范围

首期原则是“文本可表达的尽量覆盖”，但字段必须进入明确 DTO，并复用现有业务校验。

### 6.1 客户字段

包括但不限于：

- 客户姓名、联系人、手机号、性别。
- 默认、工作日、周末等地址槽位及地址明细。
- 过敏标签、饮食限制、排除菜品、排除日期、特殊要求。
- 当前客户新增表单支持的其他纯文本、枚举或可解析关联字段。

### 6.2 首单及新增订单字段

包括但不限于：

- 已有客户关联、父套餐、子套餐。
- 早餐数、午晚餐数和每餐菜品数量配置。
- 总金额、成交金额、定金、早餐及午晚餐单价等可编辑金额字段。
- 成交时间、首次配送时间、开始日期、结束日期和开始餐次。
- 餐次类型、排餐模式、指定配送日期及每个日期的餐次。
- 销售渠道、米饭数量、米饭类型、汤数量、备注。
- 试餐成单标识及关联试餐订单。
- 订单级换菜规则中的原菜、目标菜、启用状态和备注。

金额字段是否实际预填和可编辑，继续由 `customerOrder:amount:edit` 控制。没有金额编辑权限时不得利用草稿绕过后端归零或保留原值规则。

### 6.3 不在首期的字段

- 自定义菜单图片及其他图片附件。
- 图片 OCR 或多模态识别。
- 无法映射到当前表单 DTO 的自由扩展字段。

### 6.4 校验责任

Agent 提供的是字段候选，不是业务校验结论。以下规则必须由主系统在保存草稿、领取草稿或最终新增时重新检查：

- 日期、时间、数字、枚举和字段长度。
- 父子套餐关系、套餐启用状态及编号池条件。
- 客户、订单、试餐订单、菜品之间的对象关系。
- 金额关系、餐数关系、开始餐次与餐次类型兼容性。
- 订单开始日期及餐次冲突。
- 地址、试餐简化建档、换菜规则和指定配送日期的现有业务规则。

最终新增接口是业务规则的最终真相源。草稿校验通过不能替代正式提交校验。

## 7. 前端导航与表单接收

### 7.1 固定动作白名单

前端只识别：

- `OPEN_CREATE_CUSTOMER_WITH_ORDER_FORM`
- `OPEN_CREATE_ORDER_FORM`
- `CONVERT_TO_CREATE_CUSTOMER_WITH_ORDER`
- `RETURN_TO_SOURCE_AGENT_SESSION`

动作数据只允许包含 `draftId`、来源会话标识和必要的受控业务编号。任何服务端返回的 URL、路由 path、组件名或任意 query 均被忽略。

### 7.2 跳转和领取

- 使用当前 Vue Router 在同一页面标签内跳转。
- URL 只携带 `draftId`，不携带手机号、地址、金额、备注或完整 JSON。
- 业务页面创建后调用领取接口，并在领取成功后自动打开现有新增弹窗。
- 领取返回当前最新 `revision`、类型化 `payload`、缺失字段和告警。
- 页面加载真实字典及关联对象；关联对象已删除、禁用或越权时，不保留为有效选项，要求客服重新选择。

### 7.3 页面提示

- 顶部提示“来自智能客服草稿”、草稿版本和“提交前请人工核对”。
- 缺失或待复核字段使用黄色提示，不改变现有必填校验规则。
- 非法字段继续使用现有红色表单校验。
- 提供“返回原会话”入口。
- 无权限、过期、已提交或版本不兼容时不打开空白新增表单，以免造成预填成功的误解。

### 7.4 正式提交

- 现有新增请求增加可选 `draftId` 和 `draftRevision`。
- 未带草稿标识时保持现有新增行为，保证接口向后兼容。
- 带草稿标识时，后端重新校验所有权、类型、状态和版本。
- 客户或订单新增成功与草稿转为 `SUBMITTED` 必须处于同一数据库事务。
- 草稿记录保存创建后的客户或订单业务标识，用于防重复提交和状态展示，不用于扩大 Agent 查询权限。

## 8. 主系统存储与接口

### 8.1 草稿表

新增 `agent_form_draft`，建议包含：

| 字段 | 用途 |
| --- | --- |
| `id` / `draft_id` | 数据库主键和不可猜测业务标识 |
| `draft_type` / `schema_version` | 草稿类型及协议版本 |
| `status` / `revision` | 生命周期和乐观锁版本 |
| `payload` | 完整类型化草稿 JSON |
| `recognized_fields` / `missing_fields` / `warnings` | 表单提示元数据 |
| `source_session_id` / `source_message_id` | 来源会话与消息 |
| `owner_user_id` | 草稿所属客服 |
| `target_permission` | 目标表单所需新增权限 |
| `converted_from` | 非敏感的流程转换来源 |
| `expires_at` / `claimed_at` / `submitted_at` | 生命周期时间 |
| `target_business_id` | 成功新增后的目标标识 |
| 通用创建、修改、逻辑删除字段 | 复用项目实体规范 |

`payload` 包含敏感个人信息，数据库备份、访问权限和保留周期必须与客户资料相同等级管理。过期清理至少清空完整 `payload`，是否保留不含敏感信息的最小状态行由实际清理策略确定。

### 8.2 Agent 内部接口

- `POST /api/internal/agent/form-drafts`：校验并创建草稿。
- `PATCH /api/internal/agent/form-drafts/{draftId}`：携带期望 `revision` 修订草稿。

接口要求内部服务令牌和短期访问上下文，并重新校验当前客服权限。`agent-service` 的应用层在解析模型草稿候选后调用这些接口；模型不能直接看到或选择这些接口。草稿校验和保存只有这一套主系统应用入口。

### 8.3 登录客服接口

- `POST /api/agent/form-drafts/{draftId}/claim`：领取当前最新草稿。
- `GET /api/agent/form-drafts/{draftId}/summary`：恢复会话时读取脱敏摘要和状态。

正式提交继续调用现有客户或订单新增接口，只增加可选草稿关联字段，不新增 Agent 专用业务写接口。

## 9. 权限和安全

### 9.1 权限矩阵

- 新增客户草稿：`agentDiagnosis:list` + `customerProfile:add`。
- 新增订单草稿：`agentDiagnosis:list` + `customerOrder:add`。
- 客户、套餐、菜品和试餐订单解析还需要对应查询权限及数据范围。
- 创建、修订、领取和提交每一步都重新校验，不依赖先前结果。
- 草稿绑定创建客服；首期不支持管理员代领或跨客服转交。

### 9.2 输入和输出安全

- 草稿 DTO 拒绝 SQL、表名、任意 URL、路由、权限集合、Token 和未登记字段。
- 自由文本执行长度限制、HTML 转义和提示注入检测；进入正式业务字段后仍按现有规则处理。
- 完整手机号和地址只出现在原始会话、模型请求、草稿 `payload` 和有权客服领取后的正式表单中。
- 助手回答、候选卡片、草稿摘要、错误响应和普通日志默认脱敏。
- 草稿内容不写入 URL、浏览器 `localStorage` 或 Vuex 持久化存储。
- `draftId` 使用足够熵的随机标识；即使被猜到，也必须通过所有权和权限校验。

## 10. 异常处理

- 无法可靠识别新增意图：继续普通对话，不生成半成品草稿。
- 关键对象歧义：返回候选并等待选择，不进入 `READY`。
- 草稿保存失败：不显示“去新建”，不声称已保存。
- 乐观锁冲突：返回最新修订摘要，要求基于新版本继续修改。
- 领取时过期、越权、已提交或版本不兼容：不打开新增弹窗，显示稳定业务错误。
- 字典或关联对象加载失败：保留已领取表单状态，禁止提交并允许重试加载。
- 最终新增校验失败：停留在现有表单，草稿保持 `CLAIMED`，允许修改后重试。
- 网络重试：使用幂等键；同一草稿只能关联一次成功新增。
- 客户或订单新增事务回滚：草稿不得进入 `SUBMITTED`。

## 11. 日志、审计与指标

首期不建设独立草稿审计能力：

- 不新增草稿审计表、审计接口、审计详情页面或人员操作轨迹。
- 草稿表只保留其正常生命周期所需的创建人、创建/修改时间、状态、版本和过期时间。
- 正式新增客户或订单继续沿用现有业务日志，不额外复制一份 Agent 草稿审计记录。
- 应用错误日志只记录 `requestId`、`draftId`、稳定错误码、状态和耗时，不记录完整草稿、手机号、地址或对话原文。
- 首期不强制建设专门运营指标；灰度验证优先使用测试、人工验收和不含个人信息的系统级计数。后续如需指标，另行明确口径和数据保留规则。

## 12. 测试与验收

### 12.1 `agent-service`

- 识别新增客户 + 首单和新增订单意图。
- 解析所有登记字段并拒绝未知字段。
- 对关键歧义追问，对普通缺失项生成提示。
- 客户未找到时生成转换动作，多匹配时要求人工选择。
- 自然语言纠正更新同一跳转前草稿版本。
- 助手回答和普通日志不回显完整手机号、地址和完整草稿。
- 不调用客户或订单新增接口，不接受任意路由指令。

### 12.2 `eladmin-system`

- 类型化 DTO、字段白名单、长度、枚举和关联关系校验。
- 创建、修订、领取、刷新、过期和取消状态转换。
- 乐观锁冲突、跨客服领取、权限变化和数据范围变化。
- 同一草稿只允许一次成功提交。
- 业务新增与 `SUBMITTED` 状态的事务一致性。
- 不带草稿标识的现有新增接口行为保持不变。
- 过期清理不会把敏感 `payload` 长期遗留。

### 12.3 `eladmin-web`

- 固定动作到固定路由的映射，忽略任意 route/path/URL。
- 跳转后领取草稿并自动打开新增弹窗。
- 客户、首单和新增订单字段映射。
- 指定日期日历、换菜规则、试餐关联、过敏和排除菜品等复杂控件回填。
- 缺失项黄色提示、非法项红色校验和来源提示。
- 返回原会话、刷新重领和提交成功后的只读状态。
- 过期、越权、已提交、版本不兼容时不打开空表单。

### 12.4 端到端场景

1. 从完整话术生成客户 + 首单草稿并成功预填、人工提交。
2. 给唯一匹配的已有客户生成新增订单草稿。
3. 客户多匹配，选择候选后继续。
4. 客户未找到，转换为新增客户 + 首单并复用资料。
5. 跳转前在对话中纠正字段，页面领取最新修订。
6. 缺少普通字段时仍可跳转，页面高亮并由客服补齐。
7. 套餐、菜品或试餐订单在领取前失效，页面要求重新选择。
8. 草稿过期、重复点击、重复提交和跨客服猜测 `draftId` 均安全失败。
9. 尝试注入任意路由、额外 JSON 字段、SQL、HTML 和超长文本均被拒绝或安全转义。
10. 正式新增失败后可在原表单修正并重试，不产生重复业务记录。

## 13. 发布顺序与回滚

建议按以下顺序灰度：

1. 上线主系统草稿表、草稿应用服务和领取接口，暂不开放入口。
2. 上线客户/订单页面预填能力，用测试草稿完成复杂控件回归。
3. 上线 Agent 草稿候选协议、对话修订和草稿卡片，仅对白名单客服开放。
4. 完成人工验收后逐步扩大范围。

功能开关关闭后，Agent 不再生成草稿卡片，客户/订单现有页面和新增接口继续按原方式工作。已有未提交草稿可自然过期并清理敏感 `payload`；数据库迁移本身按正常版本回滚策略处理。

## 14. 明确不做

- Agent 直接新增或修改客户、订单。
- 对话内弹窗或侧边抽屉承载正式完整表单。
- 自动选择多匹配客户、套餐、菜品或试餐订单。
- 图片上传、图片 OCR、多模态建档。
- 草稿跨客服共享或转交。
- 独立草稿审计模块。
- 对话内逐字段表单控件。
- 模型返回任意前端路由。

## 15. 成功标准

- 客服能从自然语言生成客户 + 首单或新增订单草稿，并在业务页面看到可靠预填结果。
- 关键对象歧义在跳转前完成确认，普通缺失字段在页面清晰提示。
- 最终新增只能由客服在现有表单中手动触发，并执行现有全部权限和业务校验。
- 不出现跨客服草稿访问、重复提交、任意路由跳转或敏感数据进入普通日志。
- 关闭该能力后不影响现有 Agent 只读查询及客户/订单手工新增流程。
