# Phase 02 客户共享字段及客户编号同步

## 执行前规则检查

- 重新读取当时生效的 `AGENTS.md` 规则链；检查客户、套餐、订单业务说明及目标代码目录规则。
- 读取 Phase 01 的阶段交付记录、实际接口和审计表契约；如实际产物不同，先修订本阶段。

## 目标

将过敏、特殊要求和客户编号接入同一个即时更新入口，并准确记录跨实体变化。

## 前置依赖

- Phase 01 completed；需要可用的 PATCH 白名单、旧值冲突处理、事务内审计表与插入能力。

## 输入与输出

- 输入：Phase 01 接口/审计契约、`CustomerProfile`、父套餐编号池、现有手动客户编号规则。
- 输出：三个客户相关字段的事务更新、双实体客户编号审计、相关测试及业务文档更新；供 Phase 03 调用。

## 本阶段实施约束

- 过敏与特殊要求只更新客户档案；不要复制到订单表。过敏标签沿用现有去空、去重逻辑，允许清空；特殊要求允许清空。
- 客户编号只同步客户档案和当前订单，不批量改其他订单。校验当前订单父套餐的编号池前缀、数字区间和客户档案唯一约束；数字后缀长度沿用现有手工编号规则，不固定要求与自动生成值同宽，并遵守 `customer_code` 的 16 字符存储上限。同一客户保留自身原编号时不应误判冲突。
- 同一事务内检查旧值、更新两张表并写一条审计；`before_state`/`after_state` 按实体 ID 清楚记录两处编号。无数据库全表操作。
- 订单终态与编辑权限沿用 Phase 01，未获权限者不能通过档案字段绕过订单行内接口。

## 涉及文件

预计修改：订单模块的 `CustomerOrderServiceImpl.java`、`CustomerOrderInlineUpdateDto.java` 与相应 Service 测试，客户模块的 `CustomerProfileMapper.java` 或相关专用 Mapper，`eladmin/doc/business/客户管理业务说明.md`、`eladmin/doc/business/套餐管理业务说明.md`、`eladmin/doc/business/订单管理业务说明.md`、`eladmin/doc/apidoc/客户订单管理接口文档.md`。只有现有边界确实无法复用时才新增专门的编号校验方法，不新增可编辑任意客户字段的通用接口。

## 实施步骤

1. 核对客户编号的现有手工输入规则与编号池配置读取方式，确定当前订单父套餐的校验来源；确认编号同步对订单查询、客户页面的显示影响。
2. 扩展 PATCH 白名单，处理 `allergyTags` 数组和 `specialRequirements` 字符串；在事务中读取/锁定客户档案，以客户档案当前值比对 `expectedValue`，仅更新该字段。
3. 处理 `customerCode`：校验格式、区间与唯一性，事务内定向更新客户档案和当前订单；保留其他订单编号。数据库唯一键冲突映射为可理解的业务错误。
4. 扩展审计快照，记录客户档案字段实际旧新值；编号包含订单与档案两份旧新值。逐一测试旧值冲突、空值、重复标签、非法编号、并发唯一冲突、跨实体更新失败回滚。
5. 同步业务文档及 API 文档中客户共享数据、编号同步范围、错误响应和审计语义。

## 验证方式

- 编译受影响模块并运行客户档案/订单相关定向测试；验证客户档案及当前订单值一致，其他订单编号未被改动。
- 检查审计前后状态可据此手动恢复；模拟第二张表或审计写入失败，确认事务回滚。只清理本次测试 ID。

## 完成标准

- 三个字段通过同一入口按确认范围保存，数据归属正确。
- 客户编号校验与唯一约束有效，双表更新和审计具备原子性。
- 其他订单的编号保留原值；过敏/特殊要求在同客户其他订单列表中读到最新档案值。

## 阶段交付记录

已完成：

- `allergyTags` 规范化去空、去重后仅更新客户档案；`specialRequirements` 仅更新客户档案，空白文本规整为 null。两者通过客户行锁按规范化旧值比较。
- `customerCode` 按当前订单父套餐的 `poolPrefix/poolStart/poolEnd` 校验，校验档案唯一约束，并只同步当前订单与客户档案。数字后缀不要求固定宽度，整体不超过 16 字符；另一订单的冗余编号不批量修改。数据库唯一键并发冲突转换为可读业务错误。
- 审计状态使用 `customer_order:{id}` 和 `customer_profile:{id}` 两个键分别记录编号前后值；共享字段状态记录档案字段前后值。客户档案字段显示依赖列表现有 `customer_profile` 关联查询。
- 定向服务测试覆盖标签规范化、双实体编号同步及变宽数字后缀；最终后端相关测试 22/22 通过。唯一键并发竞争、第二实体/审计写入故障的真实数据库回滚未在本地数据库验证。
- Phase 03 只需调用统一 `updateInline(id, { field, value, expectedValue })`；过敏期望值使用列表数组，客户编号期望值取当前订单行 `customerCode`。
