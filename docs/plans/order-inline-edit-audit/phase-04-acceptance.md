# Phase 04 契约、跨模块回归与交付检查

## 执行前规则检查

- 重新读取当时生效的 `AGENTS.md` 规则链，读取前三个 Phase 的阶段交付记录及实际接口/数据库契约。
- 核对文档更新范围、测试数据清理规则和目标环境 DDL 发布要求。

## 目标

证明端到端行为、日志可追溯性和现有编辑能力均符合确认范围，并把发布与手动回退步骤写清楚。

## 前置依赖

- Phase 01、02、03 completed；需要迁移脚本、后端 PATCH、前端行内入口及各阶段测试结果。

## 输入与输出

- 输入：前三阶段实际产物、订单/客户/套餐业务文档、订单 API 文档、可用测试环境。
- 输出：完成的契约文档、回归记录、部署顺序和手动回退操作说明。

## 本阶段实施约束

- API 变更文档应列出权限、请求与响应、字段类型、冲突/校验错误、审计范围；业务文档写清客户编号同步范围和客户共享字段影响。
- 不运行无条件全表删除，不用 Docker 查询数据库；测试数据仅按本次记录的 ID 清理。
- 无需为验证而新增生产代码或重构无关模块；保留工作区既有改动。只有用户要求时提交。

## 涉及文件

核查并按实际结果修改：`eladmin/doc/apidoc/客户订单管理接口文档.md`、`eladmin/doc/business/订单管理业务说明.md`、`eladmin/doc/business/客户管理业务说明.md`、`eladmin/doc/business/套餐管理业务说明.md` 中确有规则变化的段落；计划文件的阶段交付记录与 `status.yaml`。必要时新增简短的审计查询/手动回退说明，放在订单文档附近。

## 实施步骤

1. 按字段做端到端矩阵：规格三项、汤 0/1、排餐模式、图片增删、过敏增删、特殊要求清空、早餐/午晚边界、状态暂停/恢复、客户编号合法/冲突；逐项检查页面、数据库实际值和审计前后快照。
2. 检查有多个订单的同一客户：档案字段在所有订单展示更新；客户编号仅当前订单和档案变化，其他订单原值不变。
3. 验证并发旧值冲突、权限拒绝、终态拒绝、写审计失败回滚，以及原完整编辑弹窗、退餐、金额权限和列表筛选未回归。
4. 核对迁移执行顺序：先审计表、再后端、再前端；给管理员写明按审计 ID 查询、逐笔对比当前值、通过受控业务修改或经审批的限定 ID SQL 手动回退的步骤，不自动删除审计记录。
5. 记录实际验证命令和结果，检查文档链接与 `git diff --check`；总结未覆盖风险。更新各阶段交付记录及 `status.yaml`。

## 验证方式

- 后端相关模块编译和定向测试、前端修改文件 lint/相关测试；如环境可用，在隔离数据上做真实接口与表验证。测试结束只清理本次数据。
- 检查 DDL 与 API 文档和代码一致，审计快照足以恢复修改前状态；仅注释或文档的后续修订无需重复 Maven 测试。

## 完成标准

- 逐字段成功、失败、并发和权限场景有可追溯的验证记录；原有主要订单操作可用。
- 业务/API/回退说明与实际实现一致，审计可按订单和操作人查到每次变更的前后状态。
- `status.yaml` 与每个 Phase 的交付记录反映真实完成情况，没有把跳过测试的构建写成测试通过。
