# Phase 03 订单列表行内交互与手机号列

## 执行前规则检查

- 重新读取当时生效的 `AGENTS.md` 规则链、订单页及共用表单相关约束。
- 读取 Phase 01、02 的阶段交付记录和实际 PATCH 契约，核对字段、空值及错误响应。

## 目标

在订单列表接入全部已确认字段的单元格即时保存，取消手机号固定，并保留原完整编辑弹窗。

## 前置依赖

- Phase 01、02 completed；需要已验证的 PATCH 接口、字段白名单和审计闭环。

## 输入与输出

- 输入：现有 `el-table`、订单 API、图片上传流程、权限及后端契约。
- 输出：可操作的订单行内编辑、保存中/失败/冲突反馈、针对性交互测试。

## 本阶段实施约束

- 手机号列只去掉 `fixed="left"`；不引入拖拽排序库。保留客户编号、客户姓名和操作列现有固定行为。
- 仅拥有 `customerOrder:edit` 且订单状态为 1/4 时显示编辑入口。无权限或终态行只读；金额权限不受影响。
- 文本/数字在失焦或回车时提交，Esc 放弃，选择值改变时提交；同一行保存中禁用重复提交。保存失败恢复显示值并刷新最新行；旧值冲突给出明确提示。
- 规格在同一单元格露出主菜、副菜、素菜三个输入，但每个子字段作为一次独立更新；含汤只提交 0/1。可计算列（合计、剩余、预计剩余等）不可编辑。
- 自定义菜单继续复用上传接口；上传成功后保存新路径，删除图片提交空值。接口保存失败时保留旧图片引用，不删除物理文件。过敏标签支持增删并在每次确认后保存。
- 不把列表行拼成整单 `PUT`；成功后刷新当前分页，保持横向滚动位置，并让同客户其他行显示最新共享字段。

## 涉及文件

预计修改：`eladmin-web/src/views/customer/order/index.vue`、`eladmin-web/src/api/customer/order.js`；如现有页面过大，可增加订单页专用单元格组件或纯数据 helper，但不抽象成全站通用表格框架。交互测试只覆盖真实保存路径。

## 实施步骤

1. 在订单 API 增加 PATCH 调用；前端统一构造 `field/value/expectedValue`，按字段传 JSON 数字、字符串、数组或 `null`。
2. 移除手机号列 `fixed`；为各目标列增加只读展示与编辑态，保持现有金额、状态、操作列渲染。规格输入显示三个原始数量，汤用含汤/不含汤选择。
3. 实现单元格进入、失焦/回车/选择保存、Esc 取消、防重复请求、冲突/失败回滚；成功刷新当前页及派生字段，恢复横向位置。
4. 复用图片上传结果路径，先上传再 PATCH；图片删除走 PATCH。处理上传成功而字段保存失败的提示和旧引用显示。
5. 用实际事件测试至少覆盖文本失焦、下拉即时保存、数值合法性、权限/终态只读、接口失败恢复和冲突刷新；不写仅镜像组件实现的测试。

## 验证方式

- 在 `eladmin-web/` 对修改文件运行 ESLint，运行覆盖本交互的相关前端测试；无需因普通页面修改默认做生产构建。
- 手动检查横向滚动时手机号随动、固定列保持、连续编辑时焦点/滚动位置、图片预览与失败反馈。

## 完成标准

- 所有指定列按约定触发即时保存，保存中不会重复提交，失败不会假装成功。
- 手机号列可横向滚动；原完整编辑弹窗、退餐和分页筛选仍可用。
- 前端只调用新的受限 PATCH，权限状态与服务端一致，相关 lint/测试通过。
