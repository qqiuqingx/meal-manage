# 订单列表行内编辑与变更审计

## 背景与目标

订单列表的手机号列取消左侧固定。用户可在列表中修改规格（主菜、副菜、素菜数）、含汤、排餐模式、特殊要求、自定义菜单、过敏标签、早餐数、午晚数、状态和客户编号；完成一次单元格输入或选择后立即保存。每次成功修改都留下足以让管理员手动回退的前后状态。

## 已确认的业务决定

- “手机号可以拖动”指取消 `fixed="left"`，随表格横向滚动；不实现列顺序拖拽。
- 规格分别编辑 `mainDishCount`、`sideDishCount`、`vegCount`；含汤切换写入 `soupCount=1/0`。
- “编号”指客户编号。修改后同步 `customer_profile.customer_code` 和**当前** `customer_order.customer_code`，不改该客户其他订单。
- 过敏标签和特殊要求归属客户档案；编辑某订单行后，该客户其他订单的展示值也会变化。
- 文本、数字在失焦或回车时保存，选择项在选中后保存；不在每次击键时发送请求。
- 日志保存每次修改前后的实际值，供管理员手动回退；不开发一键回退或历史页面。

## 跨阶段约束与公共契约

- 新增 `PATCH /api/customer/order/{id}/inline`，使用现有 `customerOrder:edit` 权限与 `@Log` 约定。请求只允许白名单字段：`mainDishCount`、`sideDishCount`、`vegCount`、`soupCount`、`scheduleMode`、`specialRequirements`、`customMenuImage`、`allergyTags`、`breakfastCount`、`lunchDinnerCount`、`status`、`customerCode`。请求含 `field`、`value`、`expectedValue`；服务端必须判断三个键均存在，支持预期值为 `null`。
- 服务端比较实际旧值与 `expectedValue`，不一致返回 HTTP 409；字段类型或业务校验错误返回 HTTP 400，权限不足沿用现有拒绝响应。比较数组时按已规范化的标签列表判断；只更新目标字段及业务必需的派生字段，不用列表数据拼整单 `PUT`。保存成功返回 204；前端刷新当前页取得计算字段及同客户其他行的最新值。
- 订单状态仍只允许进行中 `1` 与暂停 `4` 互切；终态订单不开放行内编辑。暂停生效日沿用现有转换规则。早餐/午晚修改继续校验已核销数与合计餐数并重算剩余数；客户编号遵守当前父套餐编号池格式、范围和客户档案唯一约束。金额、核销数、订单编号和其余字段不在行内接口开放。
- 新建追加式审计表 `customer_order_inline_audit`：记录订单 ID、客户 ID、字段键、操作人、时间、`before_state`、`after_state`。状态 JSON 必须包含该次事务实际改动的所有实体字段，例如餐数及剩余数、状态及暂停生效日、客户编号在订单与档案中的值。使用 fastjson2 序列化；更新和审计插入同一数据库事务。现有异步 `sys_log` 继续记录请求，不替代该审计表。
- 审计表只新增不清理历史数据，不开放修改/删除接口。管理员按审计 ID 和当前数据核对后手动回退；手动修复本身也须记录操作人、时间和修改前后值。数据库回退脚本不自动删除审计历史。
- 沿用 Vue 2.7、Element UI、Spring Boot 2.7.18、Java 8、MyBatis-Plus 和现有上传接口；无新增依赖、无测试专用生产接口。新 Java 方法写清用途/参数/返回，实体字段有业务注释，Entity 使用 `@Getter @Setter`，Service 优先构造器注入。
- 保留未提交的无关改动；禁止无条件全表删除、清表式测试初始化及将凭据写入文件。后端编译受影响模块并运行相关测试；前端对修改文件 lint、运行覆盖交互的相关测试；文档及 SQL 做轻量检查。不因构建跳过测试而宣称测试通过。

## 实施门禁

1. 在改动公共接口和新增表前复查仓库内调用方、现有表名/迁移顺序、测试及发布环境；若发现外部调用方或编号池规则与本计划冲突，先确定影响范围并修订计划。
2. 前端切换到新入口前，后端接口、审计表和相关校验先形成可验证闭环；完整编辑弹窗保持可用。
3. 数据库迁移需先在目标环境备份并确认 DDL 发布窗口；本计划不授权执行线上 DDL。

## 主要风险与回滚

- 客户编号同时存在于档案和订单；只改当前订单是已确认范围。其他历史订单保留旧编号，日志需清楚记录两条实际变更。
- 数量、状态影响排餐和核销；必须复用现有约束并测试临界值，不能只做前端校验。
- 旧完整编辑弹窗与行内入口并存；行内更新要做旧值冲突检查，完整编辑的已有覆盖行为作为单独风险记录，不为此需求改写整单契约。
- 部署时先应用新增表，再上线后端，最后上线前端。应用回滚时保留审计表及历史记录；前端可回退到原列表和完整编辑弹窗，必要的数据回退按审计状态逐笔核对。
