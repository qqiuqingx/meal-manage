# Agent 对话与易用性优化实施计划

## 背景

当前智能客服已经具备独立 `agent-service`、统一只读工具、主系统权限与会话持久化、结构化卡片以及前端固定组件展示。现有主要问题不在工具数量，而在已有能力没有形成完整的用户闭环：

- 普通查询完成后没有从成功工具调用中沉淀客户、订单、日期和餐次焦点，短句追问容易丢失上下文。
- Agent 成功响应统一标记为 `ANSWERED`，前端虽然保留 `missingSlots` 和 `quickReplies`，但澄清状态没有贯通。
- 用户问题同时进入 system 和 user message，造成重复提示和角色边界不清。
- 页面没有把消息级 `partial/warnings` 传给卡片，部分结果仍可能展示图表。
- 后端告警携带 `toolName:errorCode` 前缀，前端按裸错误码匹配，业务提示可能退化。
- 候选客户选择、快捷追问、失败重试、业务页面跳转和会话搜索等高频操作缺少完整入口。
- 页面混合业务结论、模型信息、规则摘要和工具追踪，业务用户需要承担过多技术信息。
- 诊断页和旧卡片组件存在职责堆叠与历史代码残留，继续直接叠加功能会提高维护成本。

## 目标

- 让“那晚餐呢”“昨天呢”“查一下这笔订单的核销”等追问稳定继承最近一次已确认的业务焦点。
- 对缺少客户、订单、日期、餐次或规则主题的问题返回明确的 `NEED_MORE_INFO` 状态和受控缺失项。
- 保持 LLM 负责理解目标和选择工具，Java 只从成功工具事实中确定性更新会话上下文。
- 修复部分结果、截断、权限不足和工具失败的展示一致性。
- 提供候选选择、快捷追问、重试、复制和固定业务跳转等直接操作。
- 提升会话查找、归档恢复和空会话管理体验。
- 将技术信息收拢为按需展开内容，默认突出结论、告警和业务数据。
- 在不扩大安全协议和抽象层的前提下收敛前端页面职责与历史死代码。

## 非目标

- 不新增写工具，不开放下单、排餐、核销、退餐、退款或客户修改能力。
- 不新增数据库表或字段；继续使用现有会话槽位、`business_result_json` 和会话版本字段。
- 不把完整消息历史、隐藏推理、Prompt 或工具原始输出保存为会话上下文。
- 不增加第二个 LLM 用于意图识别、槽位抽取或会话摘要。
- 不新增通用工作流引擎、通用前端动作 DSL、动态组件协议或任意路由协议。
- 不重新设计现有 12 个只读工具及业务指标口径。
- 不为所有异常增加多层 fallback；只处理已确认的业务错误码和正常兼容路径。
- 不在本计划中删除后端动作草稿、审计表或历史数据；这类能力是否下线需要单独业务决策。

## 简化实现原则

1. **上下文来自成功工具入参**：只从本轮成功工具的强类型输入中提取已确认标识和过滤条件，不从模型自然语言回答反向猜测。
2. **单一会话 Patch**：继续使用现有 `ConversationPatch`，不再创建平行的 Session Memory 体系。
3. **澄清使用一个小型响应协议**：只增加结果状态、缺失项和快捷回复；不把整段回答改造成复杂工作流状态机。
4. **前端动作固定枚举**：候选选择和业务跳转按已知 cardType 实现固定代码，不接受后端或 LLM 下发 URL、组件名和脚本。
5. **兼容旧响应**：旧 Agent 返回纯文本时仍按 `ANSWERED` 展示；旧历史卡片继续使用当前兼容层，不做批量回填。
6. **不重复展示告警**：消息级告警和查询时间只在业务结果顶部显示一次；卡片只接收完整性状态用于控制图表。
7. **先修正确性再重构**：Phase 01 至 Phase 05 完成并测试后，Phase 06 才拆组件和删除死代码。

## 影响范围

### `agent-service`

- LLM system/user message 组装。
- 最终回答的 `ANSWERED/NEED_MORE_INFO/ERROR` 结果协议。
- 从成功工具调用生成 `ConversationPatch`。
- `missingSlots`、`quickReplies`、受控查询摘要和 OpenAPI v2 契约。
- Runner、Controller、DTO、契约和上下文单元测试。

### 主系统 `eladmin-system`

- Agent HTTP 响应 DTO 和 v2 映射。
- 会话 Patch 提交、槽位更新、消息快照保存与恢复。
- 服务端会话关键字分页、归档恢复和现有并发语义回归。
- 智能客服接口文档与业务文档。

### 前端 `eladmin-web`

- 消息级完整性参数透传和告警码标准化。
- 澄清项、快捷回复、候选选择、失败重试、复制和固定业务跳转。
- 技术详情折叠、加载状态、发送状态和会话列表。
- 诊断页组件拆分、旧卡片组件与未使用 API 清理。

## 阶段依赖

```text
Phase 01 多轮焦点
  -> Phase 02 澄清契约
      -> Phase 03 完整性展示
          -> Phase 04 任务交互
              -> Phase 05 会话管理
                  -> Phase 06 代码收敛
                      -> Phase 07 联调验收
```

Phase 03 的纯前端修复可以提前开发，但为了避免重复调整消息模型，正式合并仍按以上顺序执行。

## 核心验收场景

1. `B3303 今天午餐排了吗？` -> `那晚餐呢？`：第二轮继承客户和日期，只替换餐次。
2. `订单 O20260711001 什么情况？` -> `最近核销呢？`：第二轮继承订单，不要求再次输入编号。
3. `查一下排餐`：返回 `NEED_MORE_INFO`，明确提示缺少客户或订单、日期等必要条件。
4. 姓名匹配多个客户：展示候选表，点击“选择”后自动发送客户编号继续查询。
5. 任一工具失败但其他工具成功：保留成功卡片，显示准确告警，隐藏依赖完整数据的图表。
6. 权限不足：显示权限提示，不显示“对象不存在”，不暴露工具名和内部错误文本。
7. 请求失败：原用户消息保留，可点击“重试本条”，不会创建重复用户消息或空会话。
8. 搜索第 20 条之后的历史会话：通过服务端关键字查询可以找到。
9. 归档会话后可在“已归档”中查看并恢复。
10. 普通业务查询默认只显示结论、告警和业务卡片；模型名、规则摘要和工具链路默认折叠。

## 主要风险

- **焦点串用**：客户切换时必须清空旧订单和排餐记录焦点；日期单值与范围必须互斥。
- **歧义客户误选**：名称或模糊搜索不能直接写入客户焦点，只有明确编号/ID或用户点击候选后才能提交。
- **模型协议兼容**：Provider 暂时返回旧纯文本时要保持可展示，但不能把纯文本关键词猜测成澄清状态。
- **历史快照兼容**：旧消息没有 `missingSlots/quickReplies` 时按空数组处理，不重新调用模型或查询业务。
- **部分结果误导**：消息级 `partial`、卡片截断或完整性告警任一成立时都不能显示完整性图表。
- **会话列表压力**：服务端关键字查询沿用分页和当前客服归属条件，不做一次性全量加载。
- **清理误删**：旧组件和 API 只有在运行时代码与路由无引用、对应测试完成迁移后才能删除。

## 回滚策略

- Phase 01、02 的新增响应字段均为兼容字段；回滚 Agent 时主系统和前端按旧 `ANSWERED` 纯文本处理。
- 会话 Patch 仍写入现有字段，不涉及 DDL；回滚不需要数据迁移，已保存安全槽位继续可读。
- Phase 03、04、05 可独立回滚前端，不影响后端查询事实和历史快照。
- Phase 06 删除旧组件前保留独立提交；出现回归时只回滚清理提交，不回滚已验证的交互修复。
- 发布按主系统兼容契约、Agent 服务、前端顺序；回滚按前端、Agent 服务、主系统逆序。

## 执行规则

1. 每次先读取 `status.yaml`，只加载 `current_phase` 对应文件。
2. 当前 Phase 的测试和完成标准全部通过后再更新状态。
3. 修改业务逻辑前读取 `eladmin/doc/business/智能排查助手业务说明.md`；完成后在 Phase 07 同步文档。
4. 新增或修改方法必须补充清晰方法注释。
5. 保留用户工作区中已有未提交修改，不回滚、不覆盖无关文件。
6. 测试不得新增或遗留业务数据；本计划原则上全部使用 mock/内存测试。
7. 如果实施中发现需要 DDL、写工具或通用动作协议，暂停该 Phase 并单独评审，不在本计划内顺带扩展。
