# 订单餐数截止与暂停生效日期

## 背景与目标

客户排餐日历当前将匹配送餐模式的每个日期餐次都预设为 1 份，导致 20 餐的 DAILY 午晚餐订单在第 10 天之后仍显示计划。用户确认：早餐与午晚餐各按自己的购买餐数池，从订单开始日期及开始餐次顺序分配；排除和人工数量覆盖应计入分配；暂停订单从首次 1→4 状态变更的当天起不再分配或生成。

## 影响范围与规则来源

- 已完整读取 `/Users/qqx/.codex/AGENTS.md` 和仓库根 `AGENTS.md`；目标目录无更深的 AGENTS.md。项目 `CLAUDE.md`、`eladmin/CLAUDE.md` 同时适用。
- 订单实体/保存接口/订单表、客户用餐统计接口、排餐生成服务、订单表单、相关业务与接口文档。
- 排餐模式当前使用 `SCHEDULE`、`DAILY`、`WEEKDAY`、`WEEKEND` 字符串；不新增并行枚举。
- 现有订单 33、65 为 DAILY 且无结束日期、无逐日覆盖；当前测试库共有 13 笔 DAILY 订单。改变基础计划会影响这些订单的日历和生成候选。

## 实施约束与公共契约

- `pause_effective_date` 为兼容性新增可空字段；只有后端检测到进行中 1→暂停 4 时自动写入本地业务日期，不允许由普通保存请求决定。暂停状态下不因再次编辑覆盖该日期；恢复进行中时清空以开始下一次暂停周期。
- 订单开始日期、开始餐次、排餐模式、指定日期、排除日期、人工份数覆盖按日期和早餐/午晚餐两池顺序计算；本月之外更早的安排也要占用购买餐数。已核销/已生成结果保留现有防重复、防删规则。
- 日历目标份数与排餐生成候选必须使用同一基础日期计算；未完成生成路径之前不切换现有可用行为。
- 不改订单购买餐数、核销餐数规则；数据库迁移只添加列，不自动修改现存订单。旧暂停订单若无生效日期，需显式核实数据再补齐，不能猜测。
- 修改公共 API/数据库前核对现有调用方；保留旧字段，新增字段以兼容方式返回。无新增依赖、无测试专用生产接口。按需运行 Java 8/Maven 3.5.2、前端测试和轻量 diff 校验。
- 业务逻辑修改前阅读对应业务文档，修改后同步 `eladmin/doc/business/`；接口变化同步 `eladmin/doc/apidoc/`。已有工作区改动不得覆盖。

## 风险与回滚

- 规则改变会让旧 DAILY 订单超过购买餐数的日期从日历消失；已有生成/核销结果必须单独显示并保护，不得被视图重算删除。
- 排除与人工覆盖可能使截止日期跨月；计算必须读取此前的有效覆盖并保留历史份数。
- 回滚应用时保留新增可空列和已有数据；不可直接删列或改写历史排餐记录。
