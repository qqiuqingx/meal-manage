## 目标

在客户档案页面提供上传、预览、确认和结果反馈，并以真实文件完成只读预览与受控导入验收。

## 前置依赖

- 本计划 Phase 01–03 全部完成；customer-meal-calendar-quantity Phase 01–03 全部完成。

## 输入与输出

- 输入：预览/提交 API、第三版业务工作簿、实际导入日期、操作人授权及数据备份。
- 输出：可操作的导入页面、逐位客户报告、排餐计划可见的未来数量和暂停标记、验收记录。

## 本阶段实施约束

- 预览只是只读；正式提交必须由有权限操作人明确触发。只有实际客户数据快照与导入日期一致，才可执行真实导入。
- 客户禁忌工作表始终忽略；跳过的错误行不生成半套数据。页面只显示必要的个人信息并遵守现有权限。
- 新/改接口同步文档；前端不自行计算后端写入值。

## 涉及文件

- 修改：eladmin-web/src/views/customer/profile/index.vue、eladmin-web/src/api/customer/profile.js、必要的订单列表状态文案、eladmin/doc/apidoc/客户档案管理接口文档、客户管理/订单管理/排餐管理业务说明。
- 可新增：客户导入预览弹窗组件与导入结果下载组件，文件保持职责单一。

## 实施步骤

1. 在客户档案入口加受 customerProfile:import 保护的导入按钮；上传后展示文件哈希、预计新增/跳过人数、各客户来源行、餐数、套餐、暂停判定和错误。
2. 确认提交时重传同文件和导入日期，显示逐位成功/跳过及行号原因；支持下载不含完整手机号/地址的异常清单。重复提交显示“已存在”而非再次新增。
3. 对暂停订单在排餐计划展示待通知、来源日期和份数，但不生成菜品；B596 在单客户弹窗显示两份、一份含汤，并在生成和逐份核销后余额正确。
4. 使用当前真实文件先只读预览。正式数据写入前核对哈希、9 月日期是否仍未配送、备份及权限；若快照过期，要求业务提供新文件，重新预览后再提交。
5. 运行后端相关测试、前端 lint/构建，检查文档、接口示例、回滚步骤与 git diff --check；形成不含敏感资料的验收摘要。

## 验证方式

- 以匿名样例走“上传→预览→部分成功提交→排餐计划→逐份核销”端到端链路。
- 真实文件只读预览能解释 4 条坏电话、153 条待通知和 B596 双份；真实写入仅在门禁满足后由授权操作人触发。
- 测试数据按本次新建主键清理，不删除业务记录。

## 完成标准

- 用户能在页面完成预览、提交和错误定位；排餐计划、暂停状态、订单余额与真实逐份行为一致。
- 两套计划各自的 status.yaml 与阶段交付记录完整；真实数据导入是否执行及其文件哈希有明确记录。
