## 背景与目标

业务用餐计划表包含当前客户、地址、套餐线索、餐数、送餐安排和备注。手工逐位建档过慢，需要上传 Excel、预览逐行转换与错误、确认后批量新建客户及首单，并在页面显示成功/跳过原因。每位客户只建一个客户档案和一笔首单；早餐不导入；客户禁忌工作表本次不导入。

本计划只负责 Excel 客户/订单导入、订单“暂停”状态和导入结果。单客户排餐日历样式、逐餐份数、B596 双份不同含汤的通用排餐与核销能力，独立由 ../customer-meal-calendar-quantity/ 实施。本计划写入其已经确定的逐餐数量契约，不在导入阶段重做日历页面。

## 架构决策与跨计划依赖

1. Apache POI 5.4.0 已存在于后端依赖中，按该版本解析第三版模板；拒绝表头错位、不可信公式缓存或行列格式变化。上传预览不写库。
2. Excel 先按合并单元格和编号/电话聚成客户草稿，再规范化与校验；正式导入每个客户单独事务，允许其他合规客户成功。服务端在确认时重读同一文件并复核哈希、编号池及数据库冲突，不信任前端提交的计算结果。
3. 报告按源行号/客户编号给出新增、已存在跳过、资料错误、套餐配置错误及数据库失败；重复上传同一客户编号与电话不重复建档，编号相同但电话不同绝不合并。结果不在日志打印完整手机号或地址。
4. 新建普通订单状态为 ACTIVE(1)，E/F 命中“等通知”时为 PAUSED(4)。暂停单对余额、客户用餐统计、编号池占用、订单冲突与禁止删除均属于有效订单；对自动/人工排餐及核销无资格。恢复后才可实际排餐；退款允许按剩余餐数从暂停态发起。
5. H“等通知送餐”的 mealType=null 表示未指定餐次，不自动排餐；人工确认日期/午晚餐后才可建立明确餐次。当前建档代码会将 null 规范化为 ALL，实施时必须保留该导入语义并修正列表显示与编辑路径。
6. 日历计划的 Phase 01/02 必须先提供数量表字段、保存服务与逐份排餐契约，导入 Phase 03 才可写入未来日期和 B596；日历 Phase 03 完成后才能进行本计划最终界面验收。两个 status.yaml 各自独立。
7. 当前核销拒绝 0 单价，而本次导入金额均为 0。正式提交前须让合法 0 单价订单可逐份核销且每份扣 1 餐，不伪造金额。

## 实施约束与确认门禁

- 公共 API、数据库状态注释、编号规则及权限变更前审计调用方与现存数据；写入各 Phase 的交付记录。
- 新增/修改方法要有清晰用途、参数、返回注释；新实体字段有业务注释；每次 API/业务改动同步更新 eladmin/doc/apidoc/ 与 eladmin/doc/business/。
- 数据库预检按项目规则直接使用 Python pymysql 或其他本地工具，不通过 Docker 查询数据库。
- 不新增测试专用生产接口、构造器或开关；业务数据按客户 ID/订单 ID 定向写入，禁止无条件删除。测试只清理本次新建主键。
- 新权限采用 customerProfile:import，与单笔新增区分；权限点和菜单项需要迁移脚本与调用方确认。若未授权，接口拒绝。
- 真正执行客户数据导入前，操作人须审核预览及业务备份。若正式导入日期晚于此快照的 9 月 24 日，或 25—30 日已有送餐，必须使用更新后的业务文件重新计算，不能机械加回过期日期。实现功能不等于自动执行生产导入。
- Maven Surefire 默认跳过测试，验证时显式启用；执行前使用项目适配的 Java 8/Maven 环境。前端遵守 Vue 2.7/Element UI 现有实现。

## 风险与回滚

- 源文件改动、公式缓存、日期截止和手动编号池可能改变可导入人数；每次预览、提交均重新核对，失败行保留原因，不以当前快照数字强行导入。
- 当前快照不同客户的有效编号已无冲突。此前提出的“旧客户”显示后缀不在本次数据中触发；若新文件再次撞号，先报错并由业务改成唯一有效编号，不在导入器内生成不符合编号池规则的后缀编号。
- PAUSED(4) 若只修改排餐查询，客户会从用餐统计消失或编号被复用；Phase 02 必须审计全部 status=1 查询。
- 暂停单保存的 9 月未来日期是可见但不可执行的计划；恢复订单后仍须校验日期、餐数和已核销状态。
- 程序回滚保留新表字段及已导入数据，禁止自动批量删除；业务回退只可对本次导入生成的明确客户/订单 ID 做审计后处理，已有核销时需先走业务回退链路。
