# 客户用餐统计与排餐日历按订单展示实施计划

编制日期：2026-09-29。调研基线：`11b0e694` 及当前工作区。当前实施状态：Phase 01–03 已完成；Phase 04 已清理旧路径并同步文档，隔离 MySQL 与页面环境验收待提供。

## 已确认目标

1. `customer/mealStats` 改为一笔订单一行，早餐、午晚不再拆成两行；同一客户多笔订单分别展示。
2. 按用户指定顺序展示 24 个业务字段，另保留每笔订单的“排餐日历”操作入口。详见 [字段及接口契约](contracts.md)。
3. “特殊要求”只取 `specialRequirements`；“基本情况”取 `medicalRequirements`；“术后天数”展示 `postoperativeInfo` 原文，不计算天数。
4. 排餐日历的读取、取消、恢复、份数及含汤调整、保存、清理已生成未核销份，都严格限定当前订单。
5. 用户已确认：保留客户档案“排除日期”作为客户统一停餐；订单日历标识统一停餐且不能单独恢复。订单日历的新调整不修改客户统一停餐。

## 调研结论与影响范围

当前列表在 `CustomerProfileServiceImpl.queryMealStats` 中按客户聚合订单，再拆分早餐/午晚餐池；分页也是对组装后的行做内存切片。当前页面把整位客户的日历数据随列表返回，并只在客户首行显示入口。

真正需要改造的不是列数，而是日历写入边界：

- `saveMealScheduleAdjustments` 更新客户 `excluded_dates`，会影响同客户所有订单。
- `softDeleteMissingByCustomerIdAndDateRange` 按“客户＋月份”同步覆盖记录。
- `resolveManualAdditionOrder` 在目标订单不可用时，会选择同客户另一笔订单。
- `deleteUnverifiedCustomerMealForCalendarAdjustment` 按客户清理一个日期餐次。
- 日历 revision 是“客户排除日期＋客户当月调整”，没有隔离订单。

这些路径在新订单日历中必须替换。现有 `customer_meal_schedule_addition` 已有 `order_id/record_date/meal_type/quantity/soup_quantity` 及订单日期餐次索引；现有按订单减份的清理方法已支持目标份数为 0。可复用现有表和算法，预计不新增业务表或数据库字段。

涉及模块：客户用餐统计、客户订单查询、排餐生成与数量清理、对应前端页面和测试。客户档案统一停餐及核销/退餐是回归边界。订单建档表单中的 `MealScheduleCalendar` 是编辑 `deliveryDates` 的另一项功能，不与本次运营排餐日历混为同一个组件。

## 架构决策与跨阶段契约

### 调整数据模型

推荐复用现有订单数量覆盖表：`quantity=0` 表示当前订单在该日期餐次停餐，正整数表示目标份数；没有覆盖记录时按基础排餐规则计算。恢复默认通过移除当前订单该单元格的覆盖记录实现，不能把 `0` 当作“没有记录”。客户统一停餐始终优先，历史正数覆盖和客户统一停餐原样保留，无数据搬迁。

比较过的方案：

| 方案 | 结论 |
|---|---|
| 复用订单数量覆盖表并支持 0 | 采用。已有订单键与数量语义，日历与生成使用同一套有效目标数量。 |
| 给订单新增排除日期 JSON 或新增停餐表 | 不采用。需要额外持久化结构，并同时维护数量覆盖和停餐两套规则。 |
| 只在前端过滤订单，仍保存客户日历 | 不满足需求。取消、删除和自动改绑仍会影响其他订单。 |

### 查询与业务职责

- 用 `orderId` 作为行键和日历身份；客户共享资料可重复展示，不合并跨订单单元格。
- 列表只返回统计行；打开日历时单独加载“订单＋月份”详情，避免分页列表携带全部日历。
- 新增有实际生产职责的 `CustomerMealStatsService/Impl`，承接本页面的列表及订单日历读写，从 `CustomerProfileServiceImpl` 定向迁移相关代码，避免在客户档案 Service 中继续堆叠日历逻辑。
- 复用订单统计 SQL、`CustomerMealStatsScheduleUtil` 和按订单减份服务；不调用订单管理 HTTP 接口拼装本页面，不新增互相依赖的 Service 环。
- 列表筛选范围沿用当前页面：进行中/暂停、剩余餐数大于 0、开始日期早于所选月份下一月首日。不扩展为全部历史订单；所选月份控制可见范围和日历，不把订单累计餐数改成月度发生额。

### 接口及旧路径影响确认

详见 [contracts.md](contracts.md)。已查明仓库内旧列表及保存 API 的生产前端调用方是本页面的 `src/api/customer/profile.js`；旧保存 Service 由对应 Controller 调用。改造时列表保留 URL、更新响应粒度，日历使用带 `orderId` 的新读写 URL。

在切换前复查引用及发布调用清单；如发现新增外部调用方，先确认影响再调整方案。确认无调用方的旧客户维度保存 API、请求 DTO、自动改绑及整客户同步删除路径直接移除，不增加双协议/回退模式。前后端作为同一版本交付；实施中的阶段产物不单独切换线上页面。

## 主要风险与应对

1. **跨订单误删/自动改绑**：删除条件、请求归属和测试都锁定 orderId；同客户另一笔订单始终作为对照数据。
2. **0 份只在 UI 生效**：覆盖保存、数量计算、候选订单合并、生成目标数量和跨月分配必须一起识别 0。
3. **客户统一停餐与订单停餐混淆**：响应保留独立来源标识；统一停餐单元格禁止本页修改，保存不写客户字段。
4. **已核销或并发修改**：revision 检查、事务内重读、未核销条件更新及受影响行数校验；不能只依赖前端禁用。
5. **跨月数量变化**：累计算法读取同订单此前覆盖；保存只写当前月；修改后跨月计划按现有累计分配规则重新计算，不自动改写其他月份的记录或清理其已生成结果。
6. **历史导入餐数**：核销总数使用订单 `verifiedCount`，不要再次叠加 `importedVerifiedCount`；午晚池预算仍按原有规则扣除导入基数。
7. **回滚误恢复配送**：新版本的 0 份覆盖不能被旧版本正确处理，不能简单删除 0 份记录后回滚。

## 回滚与交付边界

- 上线前未写入新语义记录时，可成套回退前后端发布产物，数据库无结构变更。
- 已有 0 份覆盖写入后，优先前滚修复。若必须回退旧应用，先暂停日历写入和相关排餐生成，导出本次部署后受影响订单/日期/餐次及调整记录快照，制定能保留逐订单停餐语义的受控恢复方案并核对实际排餐；不得把订单停餐转换成客户统一停餐，不得直接清零删除记录。
