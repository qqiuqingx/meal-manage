# Agent 客户/订单表单草稿与页面预填实施计划

## 背景

智能客服当前只有 12 个只读业务工具和固定业务跳转。目标是在不让 Agent 直接新增客户或订单的前提下，引入第 13 个受控工具 `saveFormDraft`：LLM 负责提取资料、处理关键歧义并保存辅助草稿；客服点击固定动作后跳转到现有客户或订单页面，核对并手动提交。

设计真相源：`docs/superpowers/specs/2026-08-12-agent-form-draft-navigation-design.md`。

## 目标

- 支持 `CREATE_CUSTOMER_WITH_ORDER` 和 `CREATE_ORDER` 两种服务端草稿。
- 支持 LLM 调用 `saveFormDraft` 创建或修订草稿，并依据确定性结果回答。
- 只有 `success=true + status=READY` 才生成正式表单“去新建”动作；缺少唯一客户且无歧义的 `EDITABLE` 新增订单仅允许生成固定转换对话动作。
- 跳转后复用现有客户/首单和订单表单，尽量预填所有文本可表达字段。
- 客服必须在业务页面手动提交；现有业务 Service 仍是最终校验真相源。
- 保障草稿所有权、权限、幂等、乐观锁、一次提交和敏感数据日志边界。
- 首期不支持图片，不建设独立草稿审计模块。

## 影响范围

### `eladmin-system`

- 新增 `agent_form_draft` 表和草稿领域服务。
- 新增内部保存、登录客服领取/摘要接口。
- 扩展 Agent 工具白名单和跨服务响应快照。
- 客户与订单创建事务关联草稿一次性提交。

### `agent-service`

- `ToolRegistry` 从 12 个只读工具扩展为 12 个只读工具加 1 个 `FORM_DRAFT_WRITE` 工具。
- 新增强类型草稿输入/输出、主系统客户端、专用敏感数据护栏和副作用幂等语义。
- 从工具事实确定性生成草稿摘要和固定 UI 动作。

### `eladmin-web`

- 对话页新增草稿卡片和固定导航。
- 客户/订单页面按 `draftId` 领取、映射、自动打开现有新增表单。
- 提交时携带草稿版本；缺失字段提示、返回原会话和异常状态闭环。

### 数据库与文档

- 新增草稿 DDL。
- 更新智能客服、客户、订单业务文档和 API 文档。
- 更新 Agent OpenAPI、README 和架构基线。

## 阶段依赖

```text
Phase 01 草稿生命周期
  -> Phase 02 LLM 草稿工具
      -> Phase 03 确定性动作与会话恢复
          -> Phase 04 对话卡片与导航
              -> Phase 05 客户 + 首单
                  -> Phase 06 新增订单
                      -> Phase 07 安全与端到端
                          -> Phase 08 文档与发布
```

Phase 05 与 Phase 06 可以在 Phase 04 完成后分别开发，但合并和验收仍按顺序进行，以便先稳定共享的领取与提交协议。

## 全局实现约束

1. `saveFormDraft` 是模型可调用工具，但只能写辅助草稿，不能写正式业务表。
2. 工具输入、主系统草稿 DTO 和前端映射均使用 `schemaVersion=v1`；禁止任意 Map 穿透到业务实体。
3. `saveFormDraft` 标记为 `FORM_DRAFT_WRITE` 且不可使用 Agent 只读同参缓存；重试依赖主系统幂等键。
4. 创建使用 `owner + sessionId + clientMessageId` 幂等，修订使用 `draftId + expectedRevision` 乐观锁。
5. 草稿状态由主系统计算。普通 `EDITABLE` 可保存但不能打开正式表单；新增订单缺少唯一客户时可生成固定转换对话动作，`READY` 才能生成正式表单跳转动作。
6. URL 只携带 `draftId` 和受控来源会话标识，不携带草稿内容或任意 route/path。
7. 完整手机号、地址允许进入模型、会话原文和草稿 payload；不得进入普通日志、卡片摘要或工具追踪。
8. 每个新增/修改方法补充清晰方法注释；新增实体字段补充业务注释。
9. 所有测试数据只清理本测试创建的数据；优先使用 mock 或事务回滚测试。
10. 保留工作区已有未提交改动，不回滚、不覆盖无关文件。

## 主要风险

- **副作用重复执行**：Agent 现有缓存和 Provider 重试针对只读工具，必须为草稿写入改为主系统幂等。
- **字段漂移**：客户、订单复杂表单持续演进，需要协议字段目录和跨服务契约测试锁定。
- **敏感数据扩散**：现有 `SensitiveDataPolicy` 默认拒绝手机号和地址，只能对草稿工具的登记路径做窄范围放行。
- **状态误判**：模型文本不能决定是否可跳转；以成功工具事实的 `status` 为准。
- **历史恢复丢按钮**：草稿摘要和 UI 动作必须进入主系统消息快照，但不能保存完整 payload。
- **重复业务记录**：正式创建与草稿 `SUBMITTED` 必须同事务，且提交前锁定草稿行。
- **关联对象失效**：套餐、菜品、试餐订单在领取和提交时必须重新查询并校验。
- **金额越权**：草稿不能绕过 `customerOrder:amount:edit` 的归零或忽略逻辑。

## 发布与回滚原则

- 发布顺序：主系统 DDL/兼容接口 -> `agent-service` -> 前端 -> 白名单开关。
- 新字段和新接口保持兼容；功能关闭后不再向模型暴露 `saveFormDraft`。
- 前端可独立回滚为忽略草稿动作；客户/订单原手工新增流程保持可用。
- Agent 回滚后主系统保留草稿表和兼容响应字段，不影响只读查询。
- 未提交草稿自然过期并清空敏感 payload；不通过破坏性 SQL 回滚数据。

## 执行规则

1. 每次只读取 `status.yaml` 和 `current_phase` 对应文件。
2. 当前 Phase 的验证和完成标准全部通过后，才更新 `status.yaml`。
3. Phase 状态使用 `pending / in_progress / completed / blocked`；`current_phase` 指向首个未完成阶段。
4. 修改业务逻辑前按 Phase 指引重读对应业务文档。
5. 任何新增自动提交、图片、多客服转交或独立审计需求都必须暂停并重新评审，不在本计划内扩展。
