# 客户禁忌自动匹配与人工移除记忆

日期：2026-10-02
状态：用户于 2026-10-02 批准实施；代码和相关验证已完成，数据库迁移未执行。

## 已确认目标

- 菜品、配料、配料标签、配料二级分类、菜品标签更新后，自动重新匹配客户禁忌原文。
- 新命中对象直接保存到客户的已确认禁忌对象，不要求逐客户确认。
- 记住人工移除的对象，后续自动匹配和导入补录不再加回。
- 人工主动选回对象时解除该对象的排除记录。
- 保留完整禁忌原文、人工添加的对象和已有对象引用；D 列菜品特殊需求仍只录原文。

## 当前实现与复用边界

导入流程通过 CustomerDietDictionaryService 加载五类有效字典，CustomerDietMatchService 完成精确匹配和 HanLP 分词，CustomerProfileImportWriter 合并保存引用及原文。普通查询只读取已保存数据。订单行内编辑和客户档案编辑都能整体替换禁忌对象。

引用仅保存 type、id、name，没有人工排除元数据。订单行内编辑有前后状态审计，但客户档案编辑没有同等完整的独立删除历史，不能可靠还原全部历史人工移除。

项目为 Spring Boot 2.7.18、Java 8、fastjson2 2.0.54，已有 taskAsync 线程池。优先复用现有匹配和事务设施，不引入 MQ、新依赖或浏览器轮询。

## 触发方案比较与推荐

| 方案 | 更新时机 | 优点 | 限制 |
| --- | --- | --- | --- |
| 字典写事务提交后触发后台匹配（推荐） | 字典保存成功后开始 | 不依赖打开客户页面；不拖长字典写事务；符合自动保存目标 | 需要覆盖五类字典写入入口并处理任务并发 |
| 打开客户页面时匹配并保存 | 浏览客户时 | 入口较少 | 没有打开的客户不会更新，且读取接口产生写操作 |
| 定期重匹配 | 定时间隔到达 | 写入口改动较少 | 更新延迟由间隔决定，不符合修改后及时更新的目标 |

采用第一种。这里只承诺提交后开始后台更新，不承诺在字典保存响应返回前完成全部客户更新。用户刷新订单管理、排餐计划或客户档案后看到已保存结果；暂不做页面推送。

## 数据与合并规则

在 customer_profile 新增可空 JSON 列 dietary_restriction_exclusions，保存人工排除对象的稳定键数组，如 INGREDIENT:501。数据库 NULL 等价于空集合。该列只由服务端维护，不接受客户端直接写入，也不作为客户公开字段返回。

对象身份仍由 type:id 确定，不按名称判断是否为同一个对象。同一 ID 改名后仍受原排除记录约束；删除并重建得到新 ID 时视为新的字典对象。已有引用继续沿用现有名称快照规则，不顺带改变历史引用展示契约。

人工提交对象集合时，在客户行锁下：

1. 比较当前已保存对象与本次提交对象，差集中被移除的稳定键加入排除集合。
2. 本次提交中明确选中的稳定键从排除集合移除。
3. 对象列表与排除集合在同一事务内保存；仍沿用有效字典校验和历史引用保留规则。
4. 订单行内编辑保留 expectedValue 并发校验，并在既有审计中记录对应变化。

自动更新时：

1. 从保存的 dietary_restrictions_raw 原文块进行现有规则匹配。
2. 用当前客户排除集合过滤匹配结果。
3. 按 type:id 去重并追加到已有禁忌对象；不删除已有对象。
4. 原文、对象和排除集合均无变化时不更新记录时间。

禁忌原文不存在时不推断新对象。字典停用或删除不会自动清除已有引用，沿用当前保留历史引用的约定。原文命中标签只关联标签对象，不展开成标签下全部菜品或配料；本次不修改排餐过滤、allergyTags 或 excludedDishIds。

## 业务入口与任务流程

- 菜品、配料、两类标签及分类的新增、改名、启停、删除等字典变化，在已有写事务中发布统一字典变更事件。
- 仅绑定或解绑标签关系，且字典自身没有变化时，不需要重匹配；新增标签自身仍会触发。
- 客户模块在字典事务成功提交后响应事件，复用 taskAsync 开始后台批处理；事务回滚不触发客户更新。
- 同一进程只运行一轮重匹配，连续事件合并；运行中再次变化时，在本轮结束后读取最新字典再运行，避免丢失变更。
- 每轮建立一份字典与分词器快照，按客户主键游标批量读取非空禁忌原文，避免每个客户重建字典或一次加载全部客户。
- 保存单个客户时独立事务，重新锁定并读取当前原文、引用、排除集合，再合并；自动任务只锁客户，不再锁订单。订单编辑/导入沿用订单先锁、客户后锁的顺序。
- 单客户失败记录客户主键并继续其他客户；后台操作人标识不依赖异步线程里的登录上下文。
- 应用就绪后自动请求一轮匹配，覆盖已有原文，也恢复应用停止期间或退出前未完成的工作。再次执行必须幂等。
- 不增加普通列表读取时的隐式写操作，不自动启动或修改生产环境。

## 导入与页面契约

完整导入和仅第二页补录共用匹配核心，并尊重人工排除记录。预览应区分“未匹配”与“已人工排除”；已排除对象不列入本次自动录入列表，同名多候选中只有未排除对象可录入。确认写入时再次读取最新排除集合，避免预览后发生的人工删除被加回。

允许在导入预览匹配状态中新增 EXCLUDED，含义为该词项的字典候选全部被人工排除；现有确认请求参数不变。部分候选被排除时，UNIQUE/MULTI 按实际将录入的对象数量展示，并说明人工排除情况。前端必须支持零个 selectedItems 的 EXCLUDED 状态。

订单行内编辑每次进入编辑时重新获取有效字典，仍复用正在进行的请求，去掉永久一次加载缓存；新增配料后无需关闭整个订单页面才能选择它。人工移除和重新选择沿用现有多选操作，不增加用户必经确认步骤。

## 初次上线边界

人工排除记忆从功能上线后开始可靠维护。历史未完整记录的人工删除不根据“原文匹配结果减去当前对象”猜测，因为这也可能表示此前字典缺项。首次启动自动重匹配会为已有原文补齐当前可匹配对象；若有历史人工移除，需要在上线后重新移除一次，由新规则记录。不得宣称已完整保护历史未记录的人工删除。

新增列需要部署前执行对应限定结构迁移；本次设计与计划不执行数据库脚本。未迁移的环境不通过静默回退掩盖缺失列。回退代码时保留已生成的人工排除记录和原文，不清空客户数据；旧代码不再提供自动匹配与人工排除保护。

## 验证与完成条件

- 已有原文“不吃秋葵”，新增秋葵后自动保存，用户无需确认。
- 人工移除秋葵后，字典再次变化、任务重试、应用重启和重复导入都不加回；人工选回后可以正常保留。
- 人工新增对象、已有停用或删除引用、原文标点换行、D 列仅原文行为均保留。
- 两种人工编辑入口都记录排除；原文为空、同名跨类型对象、部分及全部候选排除正确。
- 字典事务回滚不更新客户；连续事件、运行中变更、单客户失败以及人工编辑与后台写入竞争均有测试。
- 后端编译受影响模块并执行匹配、导入、客户编辑、订单编辑和任务相关测试；前端执行必要 lint 和相关 Vue 单元测试。
- 不用业务数据库做清表式验证，不自动部署；保留工作区原有未提交修改，仅用户要求时提交。
