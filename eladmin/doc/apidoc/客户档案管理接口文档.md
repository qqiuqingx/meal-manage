## 1. 概述

客户档案管理模块提供客户基础档案、地址、过敏食物、医嘱要求、孕周等信息的管理能力。
首单（第一笔订单）随客户创建时自动生成。

### 1.1 模块结构

- **后端路径**: `/api/customerProfile` (客户档案), `/api/customerPackageCategory` (套餐分类)
- **前端路径**: `customer/profile/index` (客户档案页面), `customer/packageCategory/index` (套餐分类页面)

### 1.2 权限定义

| 权限标识 | 说明 |
|---------|------|
| `customerProfile:list` | 客户档案列表查询 |
| `customerProfile:add` | 新增客户档案 |
| `customerProfile:edit` | 编辑客户档案 |
| `customerProfile:del` | 删除客户档案(仅内部管理工具) |
| `customerProfile:import` | 客户与首单 Excel 批量导入（预览与确认提交）|
| `customerPackageCategory:list` | 套餐分类列表 |
| `customerPackageCategory:add` | 新增套餐分类 |
| `customerPackageCategory:edit` | 编辑套餐分类 |
| `customerPackageCategory:del` | 删除套餐分类 |
| `customerPackageCategory:status` | 启用/停用套餐分类 |
| `customerOrder:amount:view` | 查看新增客户首单中的金额信息 |
| `customerOrder:amount:edit` | 录入新增客户首单中的金额信息 |

首单金额权限补充说明：

- 无 `customerOrder:amount:view` 时，新增客户页不展示首单金额字段。
- 无 `customerOrder:amount:edit` 时，`orderInfo` 中金额字段允许不传，后端统一按 `0` 创建首单。

### 2.3 新增套餐分类

**请求**

```
POST /api/customerPackageCategory
Content-Type: application/json

{
  "categoryName": "两荤一素",
  "categoryCode": "PACKAGE_A_1",
  "parentId": 1,
  "level": 2,
  "sort": 1,
  "enabled": true
}
```

**字段说明**

| 字段 | 类型 | 必填 | 说明 |
|-----|------|------|------|
| categoryName | string | 是 | 分类名称 |
| categoryCode | string | 是 | 分类编码(全局唯一) |
| parentId | long | 否 | 父级ID(顶级为NULL) |
| level | int | 是 | 层级(1=父级,2=子级) |
| sort | int | 是 | 排序 |
| enabled | boolean | 是 | 是否启用 |
| codePrefix | string | 否 | 编号前缀(仅父级使用,单个大写字母) |

### 2.4 编辑套餐分类

**请求**

```
PUT /api/customerPackageCategory
Content-Type: application/json

{
  "id": 3,
  "categoryName": "两荤一素(升级版)",
  "categoryCode": "PACKAGE_A_1",
  "parentId": 1,
  "level": 2,
  "sort": 1,
  "enabled": true
}
```

### 2.5 启用/停用套餐分类

**请求**

```
PUT /api/customerPackageCategory/{id}/status
Content-Type: application/json

{
  "enabled": false
}
```

### 2.6 删除套餐分类

**请求**

```
DELETE /api/customerPackageCategory/{id}
```

**说明**

- 仅在无客户引用且无子节点时允许删除
- 其他场景仅允许停用

### 3.2.1 饮食对象字段

- `dishRequirements`：想吃对象列表。
- `dietaryRestrictions`：禁忌对象列表。
- 每个引用包含 `type`、`id`、`name`；对象身份由类型和ID确定，名称由服务端字典填充为快照。
- 支持 `DISH`、`INGREDIENT`、`INGREDIENT_TAG`、`INGREDIENT_CATEGORY`（仅二级分类）、`DISH_TAG`。
- 编辑请求未传或传 `null` 时保留原值，传 `[]` 清空，传非空数组时整体替换并校验类型/ID。已有停用或删除引用可原样保留；新选项只能选择当前有效字典项。
- `dishRequirementsRaw`、`dietaryRestrictionsRaw` 是只读来源原文块数组，仅由导入写入；客户详情返回，普通客户编辑不修改。
- `postoperativeInfo` 是术后情况原文，例如“5天”“4个月”；不会解析日期或自动递增。原 `productionDate`/`production_date` 字段已替换，不再返回。
- 部署前按客户主键备份旧 `production_date`，再执行 `eladmin/sql/20260928_customer_diet_items.sql`；旧日期原值作为字符串保留供人工核对，不推算术后天数。

### 3.2.2 查询客户饮食对象选项

供客户维护表单、订单行内编辑和导入预览使用；只返回当前有效菜品、配料、配料标签、配料二级分类和菜品标签。

```http
GET /api/customerProfile/diet-options
```

**权限**：`customerProfile:list`、`customerProfile:add`、`customerProfile:edit`、`customerProfile:import` 或 `customerOrder:edit`。

每个选项返回 `type`、`id`、`name`；配料二级分类另有 `categoryPath`。标签字典没有停用字段，现存标签均返回。该接口只读，不扩大字典写权限。

### 3.3 解析客户建档话术

**请求**

```http
POST /api/customerProfile/intake/parse
Content-Type: application/json
```

**请求体**

```json
{
  "text": "联系人：测试客户甲\n电话：13800138001\n地址：成都市高新区示例路88号1栋1单元\n套餐：营养餐\n来源：小红书\n配送日期：默认等通知配送\n菜品配置：2主1副1素0汤\n合计：30餐不含汤"
}
```

**解析补充**

- `配送日期` 字段支持混合写法，例如 `配送日期：6 月 1 日、晚餐开始、默认每天配送晚餐`。
- 上述写法会解析为：`orderInfo.startDate = 2026-06-01`，`orderInfo.scheduleMode = DAILY`，`orderInfo.mealType = DINNER`，`orderInfo.startMealType = DINNER`。
- `每天送`、`每天配送`、`每日送`、`每日配送` 均识别为 `DAILY`。
- `来源` 会忽略括号或方括号内的候选提示，按括号外真实选择匹配渠道。例如 `来源：（小红书or抖音or推荐）抖音个人搜索` 识别为 `抖音`；`来源：（小红书·抖音·推荐）` 默认 `其他`。
- `过敏食物` 整段为 `无`、`没有`、`无过敏` 等空值表达时回填空数组；`不能吃的` 整段为 `无`、`没有`、`暂无` 等空值表达时不写入 `specialRequirements`。
- `套餐/父套餐` 优先按系统父套餐名称或编码匹配；未填写或未匹配成功时，会从 `餐别` 按分隔符拆出的完整片段中兜底匹配已启用父套餐名称或编码，例如 `餐别：小月子餐、两荤一素一汤` 可匹配父套餐 `小月子餐`，不会误匹配内部的 `月子餐`。
- `餐数/合计` 未填写时，可从 `菜品配置` 中的 `N餐` 提取午晚餐数，例如 `菜品配置：7 餐、1主0副1素1汤` 会解析 `orderInfo.lunchDinnerCount = 7`。
- 父套餐名称包含 `试餐` 时，话术解析按试餐简化建档规则生成草稿：联系人可不填，系统自动补 `试餐客户` + 手机号后 4 位；餐数默认 `breakfastCount=0`、`lunchDinnerCount=1`；菜品配置默认 0；米饭类型默认 `白米饭`；手机号、地址和套餐仍必须可解析。


**试餐简化建档请求示例**

当 `orderInfo.parentPackageId` 对应的父套餐名称包含 `试餐` 时，可仅提交手机号和父套餐：

```json
{
  "phone": "13800000000",
  "orderInfo": {
    "parentPackageId": 1
  }
}
```

**字段说明**

| 字段 | 类型 | 必填 | 说明 |
|-----|------|------|------|
| customerCode | string | 否 | 手动客户编号；不传时后端自动分配 |
| customerName | string | 普通套餐是，试餐套餐否 | 客户姓名；试餐简化建档未传时后端自动补 `试餐客户` + 手机号后4位 |
| phone | string | 是 | 手机号(中国大陆手机号格式) |
| deliveryPhoneInfo | string | 否 | 地址列配送电话原文，可包含多条；与 `phone` 分开保存 |
| gestationalWeek | int | 否 | 孕周(正整数) |
| allergyTags | array | 否 | 过敏食物标签(JSON数组) |
| excludedDishIds | array | 否 | 排除菜品ID列表(JSON数组) |
| medicalRequirements | string | 否 | 医嘱要求 |
| specialRequirements | string | 否 | 普通客户特殊要求，与结构化饮食对象分别维护 |
| dishRequirements | array | 否 | 客户想吃的结构化对象，数组元素含 `type`、`id`、`name`；`name` 会由服务端按字典覆盖 |
| dietaryRestrictions | array | 否 | 客户禁忌的结构化对象，字段规则同 `dishRequirements` |
| postoperativeInfo | string | 否 | 术后情况原文，最大 255 字符；不按日期解析 |
| addresses | array | 是 | 地址列表；试餐简化建档同样要求至少一个地址非空 |
| addresses[].addressType | string | 是 | 地址类型(DEFAULT/WORKDAY/WEEKEND) |
| addresses[].addressDetail | string | 是 | 详细地址(至少一个非空) |
| addresses[].contactName | string | 否 | 联系人姓名 |
| addresses[].contactPhone | string | 否 | 联系人电话 |
| orderInfo | object | 是 | 首单信息 |
| orderInfo.parentPackageId | long | 是 | 父套餐ID |
| orderInfo.childPackageId | long | 否 | 子套餐ID（前端空字符串会转换为null） |
| orderInfo.breakfastCount | int | 否 | 早餐数；试餐简化建档默认 `0` |
| orderInfo.lunchDinnerCount | int | 否 | 午餐+晚餐数；试餐简化建档默认 `1` |
| orderInfo.mainDishCount | int | 否 | 每餐主菜/荤菜数量（null默认0，负数报错） |
| orderInfo.sideDishCount | int | 否 | 每餐副菜数量（null默认0，负数报错） |
| orderInfo.vegCount | int | 否 | 每餐素菜数量（null默认0，负数报错） |
| orderInfo.riceCount | int | 否 | 每餐米饭数量（null默认1，负数或超过10报错） |
| orderInfo.riceType | string | 否 | 米饭类型；普通套餐默认 `普通杂粮米饭`，试餐简化建档默认 `白米饭` |
| orderInfo.soupCount | int | 否 | 每餐汤数量（null默认0，负数报错） |
| orderInfo.startDate | string | 普通套餐是，试餐套餐否 | 签约开始日期(YYYY-MM-DD)；试餐简化建档默认服务端当天 |
| orderInfo.startMealType | string | 否 | 首单开始餐次：`BREAKFAST`/`LUNCH`/`DINNER`；试餐简化建档默认 `LUNCH` |
| orderInfo.endDate | string | 否 | 签约结束日期(YYYY-MM-DD) |

**校验规则**

- `customerCode` 可不传，不传时后端自动生成；传入时必须以父套餐编号池前缀开头，前缀后为纯数字，数字值在编号池范围内且未被占用，数字部分不限制固定位数
- `DEFAULT`、`WORKDAY`、`WEEKEND` 三个地址槽位中至少有一个地址明细非空，试餐简化建档同样适用
- 普通套餐要求早餐数与午餐+晚餐数不能同时为空；试餐简化建档默认补 `breakfastCount=0`、`lunchDinnerCount=1`
- `totalCount` 由后端根据 `breakfastCount + lunchDinnerCount` 自动计算
- `endDate >= startDate`
- 首单份数总和必须 > 0
- `startMealType` 必须与 `mealType` 兼容：`ALL → BREAKFAST/LUNCH/DINNER`，`LUNCH_DINNER → LUNCH/DINNER`，`LUNCH → LUNCH`，`DINNER → DINNER`
- `mainDishCount`、`sideDishCount`、`vegCount`、`soupCount` 可不传（默认0），传入时需为0-10之间的整数
- `riceCount` 可不传，默认 1；普通套餐 `riceType` 可不传时默认 `普通杂粮米饭`，试餐简化建档默认 `白米饭`
- `childPackageId` 为空时表示无子套餐，前端传递空字符串会被自动转换为null

**试餐简化建档补充说明**

- 试餐判定口径：父套餐名称包含 `试餐`
- 试餐简化建档时，后端会自动补齐客户姓名、餐数、金额、开始日期、开始餐次、餐次类型和米饭类型等首单默认值
- 试餐简化建档时仅放宽姓名必填和开始日期等首单字段，地址必填、手机号格式、父套餐启用状态、编号池规则仍保持不变

**创建后行为**

- 未传 `customerCode` 时自动生成客户编号（格式：`{父套餐编号池前缀}{序号}`，如 A001、A11001）
- 自动在 `customer_order` 表创建首笔订单，状态为"进行中"

### 3.7 批量删除客户档案

**请求**

```
DELETE /api/customerProfile
Content-Type: application/json
```

**请求体**

```json
[1, 2, 3]
```

> `Set<Long>` 客户ID集合，支持单个或批量。

**响应（成功）**

```

```

**响应（失败 - 存在有效订单）**

```
HTTP 400 Bad Request

{

  "message": "以下客户存在进行中或暂停的订单，无法删除：张三、李四",
  "data": null
}
```

**校验规则**

- 删除前检查 `customer_order` 表中是否存在 `status=1`（进行中）的订单
- 若任一客户存在进行中或暂停订单，拒绝整个批量删除请求，并返回被拦截的客户姓名列表

- 同步删除：`customer_profile_address`（地址记录）
- 同步删除：`customer_profile_package`（签约记录）
- **不删除**：`customer_order`（订单记录独立管理）

**权限**

- `customerProfile:del`

**「客户禁忌」第二工作表规则**

| 列 | 含义 | 处理规则 |
|---|---|---|
| A / B | 旧编号 / 新编号 | B 非空时只按 B 关联月份表有效编号，否则按 A；B 无匹配不回退 A |
| C | 不导入 | 不读取该列内容 |
| D | 菜品特殊要求 | 仅原文写入 `dishRequirementsRaw`，保留标点、空白和换行，不拆词、不匹配字典、不自动生成结构化对象 |
| E | 医嘱 / 基本情况描述 | 原文写入现有 `medicalRequirements`，不参加字典匹配 |
| F | 客户禁忌 | 固定表示不能吃；保存完整原文并尝试五类字典精确匹配 |
| G | 成交时间 | 新订单的 `dealTime`，其日期同时作为 `startDate`；月日按月份表年份补齐，纯日期时分秒为 00:00:00，空值确认时填入当前时间 |
| H | 术后 | 原文写入 `postoperativeInfo`，不转换成日期 |

- 第二工作表缺失时保留月份表原导入能力。表头结构必须符合固定列契约；标题行和说明行不会当作客户记录。
- D 列仅保存完整原文，完整月份导入和仅第二页导入均不生成 D 列匹配项或新增想吃对象；补录保留已有客户的想吃对象，重复原文块按完整内容去重。
- F 列先整段精确匹配，再按常见分隔符拆词；只去除有限的表达前缀，不按句意改变禁忌方向。唯一候选自动选择；多候选完整返回类型、ID、名称和必要的分类路径；无匹配为非阻塞提示。
- F 列未整词命中的词项通过 HanLP 1.x Portable 分词，再按词语与有效字典名称全等查找对象。内置基础词库和本次导入独立的领域词典用于识别 `芒果菠萝` 等连写名称；未识别片段作为 `UNMATCHED` 保留，完整名称优先匹配，禁忌方向与同名对象全部录入规则不变。
- 页面将医嘱、菜品特殊需求原文与禁忌匹配显示为紧凑摘要；「查看明细」提供完整原文、成交时间、术后信息和禁忌逐词匹配结果的滚动浮层，不改变预览响应字段或确认参数。
- `sourceKey` 用于确认时定位歧义词项。客户端回传 `dietSelections` 仅允许 `SELECT` 某个返回的候选，或用 `SKIP` 明确跳过。未知/重复来源键、伪造候选、遗漏歧义、字典摘要变化都会在任何客户写入前拒绝。
- 页面有未确认歧义时会显示阻塞提示和「待确认匹配」筛选，提交按钮保持禁用；逐项选择候选或明确跳过后才可提交。其他客户的资料错误会在逐位结果中跳过，不单独阻止本次提交。
- 图片及 `DISPIMG` 公式跳过，不做 OCR；其他公式读取缓存值，缓存不可用时提示。整段 D/F 原文块始终单独保留，重复导入按完整内容去重。
- 同一客户多行医嘱/术后内容相同才合并；冲突需核对。非空成交时间解析失败或多行成交时间不同会阻止该客户提交。空值在确认请求开始时统一取同一时间。已有客户补录不改历史订单成交时间。
- 同编号、同手机号的已有客户进入补录：只更新空缺医嘱/术后字段、去重合并结构化引用与原文块；锁行后复核身份，不修改地址、餐数或订单。相同资料重传为无变化，编号或手机号冲突则跳过。
- 即使 D/F 为空，只要 E/G/H 任一列有内容，该来源行仍进入客户预览。无法关联月份表客户的第二工作表行在预览中单独提示，不据此新建客户。

问题分类（`issues[].category`）：

| 分类 | 说明 |
|-----|------|
| `WORKBOOK_ERROR` | 工作簿级错误（表头/月份/日期餐次结构不符）|
| `PROFILE_ERROR` | 客户资料错误（电话、编号、地址、餐数、送餐描述）|
| `PACKAGE_CONFIG_ERROR` | 编号无法匹配唯一的启用父套餐编号池 |
| `ALREADY_EXISTS` | 编号已存在，按幂等跳过 |
| `SKIPPED` | 业务规则跳过（如纯早餐行）|
| `DATABASE_ERROR` | 写库失败（确认提交阶段）|
| `WARNING` | 非阻塞提示 |

**校验规则**

- 读取名称形如 `NN年N月` 的月份工作表；可选读取名称为 `客户禁忌` 的第二工作表，WPS 保留页忽略。缺少第二工作表时仍可按原月份工作表流程预览和导入。
- 文件列按标题行与 2/3 行日历表头联合定位，拒绝表头错位与行列结构变化。
- 日格合计、餐数、剩余餐数以及「合计餐数」公式值逐行交叉核对；「合计餐数」为空时按 0 读取且不因空值报错，有实际取值但公式缓存不可信时报错。
- 编号按启用父套餐的编号池归属：以编号池前缀开头、数字部分落在池区间内，且在启用父套餐中唯一命中；套餐名称不参与匹配，编号池配置以套餐管理为准。无法唯一命中时报 `PACKAGE_CONFIG_ERROR`。
- 同编号出现不同手机号或地址时按客户编号冲突报错，不合并。
- 「剩余餐数」为 0 不构成错误或警告；待导入餐数也为 0 时仍可预览并确认建档。
- 同一餐次份数为 2 时，只有「特殊要求」给出与有效编号一致的「编号-2含汤」且「含汤」列为 `不含汤` 才认定第二份含汤；无法确定的多份描述逐行报错。
- 电话列写入客户手机号；地址列中的所有配送电话标签值写入客户主档 `deliveryPhoneInfo`，即使与电话列不同。地址槽位的 `contactPhone` 取首条可用配送电话，缺失时回退客户手机号。预览只返回脱敏的单值地址联系电话，不返回完整配送电话信息。
- 日志不打印完整手机号与地址。

**权限**

- `customerProfile:import`

### 3.9 客户与首单 Excel 批量导入确认提交

该接口只有在操作人核对预览、实际导入日期、套餐编号池配置并完成业务备份后才调用。服务端会重新解析同一工作簿并逐客户写入，预览中有阻塞错误的客户跳过，单个客户事务失败不影响其他客户。

若预览使用 `dietOnly=true`，确认请求必须同样传 `dietOnly=true`。服务端只按第二页编号补录数据库已有客户；编号不存在则跳过，不会新建客户、地址、订单或未来逐餐计划。确认时仍复核文件摘要、饮食字典摘要，并锁定客户行复核编号。多候选对象由服务端全部自动录入，无需提交选择数组。

**请求**

```
POST /api/customerProfile/import/confirm
Content-Type: multipart/form-data

file=<与预览完全相同的工作簿>
fileHash=429f68f40e65fe88b72c8fb1add699feb7054a1e9a5ef409ee97d41416fa09cf
dictionaryHash=<预览返回的饮食字典摘要>
importDate=2026-09-24
```

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|-----|------|------|------|
| file | file | 是 | 预览所用的 `.xlsx` 文件，不超过 40MB |
| fileHash | string | 是 | `preview` 返回的 SHA-256；与上传文件不一致时整次请求拒绝 |
| dictionaryHash | string | 含「客户禁忌」工作表时是 | 预览返回的饮食字典快照 SHA-256；候选字典发生变化时整次请求拒绝 |
| importDate | string | 否 | 预览时使用的导入日期(YYYY-MM-DD)，应原样传回；不传取当天 |
| orderStateHash | string | 续导是 | 预览返回的订单状态摘要，完整模式应原样回传；订单、核销或日期边界变化时拒绝并重新预览，第二页模式不校验 |
| dietOnly | boolean | 否 | 与预览时相同；`true` 仅补录「客户禁忌」页，不创建客户或订单 |

| 结果状态 | 说明 |
|---------|------|
| `CREATED` | 客户档案与地址已创建；待导入餐数大于 0 时，同一客户事务还会创建零金额首单、历史逐餐数量和未来逐餐数量 |
| `UPDATED` | 已有客户共享资料补录、已有档案首单创建或原订单月度续导/旧月补录；续导返回目标 `orderId`，不重复创建地址 |
| `ALREADY_EXISTS` | 相同资料已存在且无新增内容，或身份冲突而跳过 |
| `SKIPPED` | 预览校验不通过或按业务规则跳过；`message` 列出原因 |

来源午晚餐购买数为 0 时只建客户档案和地址，`CREATED` 结果的 `orderId` 为 `null`。G 列成交时间仅在实际创建订单时写入；空值使用确认请求开始时捕获的统一时间。已有客户完整导入按父套餐、原成单日期和导入来源唯一定位订单；不能唯一定位时预览报错，续导不改历史成单时间或开始日期。新建首单 `startDate` 取实际 `dealTime` 的日期（G 列为空时取统一确认时间的日期），并保存实际 `import_date` 与来源 `import_month`（月首日）；有效排餐开始日为 `max(startDate, import_date + 1日)`；早餐数、金额和单价为 `0`，已核销数以 `importedVerifiedCount` 为初值，剩余数等于来源剩余餐数加未来日格份数。导入前历史已核销保留订单汇总；`historicalMealCells` 按日期、餐次、份数保存到数量日历表，不生成逐餐核销日志或排餐结果。部署本调整前须执行 `eladmin/sql/20261001_customer_order_import_date.sql`，既有订单不批量自动回填；月度续导还须先执行 `eladmin/sql/20261001_customer_order_import_month.sql`；数量日历只读展示这些历史记录；未来餐数计算不变，历史期间和缺格不占用未来排餐余额。无剩余且未暂停的订单创建为已完成。E/F 或送餐描述含「等通知」时订单状态为暂停，送餐描述命中时餐次留空。未来午晚餐格写入日历数量契约，暂停订单保存计划但不能排餐或核销。重复提交不会重复创建已存在客户。异常清单不包含完整手机号或地址。

文件/字典/订单状态摘要不匹配、导入日期与预览不同、工作簿结构不合格或缺少必要摘要时整次请求拒绝，不创建或更新客户订单。工作簿本身不落临时文件，日志不记录手机号、地址或原始文件内容。

#### 月度续导规则

完整模式一次处理预览展示的来源月份；同客户、同父套餐和原成单日期的导入订单必须唯一。新月份或同月份更新时，购买数T取该表午晚餐I列之和，可用餐数R=J列之和+该表导入日之后的未来份数（J20+未来5=25）；来源累计消费V表=T−R表；表期内系统核销S内已包含在其中，历史基数H=V表−S内。表期外真实消费S外不返还，最终余额R表−S外，无额外后续消费时J20+未来5=25。购买数、剩余数、采用年月以最大来源年月为准；旧月只补数量，不回退上述字段和日期边界；同月同内容不叠加。

旧导入订单已唯一定位但 `import_month` 为空时，优先从有效导入日格推断来源月份；日格也为空时允许导入历史文件，预览 `currentImportMonth=null`、`importAction=UPDATE_MONTH`，按现有校验计算餐数与余额。首次确认保存该文件的来源月份、采用日期边界及日格，建立月份基线；空日历文件同样保存月份。后续仍按最大来源年月更新餐数，较早月份只补数量；不需要人工回填或额外确认流程，不用订单创建日期代替来源月份，普通手工订单仍不能自动续导。

每位客户独立事务，锁序为订单→客户→排餐。人工来源、已核销数量/含汤冲突、负历史基数或已完成订单出现正余额时，该客户标错或回滚，不删除核销日志或自动恢复状态；其他合法客户可继续。暂停、取消、已退餐状态与单价、金额字段不由续导自动修改。只清理本订单、本来源月份的超额未核销结果；其他月份保留，已经进入历史的导入格转为只读并保留真实进度。仅第二页模式仍不创建或续导订单。

### 3.10 客户用餐统计订单列表

列表在数据库分页前按所属父套餐的字母前缀 `parent_package.prefix` 升序排列（A、B、C……），未配置前缀或未关联套餐的订单排在最后；同一前缀内保留客户编号、开始日期、成交时间和订单 ID 升序，空编号和空日期排在各自字段的最后。分页追加及筛选使用相同顺序，无需新增排序参数。

```http
GET /api/customerProfile/mealStats?page=1&size=20&customerCode=A068&customerName=张三&phone=138&statsMonth=2026-10
```

权限：`customerProfile:list`

筛选参数沿用客户编号、客户姓名、手机号和统计月份。统计月份格式为 `yyyy-MM`；为空时不限制订单开始月份。响应继续使用 `PageResult`，但 `content` 和 `totalElements` 均按订单统计：同一客户的不同订单分别返回，即使一笔订单同时含早餐和午晚餐也只占一行。后端先对订单分页，再批量补充当前页客户共享资料、地址、已排餐统计和今日成功未核销数量；不返回金额。

每行按以下 24 个业务字段顺序返回，随后是排餐日历操作入口：

`phone`、`addressText`、`customerCode`、`customerName`、`specialRequirements`、`scheduleModeText`、`mealTypeText`、`specification`、`soupCount`、`breakfastCount`、`lunchDinnerCount`、`totalCount`、`verifiedCount`、`scheduledCount`、`remainingCount`、`estimatedRemainingCount`、`statusLabel`、`medicalRequirements`、`dealTime`、`postoperativeInfo`、`dishRequirements/dishRequirementsRaw`、`allergyTags`、`dietaryRestrictions/dietaryRestrictionsRaw`、`customMenuImage`。

- 普通剩余订单：`status IN (1,4)` 且 `remaining_count > 0`；指定月份时要求 `start_date < 次月首日`，不按结束日期过滤。另返回所选月份存在有效历史导入数量的订单，即来源为“客户用餐计划表历史导入”、未删除且日期在 `[月初, 次月首日)` 的数量记录；这类订单不限制状态、余额或开始日期。未指定月份时历史记录不按月限制。
- 因此 10 月 1 日导入 9 月数据，即使订单开始日取历史成单日期、状态已完成或剩余为 0，也能在 9 月列表找到并打开只读历史日历。客户编号、姓名、手机号条件同时作用于剩余与历史两种路径；分页和总数仍按唯一订单计算。
- `verifiedCount` 取订单累计核销数，已含导入基数；`scheduledCount` 为全部有效排餐结果行，含成功和失败；`estimatedRemainingCount = max(remainingCount - 今日成功且未核销份数, 0)`，今日由服务端按业务日期计算。
- `specialRequirements` 只取客户档案特殊要求，`medicalRequirements` 单独返回医嘱，`postoperativeInfo` 返回原文。客户共享字段来自当前档案，订单字段来自当前订单。
- 餐数、核销、已排餐和剩余是当前订单累计值，不是所选月份内的增量或历史快照。

```json
}
```

`overrides` 必填并表示当前订单当月完整可编辑覆盖；历史导入数量不传，服务端自动保留，提交已有历史日期餐次的修改返回 400。空数组表示恢复本订单本月全部可编辑覆盖为默认，`null` 不表示清空。`orderId` 只从 URL 读取。日期、餐次、数量、含汤范围、订单有效期和开始餐次均由服务端校验；目标数量 0 表示当前订单该日餐次停餐，负数非法。零份的 `soupQuantity` 归一化为 `null`。

客户统一停餐格只能原样保留现有覆盖，不能在订单日历新增、修改或移除。保存不会更新 `customer_profile.excluded_dates`，所有覆盖同步删除均限定当前 `orderId` 和月份。已核销份数是目标下限；减少时仅删除当前订单超出目标的未核销份，并同步清理菜品、换菜关系和排餐汇总。增加或恢复计划只保存数量计划，不自动生成菜品。

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "orderId": 902,
    "statsMonth": "2026-10",
    "revision": "保存后的修订标记",
    "deletedUnverifiedPlanCount": 1
  }
}
```

修订标记已变化，或清理时排餐被并发核销，返回 `409 Conflict`，整次保存回滚。非法覆盖、越月、重复日期餐次、订单状态不可编辑或超出可用餐数返回 `400 Bad Request`；订单或客户档案不存在返回 `404 Not Found`。

### 5.3 create/edit 两路径分离

| 路径 | 传入 orderInfo | 修改客户基本资料 | 修改地址 |
|------|---------------|---------------|---------|
| POST（创建） | ✅ 必填 | ✅ | ✅ |
| PUT（编辑） | ❌ | ✅ | ✅ |


**表期之外真实消费的保护**：J列加未来份数是最大来源月份的余额基数；表能覆盖的日期为来源月末与采用导入日的较早者。该覆盖期内的系统真实核销抵扣历史基数，不再扣余额；表期之外已发生的真实核销仍保留其扣减，不能因重传过去月份返还。没有额外后续核销时，J20+未来5仍为25。预览的 `postSnapshotVerifiedCount` 说明保留的表期后消费，`afterRemainingCount` 显示最终可用余额。

同月已经完整结束后再次上传，不推进原订单已经开始的后续履约区间。日历和排餐将当前区间之前已使用或成功预占的份数排除，不重复分配；归档数量只读并保留真实进度。核销接口拒绝对已由导入历史期间对账的记录再次扣餐，但不伪造核销状态或生成历史日志。

### 客户禁忌自动更新补充契约

- 字典变化成功提交后后台自动匹配并保存客户原有禁忌原文，应用就绪时执行一轮；普通列表/详情读取保持只读，客户端无需新增确认请求。完成后刷新页面获取结果。
- 客户编辑和订单行内编辑传入对象数组时，移除的原有 `type:id` 会被内部记录，自动匹配与重新导入跳过；明确重新选择当前有效对象解除该键排除。内部 `dietary_restriction_exclusions` 不公开返回，也不允许客户端直接写入。
- 导入预览 `dietMatches[].status` 增加 `EXCLUDED`，表示本词项所有候选均被人工排除，`selectedItems=[]`，不阻止导入。`excludedItemCount` 返回被排除候选数；部分排除时 `UNIQUE/MULTI` 按实际允许录入数量决定，`message` 说明排除情况，`candidates` 仍保留完整匹配候选供追踪。
- 完整导入和仅第二页模式均尊重人工排除；确认写入在客户行锁下再次过滤最新排除结果。确认请求参数、权限和 D 列仅保存原文约定不变。
- 已有对象和名称快照不自动清除；标签引用不展开为具体菜品/配料，也不改变排餐过滤。历史未完整记录的人工删除无法自动还原排除，记录从上线后建立。
- 部署前执行 [新增内部排除字段](../../sql/20261002_customer_diet_restriction_exclusions.sql)。后台新增保存使用 `system:diet-rematch` 操作人标识，无变化不更新客户时间。
