# 客户订单管理 API 文档

> 文档版本: 1.10
> 更新日期: 2026-09-30

## 1. 概述

客户订单管理模块提供订单的创建、编辑、删除、查询等能力，订单关联客户档案。

### 1.1 模块结构

- **后端路径**: `/api/customer/order`
- **前端路径**: `customer/order/index`

### 1.2 权限定义

| 权限标识 | 说明 |
|---------|------|
| `customerOrder:list` | 订单列表查询 |
| `customerOrder:add` | 新增订单 |
| `customerOrder:edit` | 编辑订单 |
| `customerOrder:del` | 删除订单 |
| `customerOrder:amount:view` | 查看订单金额、单价、核销金额、餐费余额 |
| `customerOrder:amount:edit` | 录入或修改订单金额、单价等金额字段 |

金额权限补充说明：

- 无 `customerOrder:amount:view` 时，列表、详情、按客户查询订单、试餐关联订单接口中的金额字段统一返回 `null`。
- 无 `customerOrder:amount:edit` 时，新增订单金额字段允许不传，后端统一补 `0`。
- 无 `customerOrder:amount:edit` 时，编辑订单金额字段允许不传，后端保留数据库原值。

### 1.3 订单状态

| 状态值 | 说明 |
|-------|------|
| 0 | 已取消 |
| 1 | 进行中 |
| 2 | 已完成 |
| 3 | 已退餐 |
| 4 | 暂停 |

订单列表和详情响应增加 `pauseEffectiveDate`（`yyyy-MM-dd`，可为空）。状态 `4` 仍保留余额、客户统计和编号池占用，但不能排餐或核销，可以按剩余餐数退餐。新建订单可指定 `1` 或 `4`；编辑只允许状态不变或在 `1` 与 `4` 之间暂停/恢复，已取消、已完成和已退餐订单不可恢复。编辑时从状态 `1` 改为 `4`，服务端自动写入当天；恢复时清空。请求不接受客户端指定生效日期。恢复一个餐次为 `null` 的待通知订单前，必须先明确选择餐次。

## 2. API 接口

### 2.1 分页查询订单

**请求**

```
GET /api/customer/order
```

**Query 参数**

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| page | Integer | 否 | 页码，从 1 开始，默认 1 |
| size | Integer | 否 | 每页条数，默认 10 |
| orderCode | String | 否 | 订单编号（模糊查询） |
| customerName | String | 否 | 客户姓名（模糊查询） |
| status | Integer | 否 | 订单状态 |

订单管理页面使用本接口实现滚动懒加载，首次请求 `page=1&size=20`，触底后递增 `page` 并追加 `content`，以 `totalElements` 判断总量。筛选、重置及常规订单操作后从首批重新加载；行内编辑刷新时使用 `page=1` 和已加载页数乘以 20 的 `size` 刷新已加载范围，保留滚动位置。页面不再展示分页器，失败时可重试。后端分页契约保持不变。

**响应字段补充**

| 字段 | 类型 | 说明 |
|------|------|------|
| scheduledCount | Integer | 已排餐餐数，统计当前订单全部有效排餐记录总数，不区分是否已核销 |
| estimatedRemainingCount | Integer | 预计剩余餐数，计算公式：`remainingCount - 今日已排餐但未核销餐数`，最小值为 0；今天已核销餐数已体现在 `remainingCount` 中，不重复扣减 |
| importedVerifiedCount | Integer | 批量导入前的历史已核销基数，包含在 `verifiedCount` 中；普通订单为 0，历史部分没有系统内逐餐核销日志 |
| pauseEffectiveDate | String | 暂停生效日期；订单从进行中首次转为暂停时由后端记录，格式 `yyyy-MM-dd`，可为空 |
| trialConverted | Boolean | 是否试餐成单 |
| trialOrderId | Long | 关联试餐订单ID |
| trialOrderCode | String | 关联试餐订单编号 |
| medicalRequirements | String | 客户共享医嘱，读取当前客户档案 |
| dishRequirements / dishRequirementsRaw | List | 客户共享的想吃对象引用与导入原文块 |
| dietaryRestrictions / dietaryRestrictionsRaw | List | 客户共享的禁忌对象引用与导入原文块 |
| postoperativeInfo | String | 客户术后情况原文 |

前端订单列表默认业务列及顺序与“排餐计划”（客户用餐统计页）一致：手机号、地址、客户编号、客户姓名、特殊要求、排餐模式、餐次、规格、含汤、早餐、午晚、合计、核销、已排餐、剩余、预计剩余、状态、基本情况、成单时间、术后天数、菜品特殊要求、过敏食物、禁忌食物、自定义菜单。余额、销售渠道、订单期间、定金、总金额、成交金额、订单编号仅默认隐藏，可在列设置中重新显示；接口仍保留这些字段，金额权限不变。订单查询、勾选、行内编辑及编辑/退餐操作沿用原有能力。

**请求体**

```json
  "childPackageId": 2,

  "breakfastCount": 30,
  "lunchDinnerCount": 60,
  "breakfastPrice": 25.00,
  "lunchDinnerPrice": 45.00,
  "verifiedCount": 0,
  "verifiedAmount": 0.00,
  "mainDishCount": 2,
  "sideDishCount": 1,
  "vegCount": 3,
  "riceCount": 1,
  "riceType": "白米饭",
```

**字段说明**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| customerId | Long | 是 | 客户ID |
| parentPackageId | Long | 否 | 父套餐ID |
| childPackageId | Long | 否 | 子套餐ID |
| totalAmount | BigDecimal | 否 | 总金额；无金额编辑权限时可不传 |
| finalAmount | BigDecimal | 否 | 成交金额；无金额编辑权限时可不传 |
| depositAmount | BigDecimal | 否 | 定金金额，默认 0 |
| breakfastCount | Integer | 否 | 早餐合计餐数，默认 0 |
| lunchDinnerCount | Integer | 否 | 午餐+晚餐合计餐数，默认 0 |
| breakfastPrice | BigDecimal | 否 | 早餐单价，默认 0 |
| lunchDinnerPrice | BigDecimal | 否 | 午餐晚餐单价，默认 0 |
| verifiedCount | Integer | 否 | 核销餐数，默认 0 |
| verifiedAmount | BigDecimal | 否 | 核销金额，默认 0 |
| mainDishCount | Integer | 是 | 每餐主菜数量，>= 0 |
| sideDishCount | Integer | 是 | 每餐副菜数量，>= 0 |
| vegCount | Integer | 是 | 每餐素菜数量，>= 0 |
| riceCount | Integer | 否 | 每餐米饭数量，默认 1 |
| riceType | String | 否 | 米饭类型，默认 `白米饭`；建议从 `GET /api/dishes?dishType=RICE_TYPE&enabled=true` 动态查询菜品名称后回填 |
| soupCount | Integer | 是 | 每餐汤数量，>= 0 |
| customMenuImage | String | 否 | 自定义菜单图片地址，用于客户换菜参考，长度不超过 500 |
| dealTime | LocalDateTime | 否 | 成交时间 |
| firstDeliveryTime | LocalDateTime | 否 | 第一次送餐时间 |
| startDate | LocalDate | 否 | 订单开始日期 |
| mealType | String | 否 | `ALL`/`LUNCH_DINNER`/`LUNCH`/`DINNER`；批量导入的待通知订单可为 `null`，此时不自动排餐，操作人确认餐次前不能恢复或调整排餐 |
| startMealType | String | 否 | 开始餐次：`BREAKFAST`/`LUNCH`/`DINNER`；默认随 `mealType` 自动补齐 |
| endDate | LocalDate | 否 | 订单结束日期 |
| status | Integer | 否 | 创建时可为 `1`（进行中）或 `4`（暂停），默认 `1`；编辑仅允许状态不变或在 `1`/`4` 间切换 |
| trialConverted | Boolean | 否 | 是否试餐成单，默认 false |
| trialOrderId | Long | 否 | 关联试餐订单ID；`trialConverted=true` 时必填 |
| remark | String | 否 | 备注 |
| replaceRules | Array | 否 | 换菜规则列表，详见下方结构 |

**replaceRules 子结构**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| sourceDishId | Long | 是 | 原菜品ID |
| sourceDishName | String | 是 | 原菜品名称（快照） |
| sourceDishType | String | 否 | 原菜品类型（快照） |
| targetDishId | Long | 是 | 目标菜品ID |
| targetDishName | String | 是 | 目标菜品名称（快照） |
| targetDishType | String | 否 | 目标菜品类型（快照） |
| remark | String | 否 | 备注 |

**业务规则**

- `finalAmount` 不能超过 `totalAmount`
- `verifiedCount` 不能超过合计餐数
- `verifiedAmount` 不能超过 `finalAmount`
- `startMealType` 必须与 `mealType` 兼容：`ALL → BREAKFAST/LUNCH/DINNER`，`LUNCH_DINNER → LUNCH/DINNER`，`LUNCH → LUNCH`，`DINNER → DINNER`
- `endDate` 不能早于 `startDate`
- `餐费余额` = `成交金额` - `核销金额`（后端自动计算）
- `剩余餐数` = 合计餐数 - 核销餐数（后端自动计算）
- 批量导入订单的历史已核销数由服务端写入 `importedVerifiedCount` 并计入 `verifiedCount`；编辑不能将已核销数降到该基数以下
- `订单编号` 自动生成，格式：`ORDyyyyMMddXXX`（XXX为当日序号）
- `riceCount` 未传时默认 `1`，`riceType` 未传时默认 `白米饭`
- `riceType` 建议提交 `dish_type = RICE_TYPE` 的菜品名称，订单页可通过菜品查询接口动态加载
- `trialConverted=true` 时必须传入 `trialOrderId`，且关联订单的父套餐名称必须包含“试餐”
- `trialConverted=false` 时后端会清空 `trialOrderId`
- `replaceRules` 为可选数组，同一订单内 `sourceDishId` 不能重复，原菜和目标菜不能相同
- 编辑时传入 `replaceRules` 会全量替换旧规则（先软删除再重新插入）
- 换菜规则在排餐计划生成时自动应用，优先级最高

**响应**

```
201 Created
```

### 2.5 编辑订单

**请求**

```
PUT /api/customer/order
Content-Type: application/json
```

**请求体**

同 2.4 新增订单，需额外传入 `id` 字段。

**业务规则**

- 只有在编辑时修改了 `parentPackageId`，系统才会按新父套餐编号池刷新**当前订单**的 `customerCode`
- 上述刷新会同步回写 `customer_profile.customer_code`，但不会改动该客户的其他订单

### 2.6 行内修改订单字段

订单列表默认显示各字段当前值；拥有编辑权限的操作人点击具体值后才打开该字段编辑控件。规格中的主菜、副菜、素菜分别修改，手机号和每个已有地址槽位也独立修改，每次仍只调用一次本接口。饮食对象字段点击单元格后直接展开多选框，可连续增删多项；收起下拉框（点击外部或按 Tab）时自动提交完整数组，Esc 取消，对象集合未变化时不发请求；来源原文保持只读。自定义菜单点击缩略图或“上传菜单”打开弹窗，图片上传完成或删除时调用本接口保存图片路径；无编辑权限时弹窗只用于预览已有图片。

**请求**

```
PATCH /api/customer/order/{id}/inline
Content-Type: application/json
```

使用 `customerOrder:edit` 权限。请求体必须且只能包含 `field`、`value`、`expectedValue` 三个键；三个键都必须出现，`value` 和 `expectedValue` 可以显式为 `null`。每次只更新一个白名单字段：

| `field` | `value` 类型与规则 | 归属及副作用 |
|------|------|------|
| `mainDishCount`、`sideDishCount`、`vegCount` | 非负整数 | 更新当前订单对应菜品数 |
| `soupCount` | 整数 `0` 或 `1` | 更新当前订单含汤设置 |
| `scheduleMode` | `SCHEDULE`、`DAILY`、`WEEKEND`、`WEEKDAY` 之一 | 更新当前订单排餐模式 |
| `customMenuImage` | 已上传文件的 `/file/...` 路径，或 `null` | `null` 清除图片引用，不删除物理文件；不接受外部 URL |
| `breakfastCount`、`lunchDinnerCount` | 非负整数 | 总餐数不得小于已核销数；同步重算 `remainingCount` |
| `status` | `1` 或 `4` | 只允许进行中与暂停互切；暂停日期按现有规则设置或清空 |
| `specialRequirements` | 字符串或 `null`；空白文本清空 | 更新客户档案；同客户其他订单列表的显示值随之更新 |
| `allergyTags` | 字符串数组；`null` 或空数组表示清空 | 去除首尾空白、空项并去重后更新客户档案；同客户其他订单列表的显示值随之更新 |
| `dishRequirements`、`dietaryRestrictions` | 饮食对象数组；`null` 或空数组表示清空，每项含 `type`、`id`、`name` | 整体替换对应客户档案字段；名称以服务端有效字典为准，仍保留在数组中的既有停用/删除引用沿用原名称快照 |
| `phone` | 符合 `^1[3-9]\d{9}$` 的大陆手机号 | 更新客户档案手机号；同客户其他订单列表同步显示 |
| `addressDetail:DEFAULT`、`addressDetail:WORKDAY`、`addressDetail:WEEKEND` | 非空且不超过 200 字符的地址文本 | 只更新对应的已有地址槽位；槽位不存在时需先到客户档案中添加 |
| `customerCode` | 字符串 | 校验当前订单父套餐编号池前缀、纯数字后缀、数值范围和档案唯一性；同步客户档案与当前订单，不修改该客户其他订单 |

数字字段的 `expectedValue` 使用 JSON 整数；字符串、数组按对应字段类型传值。过敏标签的旧值比较先去空、去重；饮食对象旧值仅按去重、排序后的 `type:id` 集合比较，不比较名称快照。客户编号数字后缀沿用现有手工编号规则，不要求固定宽度，编号整体不能超过 16 个字符。

**请求示例**

```json
{
  "field": "breakfastCount",
  "value": 25,
  "expectedValue": 24
}
```

清空菜单图片时，`value` 可为 `null`，`expectedValue` 仍须传入页面读取到的旧路径或 `null`。清空饮食对象字段时，`value` 可传 `null` 或 `[]`，`expectedValue` 传页面读取到的完整对象数组。

修改地址时，例如 `field` 为 `addressDetail:WEEKEND`，`value` 和 `expectedValue` 分别传该周末地址的新旧详细地址。列表地址对象的 `addressType` 提供对应槽位代码，`type` 仍为中文展示名称。

**响应**

```
204 No Content
```

**并发、校验与审计**

- 服务端锁定订单行并比较当前值与 `expectedValue`；旧值不一致返回 `409 Conflict`，前端应刷新当前页后让操作人确认最新值。
- 非法字段、类型、枚举、图片路径、餐数或编号返回 `400 Bad Request`；终态订单不可行内修改。权限不足沿用现有拒绝响应。
- 每次实际变更在同一事务内追加一条 `customer_order_inline_audit`，记录操作人、字段键，以及按实体主键组织的前后状态 JSON。餐数审计包含剩余数，状态审计包含暂停生效日，客户编号审计包含订单与客户档案两处值，手机号审计记录客户档案，地址审计记录地址槽位和详细地址；饮食对象审计记录对应档案数组。新对象必须来自当前有效字典，仍保留在当前值中的停用/删除对象可原样保留，不能作为新引用加入。无变化请求不新增审计记录。
- 审计记录没有修改或删除接口。管理员根据审计 ID 核对当前值后手动修复；修复本身也应保留操作人和前后状态记录。异步 `sys_log` 继续记录请求，不替代行内变更审计。


行内编辑审计表由 `eladmin/sql/customer_order_inline_audit.sql` 新增，部署时先应用该表，再上线后端和前端。表只追加，不随应用回滚删除：

| 字段 | 说明 |
|------|------|
| `id` | 审计记录主键 |
| `order_id`、`customer_id` | 被修改的订单和所属客户主键 |
| `field_key` | 本次请求修改的白名单字段键 |
| `operator`、`created_at` | 操作人和审计记录创建时间 |
| `before_state`、`after_state` | 按 `customer_order:{id}`、`customer_profile:{id}` 组织的字段状态 JSON |

索引支持按订单、客户或操作人及时间查询。此表不设业务修改/删除接口；数据库发布前需备份并确认 DDL 窗口，线上 DDL 由发布流程执行。
