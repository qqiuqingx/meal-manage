# 排餐管理

## 业务定位

排餐管理根据每日生效订单，生成客户的菜品配送计划。是连接订单（客户买了什么）和配菜（实际送什么）的执行层。每天由运营人员手动触发，或可配置定时任务自动生成。

---

## 核心概念

### 三层表结构

```
meal_plan（排餐计划主表）
  └── meal_plan_customer（排餐客户表）
        └── meal_plan_customer_item（客户菜品明细表）
```

| 表 | 作用 | 核心字段 |
|----|------|----------|
| `meal_plan` | 一次排餐事件 | record_date, meal_type, total_count, success_count, fail_count, status |
| `meal_plan_customer` | 一个客户的一份当次餐排餐结果 | customer_id, order_id, serving_no, status, fail_reason, is_verified, verification_time, supplementary_*_count |
| `meal_plan_customer_item` | 该份当次餐的菜品明细 | dish_type, dish_id, dish_name, is_replaced, original_dish_id, replace_reason |

### scheduleKey（排期匹配键）

由 `ScheduleKeyUtil` 工具类统一计算：

| 日期范围 | 周序号 | 计算规则 |
|---------|--------|---------|
| 1-7 日 | 第 1 周 | |
| 8-14 日 | 第 2 周 | |
| 15-21 日 | 第 3 周 | |
| 22-28 日 | 第 4 周 | |
| 29-31 日 | 映射为第 1 周 | 29日→第1周, 30日→第1周, 31日→第1周 |

格式：`W-D`（W=周序号 1-4，D=星期 1-7）

```
2026-04-01（周三）→ "1-3"
2026-04-08（周二）→ "2-2"
2026-04-25（周六）→ "4-6"
2026-04-29（周三）→ "1-3"  （月末映射回第1周）
```

`ScheduleKeyUtil.calcWeek` / `calcDay` / `isWeekday` / `isWeekend` 也用于订单 `schedule_mode` 判断和菜品列表的排期日期搜索，是跨模块复用的纯函数。

生成接口允许额外传入 `menuWeekNum + menuDayOfWeek` 覆盖菜单定位：

- `recordDate` 始终是实际排餐/配送日期
- `menuWeekNum + menuDayOfWeek` 仅用于查询 `meal_schedule_plan`
- 两个字段要么都不传，要么都传
- 不传时按 `recordDate` 通过 `ScheduleKeyUtil` 推导

### 餐次（meal_type）

| 类型 | code | 说明 |
|------|------|------|
| 早餐 | `BREAKFAST` | 参与排餐计划（生成 `meal_plan_customer` 记录），但不生成菜品明细 |
| 午餐 | `LUNCH` | |
| 晚餐 | `DINNER` | |

### 排餐状态（status）

| 状态 | code | 说明 |
|------|------|------|
| 生成中 | `GENERATING` | 事务进行中 |
| 成功 | `SUCCESS` | 所有客户排餐成功 |
| 失败 | `FAILED` | 部分或全部客户排餐失败 |

### 客户排餐状态（status）

| 状态 | 值 | 说明 |
|------|------|------|
| 失败 | `0` | 该客户本次排餐失败（记录在 `fail_reason`） |
| 成功 | `1` | 排餐成功 |

## 核心业务流程

### 1. 生成排餐计划

触发：`POST /api/meal-plan/generate`，参数为 `recordDate` + `mealType`，可选 `customerId`、`menuWeekNum`、`menuDayOfWeek`。

其中：

- `recordDate` 是实际排餐/配送日期
- `mealType` 支持 `BREAKFAST` / `LUNCH` / `DINNER`
- `menuWeekNum + menuDayOfWeek` 仅用于查询 `meal_schedule_plan`
- `menuWeekNum`、`menuDayOfWeek` 要么都不传，要么都传；不传时按 `recordDate` 推导菜单周次和菜单星期

**前置准备：并发锁控制**

对同日期同餐次使用 `ReentrantLock` 加锁，防止重复并发生成。事务提交后自动释放锁。

**步骤一：有效订单过滤**

对每个 `status=1`（进行中）的订单，检查：

```
remaining_count > 0
start_date <= recordDate <= end_date
meal_type 包含当前餐次（BREAKFAST/LUNCH/DINNER/ALL）
若 recordDate = start_date，则还需满足 start_meal_type <= 当前餐次：
  - BREAKFAST → 当天早餐/午餐/晚餐均可排
  - LUNCH     → 当天仅午餐/晚餐可排
  - DINNER    → 当天仅晚餐可排
schedule_mode 满足当前日期：
  - DAILY     → 每天
  - WEEKDAY   → 周一至周五
  - WEEKEND   → 周六、周日
  - SCHEDULE  → delivery_dates JSON 包含当天
    - 新格式: [{"date": "2026-04-01", "mealTypes": ["LUNCH", "DINNER"]}]
    - 旧格式: ["2026-04-01", "2026-04-02"]
    - 新格式支持按日期指定餐次
```

基础排餐按订单开始日期、开始餐次和送餐模式顺序消耗购买餐数；早餐使用早餐池，午餐和晚餐共享午晚餐池。餐数耗尽后，即使送餐模式仍匹配，后续日期也不会生成。订单状态 4 时还需检查 `pause_effective_date`，该日期当天及之后不生成。

**步骤二：已排餐数量上限检查**

批量统计各订单当前餐数池的成功排餐份数（`countScheduledByOrderIds`），统计口径为 `status=1`、`meal_plan_customer.deleted=0` 且关联 `meal_plan.deleted=0`。统计规则如下：
- BREAKFAST：只统计 `BREAKFAST`
- LUNCH / DINNER：合并统计 `LUNCH + DINNER`，因为二者共享 `lunch_dinner_count` 餐池

若该数量 >= 订单对应餐次的餐数上限则跳过：
- BREAKFAST：上限为 `order.breakfastCount`
- LUNCH/DINNER：上限为 `order.lunchDinnerCount`

**步骤三：客户排除日期过滤**

检查客户档案中的排除日期配置 `excluded_dates`，如果该日期+餐次被排除，则跳过该订单。

**餐数耗尽预警**

排餐完成后可通过 `GET /api/meal-plan/depletion-warnings` 查询目标日期的餐数耗尽预警。预警按订单的两个餐数池分别计算：

- 早餐池剩余 = `breakfast_count - BREAKFAST 已核销数`
- 午晚餐池剩余 = `lunch_dinner_count - imported_verified_count - LUNCH 已核销日志数 - DINNER 已核销日志数`

当某个餐数池当前剩余餐数为 1，或目标日期该餐数池已成功排餐数会使剩余餐数耗尽时返回预警。预警不使用订单 `remaining_count` 合计值作为唯一判断条件，避免早餐池和午晚餐池相互掩盖。

**订单级排餐日历调整**

客户用餐统计页按单笔订单加载和保存指定月份的日历，`order_id` 是覆盖、排餐查询和清理的身份键：

- 客户档案 `excluded_dates` 表示客户统一停餐，优先于订单覆盖，并对同客户所有订单生效。订单日历不修改客户字段；被统一停餐遮蔽的订单覆盖仍原样保存，解除统一停餐后重新生效。
- `customer_meal_schedule_addition` 存储订单日期餐次的完整目标量。缺少覆盖时按订单基础排餐计算；`quantity=0` 表示只停用当前订单该格，正数表示该格目标份数，负数非法。0 份不扣购买餐数，释放的额度按日期顺序分配给后续单元格。
- 早餐使用独立餐池，午餐和晚餐共享餐池；午晚餐预算先扣除 `imported_verified_count`。跨月计算保留此前月份和其他格的覆盖，订单日历只保存、清理本订单当前月份的覆盖。
- 日历请求是该订单当月覆盖的完整快照，空数组表示恢复该订单当月所有可编辑覆盖。保存和软删除都限定该 `order_id` 与月份范围；不会自动改绑同客户另一笔订单。
- 暂停、餐次未确认、已关闭或已无剩余餐数的订单只读。统一停餐格不可在订单日历修改；订单停餐格恢复默认时移除覆盖记录，不等同于将数量设为 1。
- 订单覆盖仍须符合订单状态、有效期、开始餐次、餐次类型、数量池和已核销份数。若当前月计划已超过其他月份占用后的可用量，允许不增加本月总量的减少；增加或恢复后超额则拒绝。
- `soup_quantity` 为空时沿用订单汤品设置，显式值须在 0 到目标份数之间；目标量为 0 时归一化为空。早餐不使用含汤份数。
- 调整目标数后遍历该订单当月全部受影响日期餐次，包括统一停餐格和数量顺延格。超出新目标时优先清理失败份，再清理份序较大的未核销份；目标减少不自动生成新菜品。
- 清理按订单、日期、餐次选取排餐，只能软删除 `is_verified=0/null` 的有效行；关联菜品、换菜关系及父计划汇总在同一事务内更新。若核销并发先完成导致 SQL 影响行数不足，整次保存回滚。
- 排餐生成读取同一数量分配算法；零份覆盖不作为人工新增候选，也不能中止同一日期其他订单的生成。排餐生成、核销及日历调整先按订单锁定，再更新排餐计划或客户排餐行。

**步骤四：候选菜加载（已迁移到 meal_schedule_plan）**

候选菜查询使用“菜单定位”而不是配送日期本身：

- 未传 `menuWeekNum`、`menuDayOfWeek` 时，按 `recordDate` 推导 `week_num + day_of_week`
- 传入 `menuWeekNum`、`menuDayOfWeek` 时，实际排餐日期仍是 `recordDate`，但普通菜品候选池改为按指定 `week_num + day_of_week` 查询
- 两个字段仅影响 `meal_schedule_plan` 查询，不影响订单生效判断、客户排除日期判断、排餐主记录日期等业务语义

候选菜由两部分合并而成，按 `dish.id` 去重：

1. **排期菜品**：从 `meal_schedule_plan` 表查 `week_num + day_of_week + meal_time` 匹配的记录，JOIN `dish` 取菜品详情。SQL 中用 `msp.dish_category` 覆盖 `d.dish_type`，保证候选池里每条菜的 `dishType` 与排期坑位一致（同一道菜在不同坑位可以扮演不同角色）。
2. **米饭菜品**：从 `dish` 主档查 `dish_type = RICE_TYPE` 且 `enabled = 1` 的记录。**米饭不依赖 `meal_schedule_plan`**，是全局通用菜池。

旧逻辑通过 `dish.schedule` JSON 字段过滤的方式已废弃。

**步骤五：按父套餐归类候选菜池（buildCandidateDishPool）**

对每个出现在订单里的父套餐，构造一个独立的 `dishType → List<Dish>` 候选 Map：

- 普通菜品（`MAIN/SIDE/SOUP/VEGETABLE`）：必须满足 `meal_packages` 包含当前父套餐编码或 ID 才纳入；
- `RICE_TYPE` 米饭：跳过套餐匹配检查，所有父套餐都共享同一池米饭；
- 进入候选池后，`RICE_TYPE` 被规整化为 `RICE`（`normalizeCandidateDishType`），下游选菜逻辑只看到 `RICE` 类型。

候选池按 `sort` + `id` 稳定排序，保证同一输入下选菜结果可预期。

**步骤六：过敏过滤（升级为三级匹配，2026-04-24）**

不再用 `customer.allergy_tags` 与 `dish.ingredients` 字符串做模糊匹配，而是：

1. 加载菜品 → 配料名集合：通过 `dish_ingredient_relation` JOIN `dish_ingredient` 获取每道菜对应的配料名集合；
2. 加载分类 → 配料映射：从 `dish_ingredient_category` 一次性加载「分类名 → 该分类下所有配料名集合」（一级和二级分类合并到同一个 Map，分类名重复时合并集合）；
3. 对每个客户过敏标签依次匹配：
   - **优先级 1**：与配料名精确相等 → 命中（如客户过敏"鸡肉"，菜含"鸡肉"）；
   - **优先级 2**：与某个分类名相等 → 展开该分类下所有配料名集合，菜的配料命中其中任意一个 → 命中（如客户过敏"禽肉"二级分类，菜含"鸡肉"）；
   - **优先级 3**：分类匹配同样适用一级分类（如客户过敏"肉类"一级分类，菜含"猪肉"也命中）。

匹配命中的过敏标签会回写到 `meal_plan_customer_item.allergy_reasons`（多个用逗号分隔），用于前端展示过敏原因。

**步骤七：按菜品数量配置选菜**

菜品数量配置从 `CustomerOrder` 直接读取（废弃 SubPackage 字段），每日每类固定提供 1 份：

| 菜品类型 | 每日固定提供 | 说明 |
|---------|-------------|------|
| 主菜 | 1 份 | 从 MAIN 类型选 |
| 副菜 | 1 份 | 从 SIDE 类型选 |
| 素菜 | 1 份 | 从 VEGETABLE 类型选 |
| 汤 | 0-1 份 | 从 SOUP 类型选（订单要求时才选） |
| 米饭 | 0-1 份 | 见下方"米饭选菜逻辑" |

**米饭选菜逻辑（pickRiceDish）：**

1. 候选池中筛 `dish_type = RICE`（已规整化的 `RICE_TYPE`）；
2. 若订单 `riceType` 有具体值且不等于 `默认`，先在候选中按 `name` 精确匹配；
3. 若订单 `riceType = 默认`，按未指定处理，直接从全部米饭候选中选一个可用的；
4. 匹配不到指定类型 → 回退到名称等于 `白米饭` 的默认米饭；
5. 仍未命中 → 回退到全部米饭候选中选一个可用的；
6. 选定的菜品在写入明细时 `dish_type` 统一记为 `RICE`。
7. 若订单 `riceType != 默认`，写入 `meal_plan_customer_item` 时统一标记 `is_replaced=1`，`replace_reason=客户选择替换`，`original_dish_id/original_dish_name` 固定记录排序后首个菜单米饭候选（即当天菜单基准米饭），不记录最终回退选中的米饭。

**补菜数量计算**：
```
补菜数量 = max(0, 订单配置数 - 每日固定1份)
```

| 订单配置数 | 每日固定 | 补菜数量 |
|-----------|---------|---------|
| 1 | 1 | 0 |
| 2 | 1 | 1 |
| 3 | 1 | 2 |

补菜数量记录在 `meal_plan_customer` 表的 `supplementary_*_count` 字段，供前端显示"加菜"提示。

**步骤八：订单级换菜规则应用**

在选菜完成后、保存菜品明细前，检查当前订单是否配置了换菜规则（`customer_order_replace_rule`）：

1. 批量加载所有有效订单的换菜规则，构建 `Map<orderId, Map<sourceDishId, rule>>`
2. 遍历已选菜品，若匹配到换菜规则：
   - 检查目标菜是否仍然启用且未被删除，若目标菜无效则跳过该规则（保留原菜）
   - 用目标菜替换原菜，记录 `original_dish_id`、`original_dish_name`、`original_dish_type`
   - 标记 `is_replaced=1`，`replace_reason=ORDER_RULE`
   - **跳过过敏/忌口过滤**：被替换的菜品不参与后续过敏匹配
3. 换菜规则优先级最高，覆盖之前的选菜结果（包括过敏替换的结果）

**步骤十：手工换菜（排餐单级）**

手工换菜与订单级换菜规则不同，它配置在已生成的排餐单上，用于生产单展示和现场执行：

- **订单级换菜规则**：配置在订单上，排餐生成时自动生效（`replace_reason = ORDER_RULE`）
- **排餐单级手工换菜单**：配置在某一张已生成的排餐单上，存在 `meal_plan_manual_replace` 表中

手工换菜不修改 `meal_plan_customer_item` 的数据，是独立的换菜关系表。一条换菜关系通过 `customer_plan_id` 关联某张排餐单中的某一份，不能按客户编号合并多份。

保存时采用全量覆盖策略：先软删当前排餐单旧换菜关系，再插入新关系。若保存的换菜项为空数组，则表示清空当前排餐单所有手工换菜关系，不再插入新记录。

**步骤九：回退逻辑（暂未启用）**

当日菜品因过敏全部过滤时，暂不启用次选类型替换和次日菜品回退。

### 2. 幂等生成

同一天同一餐次重复调用时，保留已核销份，只软删除未核销结果及其菜品/换菜明细，再补齐目标份数；如计划内没有已核销份，软删除旧主记录后新建。

**指定客户生成模式**：如果传入 `customerId`，只重生该客户未核销份，保留该客户已核销份、主记录和其他客户的记录。

### 3. 地址自动选择

`GET /api/meal-plan/{mealPlanId}/customer-addresses` 根据排餐日期自动选择客户地址：

| 排餐日期 | 选择规则 |
|---------|---------|
| 周六、周日 | `WEEKEND` 地址 |
| 周一至周五 | `WORKDAY` 地址 |
| 指定类型地址不存在 | fallback 到 `DEFAULT` 地址 |
| 三个都没有 | 返回 null |

该接口同时返回客户过敏标签、普通特殊要求、医嘱、想吃/禁忌原文块及已确认对象、术后信息，以及当前排餐订单的 `custom_menu_image`，供排餐页面的客户资料查看入口使用。信息从关联客户主档读取，不写入排餐结果表。

### 4. 删除排餐记录

- 按日期+餐次删除：`DELETE /api/meal-plan?recordDate=X&mealType=Y`
- 按 ID 批量删除：`DELETE /api/meal-plan/batch`，级联删除客户和菜品明细
- 按客户排餐 ID 删除：`DELETE /api/meal-plan/customers`

**重要**：删除排餐记录是软删除（`deleted=true`），且**不影响核销数据**（`meal_verification_log` 独立保留）。

## 数据模型

### meal_plan — 排餐计划主表

| 字段 | 类型 | 说明 |
|------|------|------|
| `record_date` | DATE | 实际排餐/配送日期 |
| `meal_type` | VARCHAR | 餐次：BREAKFAST / LUNCH / DINNER |
| `total_count` | INT | 参与排餐客户总数 |
| `success_count` | INT | 成功数 |
| `fail_count` | INT | 失败数 |
| `status` | VARCHAR | GENERATING / SUCCESS / FAILED |
| `generate_time` | DATETIME | 生成时间 |
| `deleted` | TINYINT | 软删除标记 |

### meal_plan_customer — 客户排餐表

### 日历调整删除规则

- 客户导入日期及之前的午晚餐格作为历史数量保存在 `customer_meal_schedule_addition`，备注为“客户用餐计划表历史导入”。订单数量日历只读显示，无真实进度时不生成核销日志或排餐结果；从未来计划转入历史的格保留已有真实进度，不计入未来排餐餐池；订单业务开始日期取成单日期，独立 `import_date` 控制未来排餐；有效排餐下界为 `max(start_date, import_date + 1日)`，之前的缺格不会占用未来余额。普通订单没有导入日期，仍以订单开始日排餐。
- 保存时按当前订单和月份提交可编辑覆盖快照；同订单、日期、餐次已有历史记录时优先恢复该记录，否则新增。旧记录的 `quantity` 默认按 1 解释。
- 未出现在快照中的覆盖仅在当前 `order_id` 和月份范围内软删除；空数组表示清除本订单本月可编辑覆盖，恢复基础排餐计算。历史导入记录由日历保存接口自动保留，日历直接修改历史格的请求被拒绝。月度导入可按文件修正该月份导入来源格，但不得减少或移除已核销份，也不能覆盖人工来源格；只清理本订单本月份超额未核销结果。
- 覆盖变化后按当前订单、日期和餐次检查已生成份数，只能软删除未核销排餐及对应菜品、手工换菜明细，并刷新父级 `meal_plan` 汇总。调低份数时保留已核销份，超出目标的未核销份优先清理失败份，再按份序从大到小清理。
- 客户统一停餐通过 `customer_profile.excluded_dates` 生效，不由订单日历改写。订单日历仅修改当前订单；其他订单的覆盖和生成排餐不参与清理。
- 并发核销导致可清理的未核销行数变化时，若受影响行数与预期不符，保存事务回滚；已核销份不得被软删除。

## 首次成功排餐标记

- **标记维度**：`order_id + meal_type`
- 仅成功排餐（`meal_plan_customer.status = 1`）参与首次判定
- 失败排餐不占用首次资格
- 左侧编号区展示时，首次客户排在前面，组内保持原顺序
- **标记页面范围**：排餐计划管理页、打印页
- **判定逻辑**：后端 SQL 使用 `NOT EXISTS` 模式，查询同一 `order_id + meal_type` 下是否有更早的成功记录

## 编号区特殊要求展示

排餐记录页面左侧编号区，除 tooltip 悬浮展示完整特殊要求外，对特定内容直接在客户编号下方以标签形式展示：

| 特殊要求内容 | 展示形式 | 标签样式 |
|------------|---------|---------|
| 包含"加x份米饭"（x 为任意数字，允许空格如"加 1 份米饭"） | 蓝色标签显示匹配到的原文（如"加 1 份米饭"） | 蓝底蓝字（`#dbeafe` / `#1e40af`），区别于黄底 supplementary 标签 |

- 数据来源：`customer_profile.special_requirements` 字段，通过 `meal_plan_customer` LEFT JOIN 获取
- 判断逻辑：前端 `getRiceRequirement()` 方法使用正则 `/加\s*\d+\s*份米饭/` 从 `specialRequirements` 中提取匹配内容
- 标签位置：客户编号下方、supplementary-tags 上方
- 无匹配时标签不渲染；特殊要求中其他内容不受影响

客户饮食资料查看入口按“医嘱 → 菜品特殊要求 → 禁忌食物”顺序展示。想吃和禁忌各自列出完整原文块及已确认的菜品、配料、标签或配料二级分类，原文可展开。术后信息直接展示 `postoperative_info` 原文，不再根据排餐日期计算生产后天数或显示 0～3 天标记。以上只用于查看，不增加自动筛菜、替换或禁忌计算规则。
