# 智能排查助手业务说明

> 当前生效版本：2026-08-05
>
> 普通业务查询和排餐诊断统一使用 `BusinessAgentRunner` 的 LLM Tool Calling 链路。Java 只负责工具供给、权限、参数约束、预算、脱敏、事实校验、审计和安全降级；模型负责理解客服目标、选择工具、组合查询、澄清和生成文本。

## 1. 业务定位

智能排查助手面向已登录的内部客服，提供客户、订单、排餐、核销、退餐、套餐、菜品和运营指标的只读查询，并支持基于同一组领域工具的排餐未生成原因分析。

助手不执行下单、排餐、核销、退餐、退款、修改客户或修改订单等写操作，也不接受 SQL、表名、任意字段、任意排序、接口地址、权限集合或访问令牌。

## 2. 服务客户口径

产品将一次订单视为客户的一次服务实例，但数据库仍保留客户档案与订单的 1:N 关系：

```text
ServiceCustomer
├── customerId / customerCode：客户档案
├── orderId / orderCode：一次服务周期
├── package：父套餐和子套餐
├── mealBalance：早餐、午晚餐餐数池
├── mealPlans：排餐记录
├── verifications：核销记录
└── refunds：退餐记录
```

同一客户存在多笔订单时，服务客户列表按订单逐笔返回，不合并订单，也不任意选择其中一笔。客户档案查询可以包含尚未下单的客户；订单、排餐、核销和退餐查询必须以可校验的客户或订单关系为边界。

### 2.1 餐数余额

早餐和午餐+晚餐是两个独立口径：

```text
剩余早餐数 = 订单早餐数 - 未删除 BREAKFAST 核销数
剩余午晚餐数 = 订单午晚餐数 - 未删除 LUNCH 核销数 - 未删除 DINNER 核销数
```

午餐和晚餐共享 `lunchDinnerCount` 餐数池，余额不得小于 0。客户档案汇总时只汇总进行中订单；排餐创建、删除和查询不会消耗餐数，只有核销会影响余额。已删除核销日志不参与统计。

### 2.2 时间和范围

- 业务日期使用 `yyyy-MM-dd`，服务时区为 `Asia/Shanghai`。
- 服务客户下单时间优先使用成交时间，成交时间缺失时回退订单创建时间。
- 核销和退餐广域查询必须提供日期范围，范围最多 31 个自然日；具体客户或订单历史可不带日期，但仍使用 SQL 分页。
- 排餐和客户订单列表均使用真实 SQL 分页，不先加载无界结果再在内存截断。
- 结果包含 `page/size/total/truncated/queriedAt/warnings`，截断结果不能被回答为完整全集。

## 3. 统一工具目录

Agent 只允许使用以下 12 个只读工具，名称、输入 Schema、输出契约、权限、结果上限、超时和卡片类型以 `agent-service/src/main/java/me/zhengjie/agent/tool/ToolRegistry.java` 为唯一登记源。

| 工具 | 业务用途 | 默认权限 | 最大结果 |
| --- | --- | --- | ---: |
| `searchCustomerProfiles` | 客户档案及是否已下单搜索 | `customerProfile:list` | 20 |
| `searchServiceCustomers` | 以订单为根的服务客户搜索 | `customerOrder:list` | 20 |
| `getServiceCustomerDetail` | 单客户或单订单综合快照 | `customerProfile:list` + `customerOrder:list` | 1 |
| `listMealPlans` | 排餐和菜品摘要 | `mealPlan:list` | 50 |
| `listVerifications` | 未删除核销记录 | `mealVerification:list` | 50 |
| `listRefunds` | 退餐记录，不含退款金额 | `mealRefund:list` | 50 |
| `previewDishCandidates` | 指定服务客户订单、日期和餐次的候选菜及过滤原因 | 客户、订单、套餐、菜品权限 | 20 |
| `listScheduledDishes` | 公共排期菜单 | `mealPlan:list` + `dish:list` | 20 |
| `searchDishes` | 菜品及配料摘要搜索 | `dish:list` | 20 |
| `getPackageDetail` | 父子套餐规格 | `package:list` | 5 |
| `queryBusinessMetrics` | 登记的运营指标和受控维度 | 指标对应业务权限 | 100 |
| `explainBusinessRule` | 版本化业务规则说明 | `agentDiagnosis:list` | 1 |

工具输入使用强类型 ID、业务编号、日期、分页和 enum；模型不能提交权限、数据范围、任意字段、SQL 或动态 URL。工具输出由主系统裁剪和脱敏后才进入 Agent。

## 4. LLM Tool Calling 流程

```text
客服问题
  ↓
BusinessAgentRunner
  ↓ 注入业务日期、会话摘要、当前可见工具和安全要求
LLM（toolChoice=auto）
  ↓ 自主选择一个或多个工具
ToolInputGuardrail
  ↓
主系统统一只读 API
  ↓ 重新执行服务身份、签名上下文、业务权限、数据范围和对象关系校验
ToolOutputGuardrail
  ↓
模型观察事实，继续查询、澄清或回答
  ↓
FinalAnswerGuardrail
  ↓
文本回答 + 工具事实 + cards + presentations + 会话 Patch
```

### 4.1 预算

- 单轮最多 6 次工具调用。
- 最多 4 个模型回合；回答修复也受该上限约束。
- 单轮累计最多 100 条业务记录。
- 同工具同参数在单轮内缓存，缓存命中不重复请求下游。
- 单工具默认超时 3 秒，HTTP 适配器有更高硬上限，模型整体超时沿用 Agent profile。
- 工具失败、权限拒绝、超时和预算耗尽转换为稳定错误码，不透传 SQL、堆栈、内部 URL 或下游原始异常。

问候、功能说明和无法确定条件的问题可以不调用工具。涉及当前系统事实的回答必须引用本轮至少一个成功工具事实；没有成功事实时只能澄清或说明无法确认。

## 5. 权限和数据范围

主系统先从当前登录客服签发短期 HMAC 访问上下文，再将当前允许的工具名称传给 Agent。工具白名单只用于减少模型可见面，不承担授权职责；每个统一内部 API 都独立校验：

1. `X-Agent-Internal-Token` 服务身份；
2. `X-Agent-Access-Context` 签名、会话和 requestId 绑定；
3. `agentDiagnosis:list` 入口权限及工具对应业务权限；
4. 部门数据范围解析出的客户 ID 集合；
5. 客户、订单和排餐对象之间的关系。

模型提交的 `customerId/orderId/departmentId/createBy` 只是关联参数，不构成授权依据。无权限对象按空结果或稳定权限告警处理，不暴露对象是否真实存在。请求结束后清理客户数据范围 ThreadLocal。

## 6. 数据安全

### 6.1 禁止进入 Agent 或最终回答

- 订单金额、单价、优惠、退款金额、支付信息；
- 内部 Token、密码、密钥、权限集合和数据范围规则；
- 完整手机号、完整地址和未裁剪的自由文本；
- SQL、Mapper、表名、动态接口 URL 和下游堆栈。

### 6.2 受控返回

- 客户姓名、手机号和地址在主系统 DTO 层脱敏；
- 饮食限制、过敏标签、特殊要求只在具体客户详情且经过长度限制时返回；
- 内部关联 ID 可以在 Agent 工具事实中用于跨工具关联，但由 Agent 输出护栏和前端卡片默认隐藏；
- 退餐结果只返回退餐餐数和已核销不退餐数，不定义退款金额字段；
- 客户自由文本视为不可信数据，命中 Prompt Injection 文本时工具结果被阻断。

输入、输出和最终回答均执行敏感数据护栏。模型不得执行工具结果文本中的指令，不得声称已经修改、下单、排餐、退款或核销。

## 7. 排餐诊断

排餐诊断和普通查询共用上述工具，不再维护独立诊断工具目录。典型问题：

```text
为什么 B3303 今天午餐没有排上？
  ├─ getServiceCustomerDetail
  ├─ listMealPlans
  ├─ previewDishCandidates
  └─ 必要时 getPackageDetail、listVerifications 或 listRefunds
```

候选菜查询若带有订单身份，主系统会先校验客户与订单的归属关系，并只按该订单的有效套餐过滤；关系不成立时返回稳定的服务客户不存在告警，不继续读取候选数据。

`agent-service/rules/meal-plan/` 是诊断规则真相源。规则必须包含 `ruleId`、版本、`requiredTools`、`evidenceFields`、原因码和下一步动作；启动时校验规则 ID 唯一、工具名已登记、证据字段和动作非空。

模型只有在规则所需工具成功返回且证据字段能够从本轮工具事实追溯时，才可将原因作为已验证依据。缺少工具或证据时只能返回“无法确认/需要人工核对”的建议，不得伪造原因、数字或已修复结论。规则说明工具只能读取 `config/agent-business-rules.json` 中登记且经过业务文档哈希校验的主题。

## 8. 会话和恢复

主系统保存最近有限轮次的用户/助手消息，以及脱敏的最近工具摘要、稳定过滤条件和查询时间；不保存模型隐藏推理、Prompt 全文或完整工具原始结果，也不保存固定待补查询或任务栈。

`conversationPatch` 只允许由本轮成功工具调用的强类型入参生成，字段白名单为 `customerId`、`customerCode`、`orderId`、`orderCode`、`mealPlanRecordId`、`recordDate`、`startDate`、`endDate` 和 `mealType`。失败工具、工具输出、模型回答、客服姓名和自由文本不能写入 Patch。相同客户的后续查询保留客户焦点；切换客户时清除旧订单和排餐记录焦点，切换订单时清除旧排餐记录焦点；单日日期与完整日期范围互斥，餐次只接受 `BREAKFAST/LUNCH/DINNER`。最近查询摘要只保留成功工具名、受控过滤条件、查询时间和 `partial` 标志。

主系统仅在 `sessionVersion` 条件更新成功后提交 Patch；没有成功工具事实时不覆盖最近查询摘要。会话恢复只恢复卡片、事实、告警、工具追踪和受控上下文快照，不重新查询实时业务数据。客服提出新的实时问题时，模型必须重新调用工具；句柄或上下文过期、权限变化或对象歧义时必须澄清。

### 8.1 澄清协议

聊天状态只能为 `ANSWERED`、`NEED_MORE_INFO` 或 `ERROR`。`NEED_MORE_INFO` 必须明确返回一个或多个受控 `missingSlots`：`CUSTOMER_OR_ORDER`、`RECORD_DATE`、`DATE_RANGE`、`MEAL_TYPE`、`PACKAGE`、`RULE_TOPIC`，不得在没有成功工具事实时给出实时业务结论。`ANSWERED` 的 `missingSlots` 必须为空。

快捷回复由服务端根据缺失项确定性生成，最多 6 项、每项最多 20 个字符：缺少日期时提供“今天/昨天/明天”，缺少餐次时提供“早餐/午餐/晚餐”，缺少日期范围时提供“输入起止日期”；客户、套餐和规则主题没有登记的固定选项时不伪造按钮。客服点击快捷回复仍按普通用户消息重新查询，不能直接修改会话槽位。

### 8.2 会话列表与生命周期

会话侧栏服务端分页查询当前客服自己的会话，关键字匹配标题、客户编号和最近摘要；前端固定每页 20 条并支持加载更多。新建会话只清空本地聊天状态，首次发送时主系统懒创建服务端会话。归档会话保留历史消息和展示快照，归档视图只读；恢复后才允许继续发送。会话列表、详情、归档/恢复和标题更新均按当前客服做归属校验，不能访问其他客服的会话。

消息写入使用 `clientMessageId` 幂等和会话版本条件更新。跨 Agent 实例继续处理时，实例只接收主系统签发的 v2 执行信封，不接受前端构造的工具白名单、访问上下文或会话内部状态。

## 9. 响应、卡片和审计

聊天响应包括 `assistantMessage`、`status`、`facts`、`cards`、`presentations`、`toolFacts`、`toolTraceSummary`、`warnings`、`partial`、`queriedAt` 和 `conversationPatch`。第一期卡片包括客户档案、服务客户、服务客户详情、排餐、核销、退餐、菜品、候选菜、套餐、指标和业务规则；简单数量问题的业务展示区只保留与用户问题相关的成功事实，并合并重复取得的同指标、同规则或相同空列表。非简单数量问题按规范化工具入参区分事实，跨日期或跨餐次对比不会被合并。完整成功事实仍保留在 `toolFacts`，全部调用仍保留在 `toolTraceSummary`。

前端业务查询结果只展示业务卡片、查询时间和业务告警，不展示 `toolTraceSummary` 中的内部工具名、调用状态或结果数量。工具追踪摘要继续保留在接口响应、会话快照、审计和服务日志中，供系统恢复与技术排障使用；仅有工具追踪摘要而没有业务卡片或告警时，不生成空的业务查询结果区域。

`cards` 是本轮面向当前问题展示的成功工具事实安全快照，`presentations` 只描述如何读取这些数据；两者通过 `sourceToolCallId` 一一关联，每张卡片最多一个展示描述。未被展示或被语义去重的成功事实不从 `toolFacts` 删除，失败调用也不从追踪和告警删除。展示描述不复制业务值，不包含 HTML、Markdown、表达式、组件名或 ECharts option。主系统只透传并持久化，前端使用固定组件解释。

`cards` 是本轮成功工具事实的安全快照，`presentations` 只描述如何读取这些数据；两者通过 `sourceToolCallId` 一一关联，每张卡片最多一个展示描述。展示描述不复制业务值，不包含 HTML、Markdown、表达式、组件名或 ECharts option。主系统只透传并持久化，前端使用固定组件解释。

回答中的数字、日期和状态必须可追溯到本轮工具事实；空结果、工具失败和截断结果必须在文本和 `warnings/partial` 中表达，不能解释为全部不存在或完整查询。

主系统业务查询审计仅记录 requestId、sessionId、客服、受控客户/订单标识、工具名、结果数量、稳定失败码、部分标记、耗时、指标/维度和回答校验状态；不记录 Prompt、模型原始输出、工具原始入参/出参、手机号、完整地址、特殊要求全文或金额。

### 9.1 结构化展示规则

当前 11 类卡片均由 Agent 服务的系统注册表覆盖。已知卡片只生成 `decisionSource=SYSTEM` 的展示描述，不调用展示规划 LLM；`DISH_LIST` 的公共排期菜单和菜品搜索共用同一规则，并按工具选择已登记的数据路径。

| 卡片类型 | 当前固定展示 | 受控数据路径或字段 |
| --- | --- | --- |
| `CUSTOMER_PROFILE_LIST` | 表格 | 客户编号、姓名、是否有订单、创建时间、手机号摘要 |
| `SERVICE_CUSTOMER_LIST` | 表格 | 客户编号、姓名、订单编号、下单时间、订单状态、套餐 |
| `SERVICE_CUSTOMER_DETAIL` | 摘要 + 分区表格 | profile 摘要；订单、排餐、核销、退餐四个 sections |
| `MEAL_PLAN_LIST` | 表格 | 日期、餐次、状态、核销状态、失败原因、菜品摘要 |
| `VERIFICATION_LIST` | 表格 | 日期、餐次、数量、退餐状态、操作时间 |
| `REFUND_LIST` | 表格 | 早餐/午晚餐数量、已核销数量、原因、操作时间 |
| `DISH_LIST` | 表格 | 菜品名称、类型、启用状态、配料摘要、适用餐次 |
| `DISH_CANDIDATE_LIST` | 摘要 + 表格 | 客户存在、客户编号、日期、餐次、候选数量和过滤原因 |
| `PACKAGE_DETAIL` | 摘要 + 表格 | 父套餐摘要和子套餐规格 |
| `METRIC_RESULT` | 摘要；完整 breakdown 时增加表格和柱状图 | `data` 摘要、`data.breakdown[{label,value}]` |
| `BUSINESS_RULE` | 文本摘要 | 规则编号、版本、标题、内容和时间 |

所有路径必须是关联卡片中已登记的点路径或数组路径；字段、格式、视图和数量由后端目录校验。v1 只接受 `TEXT/TABLE/BAR/LINE/PIE` 视图、`TABS` 布局以及 `TEXT/DATE/DATE_TIME/STATUS/MEAL_TYPE/NUMBER/BOOLEAN` 格式。标题最多 100 个字符，字段标签最多 30 个字符，表格每处最多 20 列，详情最多 8 个 sections，图表最多 4 个指标序列。

服务客户表格的固定顺序是：

```text
客户编号 | 姓名 | 订单编号 | 下单时间 | 订单状态 | 套餐
```

客户编号是第一识别字段，姓名只作辅助确认。`orderTime` 由主系统确定性生成，成交时间非空时取 `dealTime`，否则取 `createTime`，不由模型或前端重新选择。

### 9.2 图表完整性和告警

- `METRIC_RESULT` 只有在服务端已返回非空 `data.breakdown`，且外层/`data` 没有 `truncated=true` 或完整性告警时，才提供摘要、表格和柱状图；单值指标、空 breakdown 或不完整结果只提供摘要。
- 未知卡片的 LLM 建议只有在数据路径、维度、数值指标和完整性校验通过后才能生成图表；柱状图/折线图最多 50 个类别，饼图最多 8 个类别，饼图超限时先转柱状图，仍超限则降级为表格或摘要。
- Agent 不从分页或截断明细重新分组、求和或计算占比。前端收到 `partial=true`、卡片或其 `data` 标记截断、或影响完整性的 `warnings` 时隐藏图表，保留表格/摘要和原业务告警。
- 业务 `partial` 只反映工具失败、截断或业务数据不完整；展示规划失败产生的 `PRESENTATION_RULE_MISSING`、`PRESENTATION_FALLBACK_APPLIED` 等告警会返回，但不会把可用业务事实改成查询失败。
- 描述路径、关联 ID、视图或字段非法时，前端只移除无效视图；所有视图都不可用时显示“展示格式暂不可用”，仍保留 `assistantMessage`、`cards`、工具追踪和业务告警。图表初始化失败同样回退到表格或摘要。

### 9.3 未知卡片的 LLM 规划与安全降级

未登记 `cardType` 才进入独立展示规划器。规划器只接收 cardType、字段名称/类型、受控数据路径、截断和完整性状态，不接收业务值，不提供工具调用能力，也不能生成计算表达式、代码或前端配置。建议必须经过后端白名单、路径、字段类型、敏感字段、标签长度和数量限制校验。

规划器不可用、超时、返回非法建议或校验失败时，当前卡片使用 `SYSTEM` 通用降级：安全数组生成有限表格，安全对象生成键值摘要，无法安全识别时显示“展示格式暂不可用”，并增加稳定告警。该失败只影响当前卡片，不丢弃自然语言答案、业务卡片、其他卡片或原工具告警。已知卡片不会因未知卡片失败而改走 LLM。

## 10. 客户身份、会话兼容与安全边界

在已认证、具备入口权限和对应业务权限、并完成客户数据范围过滤的内部 Agent 查询链路中，客户结果使用 `customerCode + customerName`；`customerCode` 始终是主标识，完整姓名只作辅助确认。最终回答若引用完整姓名，必须同时引用同一事实中的客户编号。普通客户管理页面、普通客户 API 和非 Agent DTO 不因本链路改变姓名策略。

新响应和新会话快照保存 `cards + presentations`，并与 warnings、工具摘要和查询时间一起写入 `business_result_json`；恢复时直接使用原展示决策，不重新查业务、不重新调用 LLM、不重新补全姓名。旧 cards-only 快照由前端对已知卡片使用只读固定映射，未知卡片使用安全键值摘要；旧快照中的 `maskedName` 保持原值，不回填为新的完整姓名。

对外 Agent 结果、结构化卡片、展示描述、前端和日志均不得出现原始/完整手机号、地址、金额、价格、Token、权限集合、SQL 或内部关联 ID。内部 ID 仅在主系统关系校验和 Agent 工具间关联阶段作为不透明键使用，离开该阶段前移除；展示描述只保留安全字段路径。日志只记录 requestId、工具/卡片类型、数量、状态、稳定告警码和耗时，不记录姓名、业务值或模型原文。

## 11. 发布、观测与回滚检查

### 发布顺序

1. 先发布主系统的内部事实契约、Agent 响应透传和会话快照兼容；新增字段均为可选，不改数据库表结构。
2. 再发布 Agent 服务的系统展示注册表、完整性校验和未知卡片安全降级；确认 OpenAPI v2 契约测试及 11 类卡片覆盖通过。
3. 最后发布前端固定表格/摘要/图表组件和历史只读兼容层；确认客户编号列顺序、旧 `maskedName` 显示和图表回退均通过。

### 上线后观测

- 系统规则覆盖数量和健康告警；生产正常情况下不应出现缺少已知规则。
- `PRESENTATION_FALLBACK_APPLIED`、未知 cardType、展示规划耗时和 Agent 总响应耗时。
- 图表初始化/切换失败、截断结果隐藏图表的次数，以及表格/摘要回退是否可用。
- 观测数据只保留 requestId、工具/卡片类型、数量、状态、告警和耗时，不采集业务值、姓名、手机号、地址、金额或模型原文。

### 回滚检查

- 前端异常时先回滚前端展示组件，保留安全摘要和原有 `cards`；不得恢复原始 JSON 整体展示。
- Agent 服务异常时可停用 `presentation` 模型 profile，使未知卡片直接使用通用安全降级；系统已知规则继续生效。
- 主系统最后回滚；旧代码会忽略 `presentations` 和快照中的新增键，现有 cards、告警和会话版本不需要数据回填或 DDL 回滚。
- 回滚后仍检查客户编号优先、完整姓名受控、`orderTime` 回退和敏感数据护栏；不以回滚为由放宽手机号、地址、金额、Token、权限、SQL 或内部 ID 边界。
