# 客户管理

## 业务定位

客户管理是系统的前台业务入口，管理客户档案、地址、签约套餐、孕周信息等。一个客户档案对应一个活客户，客户档案关联多笔订单（增购时新建订单）。客户管理是连接套餐管理、配菜管理、核销管理的枢纽模块。

---

## 核心概念

### 客户档案（customer_profile）

主档，记录客户基本信息。每个客户有唯一编号（`customer_code`），支持手动输入或系统自动分配。编号格式：`{poolPrefix}{序号}`，如 `A11001`、`A11002`。

档案字段分为两类：
- **固定字段**：姓名、手机号、孕周、过敏标签、普通特殊要求、医嘱、想吃对象、禁忌对象、来源原文、术后信息、排除菜品、排除日期
- **计算字段**（非数据库存储，查询时实时计算）：剩余早餐数、剩余午餐晚餐数

### 套餐分类（customer_package_category）

与套餐管理模块（`parent_package`）是**两套独立的分类体系**，设计目的不同：

| 维度 | 模块 | 表 | 用途 |
|------|------|-----|------|
| 套餐分类 | 客户档案页 | `customer_package_category` | 客户档案页联动选择，父子两级树形结构 |
| 父子套餐 | 套餐管理 | `parent_package` / `sub_package` | 订单核心，决定餐数规格和编号池 |

`customer_package_category` 在客户档案页用于选择"月子餐 → 两荤一素"这样的分类路径，最终通过该分类关联到具体父套餐生成客户编号。`parent_package` 是底层商品配置，包含编号池、菜品线等运营数据。

### 地址管理

每个客户支持三个地址槽位：

| 地址类型 | code | 用途 |
|---------|------|------|
| 默认地址 | `DEFAULT` | 主要送餐地址 |
| 工作日地址 | `WORKDAY` | 工作日送餐地址 |
| 周末地址 | `WEEKEND` | 周末送餐地址 |

业务规则：三个槽位中**至少有一个非空**。地址随客户档案一并创建/编辑，整体覆盖。

### 过敏标签（allergy_tags）

JSON 数组格式，存储客户的过敏食物列表，如 `["牛奶", "海鲜"]`。在配菜管理中用于过滤/替换菜品。

### 订单列表维护客户共享字段

过敏标签、特殊要求、手机号、菜品特殊要求对象和客户禁忌对象属于 `customer_profile`，可在订单列表中通过受限行内入口修改；饮食对象仅编辑结构化引用，导入原文保持只读。已有的默认、工作日、周末地址也可逐条修改详细地址。请求要求订单处于进行中或暂停状态，且操作人有 `customerOrder:edit` 权限；更新后同客户的订单行均从客户档案及地址表读取最新值。手机号沿用大陆手机号格式校验；地址不能为空或超过 200 字符，新增地址槽位仍在客户档案编辑表单完成。

这类修改通过订单行内 PATCH 的旧值校验和事务审计执行。手机号等档案字段的审计快照记录在 `customer_profile:{id}` 下；地址详细信息记录在 `customer_profile_address:{id}` 下，均不复制到订单表。客户饮食字典只读选项接口也允许 `customerOrder:edit` 读取，不扩大字典写权限。客户档案编辑表单仍按本节客户档案编辑流程处理基本资料和地址。

菜品特殊要求与客户禁忌也是客户共享信息，分别保存五类菜品/配料字典对象引用及导入来源原文块。订单列表的结构化对象可行内增删，导入来源原文只读；新增引用必须属于当前有效字典，原有停用或删除引用可以保留或移除，服务端保留其名称快照。同客户的订单列表、订单详情、客户详情和排餐计划从客户档案读取当前值；它们不复制到订单或排餐表，也不参与当前排餐筛选。排餐计划只展示医嘱、菜品特殊要求、禁忌食物，顺序固定。

### 排除菜品（excluded_dish_ids）

JSON 数组格式，存储客户明确要求不要在餐单中出现的菜品ID列表。在排餐时被标记为过敏过滤菜品。

### 排除日期（excluded_dates）

JSON 数组格式，支持按日期+餐次排除配送。格式：
```json
[
  {"date": "2026-04-15", "mealTypes": ["LUNCH", "DINNER"]},
  {"date": "2026-04-20", "mealTypes": ["DINNER"]}
]
```

`excluded_dates` 是客户统一停餐规则，由客户档案维护。订单排餐日历读取并优先应用该规则，但不能在订单页新增、修改或移除它。

- 客户统一停餐对该客户的所有订单生效；客户档案解除后，各订单自己的数量覆盖重新生效。
- 单笔订单的停餐和份数调整保存在 `customer_meal_schedule_addition`：`quantity=0` 只停用当前订单的日期餐次，恢复默认时移除该订单该格覆盖。
- 订单日历的保存按 `order_id + 当前月份` 限定，不会影响同客户其他订单、其他月份或本字段。
- 已核销份不可由订单日历移除；统一停餐格只读，须到客户档案解除。

## 数据模型

### customer_profile — 客户主档

| 字段 | 类型 | 说明 |
|------|------|------|
| `customer_code` | VARCHAR | 客户编号，唯一，由系统自动生成 |
| `customer_name` | VARCHAR | 客户姓名 |
| `phone` | VARCHAR | 电话列中的客户手机号 |
| `delivery_phone_info` | TEXT | 地址列电话标签中的配送电话原文，可保留多条号码，与客户手机号独立 |
| `gestational_week` | INT | 孕周（正整数） |
| `allergy_tags` | JSON Array | 过敏食物标签 |
| `excluded_dish_ids` | JSON Array | 排除菜品ID列表 |
| `excluded_dates` | JSON Array | 排除日期列表（带餐次） |
| `medical_requirements` | TEXT | 医嘱要求（如"少盐少油"） |
| `special_requirements` | TEXT | 特殊要求 |
| `dish_requirements` | JSON Array | 已确认的想吃对象：菜品、配料、配料标签、配料二级分类或菜品标签；以类型和ID确定对象，名称保存为导入时快照 |
| `dietary_restrictions` | JSON Array | 已确认的禁忌对象，类型与ID规则同 `dish_requirements` |
| `dish_requirements_raw` | JSON Array | 想吃来源原文块，保留单元格内容、标点和换行，只读 |
| `dietary_restrictions_raw` | JSON Array | 禁忌来源原文块，保留单元格内容、标点和换行，只读 |
| `postoperative_info` | VARCHAR(255) | 术后情况原文，例如“5天”“4个月”；不按日期解析或递增 |
| `remark` | TEXT | 备注 |

### customer_profile_address — 客户地址

| 字段 | 类型 | 说明 |
|------|------|------|
| `customer_id` | BIGINT | 客户档案ID |
| `address_type` | VARCHAR | 地址类型：DEFAULT / WORKDAY / WEEKEND |
| `address_detail` | VARCHAR | 详细地址 |
| `contact_name` | VARCHAR | 联系人姓名 |
| `contact_phone` | VARCHAR | 联系人电话 |

### customer_profile_package — 签约记录

客户档案与父套餐的签约关联表（区别于 `customer_order` 的订单记录）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `customer_id` | BIGINT | 客户档案ID |
| `parent_package_id` | BIGINT | 父套餐ID |
| `start_date` | DATE | 签约开始日期 |
| `end_date` | DATE | 签约结束日期 |

### customer_package_category — 套餐分类

| 字段 | 类型 | 说明 |
|------|------|------|
| `category_name` | VARCHAR | 分类名称 |
| `category_code` | VARCHAR | 分类编码，全局唯一 |
| `parent_id` | BIGINT | 父级分类ID（顶级为 NULL） |
| `level` | INT | 层级：1=父级，2=子级 |
| `sort` | INT | 排序值 |
| `enabled` | BOOLEAN | 是否启用 |
| `code_prefix` | VARCHAR | 编号前缀（仅父级使用，单个大写字母） |

## 核心业务流程

### 1. 创建客户（销售录入）

```
POST /api/customerProfile
{
  "customerName": "张三",
  "phone": "138xxxx",
  "gestationalWeek": 32,
  "allergyTags": ["牛奶"],
  "excludedDishIds": [1, 5, 12],
  "excludeDates": [{"date": "2026-04-15", "mealTypes": ["LUNCH"]}],
  "medicalRequirements": "少盐少油",
  "specialRequirements": "米饭加量",
  "addresses": [{ "addressType": "DEFAULT", "addressDetail": "北京市..." }],
  "orderInfo": {
    "parentPackageId": 1,
    "childPackageId": 3,
    "breakfastCount": 10,
    "lunchDinnerCount": 20,
    "startDate": "2026-04-01",
    "startMealType": "DINNER",
    "endDate": "2026-06-30",
    "mainDishCount": 2,
    "sideDishCount": 1,
    "vegCount": 1,
    "riceCount": 1,
    "soupCount": 1
  }
}
```

**后端自动执行以下步骤：**

1. **参数校验**
   - 客户姓名、手机号（非空、格式校验）、地址（非空、类型校验）
   - 首单信息校验（父套餐存在且启用、餐数非负；`startMealType` 与 `mealType` 兼容；主菜/副菜/素菜/汤数量不能为负数；米饭数量不能为负数且不能超过10）
   - 排除日期格式校验

2. **生成客户编号**
   - 优先使用前端传入的手动编号（需校验前缀、数字部分、范围、唯一性；数字部分不限制固定位数）
   - 无手动编号时调用编号池服务自动分配（`poolPrefix + 序号`）
   - 编号池支持并发，使用 `SELECT FOR UPDATE` 保证唯一性

3. **创建客户档案**
   - 写入 `customer_profile` 表

4. **创建地址记录**
   - 批量写入 `customer_profile_address` 表

5. **创建首笔订单**
   - 自动生成订单编号 `ORD{yyyyMMdd}{NNN}`
   - 状态默认为"进行中"（status=1）
   - 写入 `customer_order` 表
   - 若当前账号无 `customerOrder:amount:edit` 权限，首单金额、单价字段由后端统一按 `0` 处理

### 1.1 试餐客户简化建档

当新增客户选择的父套餐名称包含 `试餐` 时，允许走简化建档：

```json
POST /api/customerProfile
{
  "phone": "13800000000",
  "orderInfo": {
    "parentPackageId": 1
  }
}
```

**试餐判定口径**

- 根据 `orderInfo.parentPackageId` 查询 `parent_package`
- `parent_package.package_name` 包含 `试餐` 即视为试餐套餐

**试餐简化建档默认值**

- `customerName` 自动补为 `试餐客户` + 手机号后 4 位
- 地址仍按普通建档规则校验，至少需要一个有效地址
- 首单默认创建 `0` 份早餐 + `1` 份午晚餐，`totalCount = 1`
- 金额字段默认 `0`
- `scheduleMode = SCHEDULE`
- `startDate = 服务端当天`
- `startMealType = LUNCH`
- `mealType = LUNCH_DINNER`
- 菜品配置默认 `mainDishCount=0`、`sideDishCount=0`、`vegCount=0`、`riceCount=1`、`riceType=白米饭`、`soupCount=0`
- `trialConverted = false`，`trialOrderId = null`

**仍然保留的校验**

- 手机号必填且必须满足大陆手机号格式
- 父套餐必须存在且启用
- 客户编号仍按父套餐编号池或顺序兜底规则生成
- 若前端额外提交地址、过敏、排除菜品、排除日期等字段，仍按普通建档的字段合法性校验

**编号生成机制**：

| 模式 | 说明 |
|------|------|
| 手动编号 | 前端传入，需校验：① 以 `poolPrefix` 开头 ② 前缀后为纯数字 ③ 数字值在 `[poolStart, poolEnd]` 范围内 ④ 唯一。数字部分不限制固定位数 |
| 自动编号 | 调用编号池服务，根据 `poolPrefix`、`poolStart`、`poolEnd` 分配下一个可用号 |

### 2. 编辑客户档案

客户档案编辑表单仅修改客户基本资料 + 地址。**不操作套餐/订单**，不走套餐变更流程。订单列表的过敏标签、特殊要求和饮食对象行内编辑是独立的受限入口，按上文客户共享字段规则写入档案。

### 3. 批量删除客户

仅允许删除**无未完订单**的客户：
- 检查 `customer_order` 表 `status=1`（进行中）和 `status=4`（暂停）的记录
- 有进行中或暂停订单 → 拒绝删除，返回被拦截的客户姓名
- 已取消、已完成或已退餐订单不影响删除

级联删除：`customer_profile_address`（地址）、`customer_profile_package`（签约记录）。**不删除** `customer_order`（订单独立管理）。

### 4. 剩余餐数计算

不存储在数据库，查询时实时计算，**汇总该客户所有未完有效订单**（`status IN (1,4)` 且 `remaining_count > 0`）：

```
总早餐数 = Σ 所有有效订单的 breakfast_count
总午晚餐数 = Σ 所有有效订单的 lunch_dinner_count
总已核销早餐 = Σ 各订单已核销的 BREAKFAST 数
总已核销午晚餐 = Σ 各订单已核销的 LUNCH 数 + DINNER 数

剩余早餐数 = max(0, 总早餐数 - 总已核销早餐)
剩余午晚数 = max(0, 总午晚餐数 - 总已核销午晚餐)
```

数据来源：
- 订单表：`customer_order` 的 `breakfast_count`、`lunch_dinner_count`
- 核销记录：`meal_verification_log` 按 `order_id` + `meal_type` 分组统计（排除已退餐的记录）

### 5. 客户用餐统计页展示口径

客户用餐统计页按订单分页，一笔订单返回一行。同一客户的多笔订单分别展示；同一订单同时购买早餐和午晚餐时仍只显示一行。

**按月查询口径：**

- 页面按月份查询，参数格式为 `yyyy-MM`
- 普通剩余订单仍须满足 `status IN (1,4)` 且 `remaining_count > 0`，例如选择 `2026-04` 时要求 `start_date < 2026-05-01`
- 另纳入所选月份存在有效历史导入数量的订单：`customer_meal_schedule_addition` 未删除且来源为“客户用餐计划表历史导入”，记录日期在该月内；这类订单不受开始日期、状态或剩余餐数限制，已完成、已退餐等订单仍可查看历史日历
- 例如 `2026-10-01` 导入 9 月数据，首单开始日期取成单日期，例如 `2026-06-02`，未来排餐下界仍是 `2026-10-02`，切换到 `2026-09` 时仍显示有 9 月历史记录的订单；历史格只读
- 未指定月份时，剩余订单和具有任意月份有效历史导入记录的订单均可查询；客户编号、姓名、手机号同时筛选两种路径，同订单多个历史格不会重复返回订单行
- 不按订单结束时间过滤
- 订单分页在数据库执行，`totalElements` 表示符合筛选条件的订单数；分页后批量读取当前页客户资料、地址、已排餐和今日未核销统计

**字段顺序与来源：**

- 依次展示手机号、地址、客户编号、客户姓名、特殊要求、排餐模式、餐次、规格、含汤、早餐、午晚、合计、核销、已排餐、剩余、预计剩余、状态、基本情况、成单时间、术后天数、菜品特殊要求、过敏食物、禁忌食物、自定义菜单和操作
- 客户共享字段从 `customer_profile` 读取当前值；客户编号、排餐配置、餐数、状态、成单时间和自定义菜单从当前 `customer_order` 读取
- “特殊要求”只显示 `special_requirements`；“基本情况”显示 `medical_requirements`；“术后天数”保留 `postoperative_info` 原文，不推算天数
- 菜品特殊要求及禁忌复用结构化对象和完整来源原文；过敏食物单独展示标签
- “餐次”按当前订单购买餐池展示中文；`ALL` 根据早餐数和午晚餐数显示其实际覆盖，不显示枚举代码
- 规格显示主菜、副菜、素菜数量；含汤由当前订单 `soup_count >= 1` 判断

**数量展示说明：**

- `核销` 直接展示当前订单 `verified_count`，其值已包含导入历史基数，不再额外相加
- `已排餐` 是当前订单全部有效结果行数，包含成功和失败、不论是否核销，不是计划格数
- `剩余` 使用当前订单 `remaining_count`
- `预计剩余 = max(remaining_count - 今日成功且未核销的排餐份数, 0)`；今日按服务端业务日期，与筛选月份无关
- 页面滚动懒加载，首批 20 条；筛选变化时重置并重新加载第一页
- 地址优先使用 `DEFAULT`，没有时依次使用 `WORKDAY`、`WEEKEND`，展示联系人、电话和地址多行内容


### 6. 客户话术解析建档

客服可在新增客户弹窗中粘贴客户沟通文本，先调用解析预览接口生成“客户档案 + 首单”草稿，再由客服确认并继续走现有新增客户接口保存。

**解析链路：**

1. 前端调用 `POST /api/customerProfile/intake/parse`
2. 后端按规则解析文本，返回 `CustomerProfileSaveDto` 兼容草稿
3. 客服应用草稿后，可继续在表单中手工调整
4. 最终仍调用 `POST /api/customerProfile` 创建客户和首单

### 首单金额权限控制

- 新增客户页首单金额展示受 `customerOrder:amount:view` 控制。
- 新增客户页首单金额录入受 `customerOrder:amount:edit` 控制。
- 文本解析草稿即使识别出金额，无金额查看权限时前端也不会展示这些字段。
- 无金额编辑权限时，后端仍会创建首单，但金额相关字段统一落为 `0`。

**关键规则：**

- 解析服务只生成草稿，不直接写入客户、地址、订单数据。
- 未传开始日期时，默认使用解析当天作为 `orderInfo.startDate`。
- 未传排餐模式时，默认 `orderInfo.scheduleMode = SCHEDULE`，`deliveryDates = null`。
- 未传米饭类型时默认 `普通杂粮米饭`；若“不能吃的/特殊要求”中明确提到“糙米”，则优先回填 `糙米`。
- `来源/客户来源/销售渠道` 会忽略括号或方括号内的候选提示，按括号外真实选择匹配渠道。例如 `来源：（小红书or抖音or推荐）抖音个人搜索` 识别为 `抖音`；`来源：（小红书·抖音·推荐）` 因无真实选择默认 `其他`。
- `套餐/父套餐` 优先按系统父套餐名称或编码映射 `orderInfo.parentPackageId`；若未填写或未匹配成功，可从 `餐别` 按分隔符拆出的完整片段中兜底匹配已启用父套餐名称或编码，例如 `餐别：小月子餐、两荤一素一汤` 可匹配父套餐 `小月子餐`，不会误匹配内部的 `月子餐`。
- `餐别：孕期营养餐不含汤（两荤一素）` 这类未命中系统父套餐的模糊描述仍仅作参考，不能替代套餐字段。
- `菜品配置` 推荐使用 `2主1副1素0汤` 这类规范格式，解析后回填主菜、副菜、素菜、汤数。
- 当解析出的父套餐名称包含 `试餐` 时，按试餐简化建档规则生成草稿：联系人可为空，系统自动补 `试餐客户` + 手机号后 4 位；未写餐数时默认 1 次午晚餐；未写菜品配置时主菜、副菜、素菜、汤默认 0；米饭类型默认 `白米饭`。
- `不能吃的` 整段进入 `specialRequirements`，不会强制拆成过敏标签或排除菜品；整段为 `无`、`没有`、`暂无` 等空值表达时忽略。
- `过敏食物` 会按逗号拆分回填 `allergyTags`；整段为 `无`、`没有`、`无过敏` 等空值表达时回填空数组。
- `排除菜品` 仅提示客服确认，不直接匹配菜品 ID。

**阻塞保存的问题：**

- 联系人为空（试餐套餐除外，系统会自动补默认姓名）。
- 电话为空或手机号格式不正确。
- 地址为空。
- 套餐为空，或没有匹配到系统父套餐。
- 普通套餐餐数为空或小于等于 0。
- 普通套餐菜品配置未解析成功，导致主菜、副菜、素菜数量仍全部为 0。

### 7. 客户自助资料登记 PoC

客户可通过客服手动发送的 H5 链接提交最小资料，用于验证公网链路和日志接收能力。当前实现不是正式客户建档流程：

- H5 只采集姓名、手机号、地址和备注。
- 后端接口为 `POST /api/public/customer-intake`，无需登录，默认由 `CUSTOMER_SELF_INTAKE_ENABLED=false` 关闭。
- 接口仅生成 `requestId` 并将四个字段写入应用日志，不调用客户建档、订单创建、话术解析或任何持久化组件。
- 接口不创建 `customer_profile`、`customer_profile_address`、`customer_profile_package` 或 `customer_order` 数据，也不提供查询、修改和后台审核能力。
- 日志中的换行、回车和其他控制字符会被替换为空格，避免日志跨行污染；但日志本身会落盘，因此公网 IP + HTTP 联调阶段只能使用虚拟测试资料。
- 正式采集真实客户资料前，必须另行确认域名与 HTTPS、身份校验或限流、脱敏、日志留存周期和正式存储方案，完成后再设计正式建档入口。

接口字段和响应详见 `doc/apidoc/客户自助资料登记接口文档.md`。

### 8. 客户与订单 Excel 月度导入

业务现场用「客户用餐计划表」逐位建档过慢，改为上传工作簿后先预览逐行转换结果与错误，操作人核对套餐编号池、日期、备份后确认提交。预览接口只读；确认接口按客户独立事务首次建档或续导原订单，保存历史逐餐数量和未来逐餐数量计划。完整导入可按月连续确认，来源月份最大者决定餐数与余额。

**使用方式：**

1. 在客户档案页上传「客户用餐计划表」工作簿（`.xlsx`）。
2. 系统读取名称形如 `26年9月` 的月份工作表，以及名称为 `客户禁忌` 的可选第二工作表；WPS 保留页跳过。缺少第二工作表时，原客户与首单导入仍可使用。
3. 返回逐位客户的转换草稿：有效编号、父套餐、送餐模式与餐次、来源午晚餐数、目标订单、当前采用月份、处理类型、餐数与余额前后值、日格差异、历史和未来数量、规格及冲突原因。
4. 操作人核对文件摘要、导入日期、套餐编号池和业务备份，再明确确认提交；提交时服务端重读文件并复核文件、字典与订单状态摘要；核销或订单发生变化时重新预览。每次确认处理预览显示的一个月份，9月、10月分别预览和确认。
5. 页面按客户显示新建、幂等跳过、资料错误和事务失败原因，并可下载不含完整手机号或地址的异常清单。

月份页已经导入后，可选择默认的「仅导入客户禁忌（第二页）」模式。该模式只校验并预览名称为 `客户禁忌` 的工作表，按 B 列非空优先、否则 A 列的编号查找数据库已有客户；月份页即使存在也只读取名称用于 G 列月日补年，不读取月份页客户、餐数或地址。未找到的编号在预览中逐行报错、标红并跳过，页面同时提示未找到的客户数量；确认时只补录已有客户的医嘱、饮食原文及引用、术后信息，不创建客户、地址或订单，也不改历史成交时间。没有月份页时，G 列月日用导入日期的年份补齐。切换导入模式后须重新预览。

**输入列与转换规则：**

| 列 | 含义 | 转换规则 |
|---|---|---|
| A / B | 原编号 / 新编号 | B 非空取 B，否则取 A 作为有效编号；有效编号同时作为客户姓名与地址联系人名 |
| C | 电话 | 只做分隔符与空白规范化；仍不合规的整位客户跳过并报告 |
| D | 地址 | 至少一个可用送餐地址；解析默认 / 工作日 / 周末槽位；电话标签中的多条配送电话完整写入客户主档 `delivery_phone_info`，地址单值联系电话取首条可用号码 |
| E / F | 备注信息 / 特殊要求 | 分别写入客户备注与特殊要求；任一列含「等通知」则该客户订单记为暂停 |
| F / G | 规格 / 含汤 | 含「无副菜」→ 主菜 1、副菜 0、素菜 1，否则 1/1/1；`含汤` → 汤数 1，`不含汤` → 汤数 0；米饭固定一份白米饭 |
| H | 送餐描述 | 含「等通知」→ 订单暂停、送餐模式 SCHEDULE、餐次留空；否则按「工作日 / 周末 / 每日」确定模式，按「午餐 / 晚餐」确定餐次；送餐描述缺失时默认按「午餐+晚餐」处理 |
| I / J | 餐数 / 剩余餐数 | 逐行核对公式；午晚餐购买数取午晚餐明细行 I 列合计，早餐行不计入。导入后可用餐数 = J 列合计 + 导入日期之后非零午晚餐格之和 |

**第二工作表「客户禁忌」固定列**：A 为旧编号、B 为新编号、C 不导入、D 为客户想吃内容、E 为医嘱（模板表头为「基本情况描述」）、F 为客户不能吃内容、G 为订单成交时间、H 为术后原文。B 非空时只按 B 关联本次导入客户；B 为空时使用 A，B 无匹配时不回退 A。列位置与表头结构会校验，标题和说明行不当作客户记录。

- E 列原文写入既有 `medical_requirements`，不做词典匹配。空值不覆盖；同一客户多行医嘱相同则合并，不同则阻止该客户提交并要求核对；已有客户的空医嘱可补齐，相同值幂等，不同值不覆盖。
- D 列菜品特殊需求只保存完整原文到 `dish_requirements_raw`，保留标点、空白和换行，不拆词、不匹配字典、不自动生成想吃对象。完整月份导入和仅第二页导入均遵循此规则；原文块按完整内容去重，已有客户的想吃对象保留。
- F 列固定表示禁忌；句子里出现“不吃”或“喜欢吃”不会改变方向。先尝试整段精确匹配，再按分隔符拆词并尝试有限表达前缀。单一命中自动关联，同名多候选全部关联；未匹配文本保留完整原文。图片跳过，不做 OCR。
- F 列未整词命中时使用 HanLP 1.x Portable 中文分词，内置基础词库与本次有效业务名称词典共同识别食物边界。例如 `过敏食物：芒果菠萝` 可分别查找芒果、菠萝；只有系统中存在的名称才关联对象，连续未识别片段仍在预览提示，完整原文始终保留。完整字典名称优先，不拆成更短名称；每次导入独立构建领域词典，不修改全局词典。
- 预览的医嘱与饮食匹配列默认显示单行医嘱、菜品特殊需求原文、禁忌匹配数量和禁忌名称摘要，长内容省略并可悬停查看。点击「查看明细」在可滚动浮层中核对完整医嘱、成交时间、术后信息、菜品特殊需求/禁忌原文、禁忌逐词来源行及全部候选对象，避免匹配项数量撑高表格行。
- 支持菜品、配料、配料标签、配料二级分类和菜品标签。名称重复时展示所有类型/ID候选；本次不使用同义词、模糊匹配或医疗语义推断。
- G 列写入新建订单的 `deal_time`，同时以其日期作为订单 `start_date`；Excel 日期单元格按日期读取，`6.11` 等月日按月份工作表年份补齐，纯日期取当天 `00:00:00`。空值在确认请求开始时统一取当前时间；非空无法解析或同一客户多行成交时间冲突时，该客户阻止提交。补录已有客户不会修改历史订单成交时间。
- H 列保存为 `postoperative_info` 字符串，不转换为日期；H 为空不清空已有信息，多行不同非空值或与已有客户不一致时提示冲突并阻止该客户补录。
- 已有客户须编号和手机号一致；饮食共享资料仍只补空缺并合并原文/对象，既有地址不由续导覆盖。完整导入按父套餐和原成单日期定位唯一导入订单并续导；仅第二页模式不修改餐数或既有订单。订单先锁、客户后锁，提交时复核身份与订单状态。重复上传时结构化对象和原文块均去重。
- D/F 原文分别保存；即使两列包含相同字典名称，只有 F 列自动生成禁忌对象，本次不做排餐冲突裁决。原文与已有对象引用均为客户共享信息。

「合计餐数」单元格为空时按 0 读取，不因空值向页面报告问题；有实际取值时继续与逐日日格交叉核对。

**编号与套餐：**

- 同编号、同电话、同地址的续行合并为一位客户；同编号出现不同电话或地址时整位拒绝，不在导入器内生成后缀编号。
- 编号按启用父套餐的编号池归属：以编号池前缀开头、数字部分落在池区间内，且在启用父套餐中唯一命中；套餐名称不参与匹配，编号池配置以套餐管理为准。
- 必须匹配到**唯一的已启用父套餐**；落在多个池或不落在任何启用编号池时逐行报错，提示文案附套餐名称与池区间仅用于定位。
- 批量导入不匹配或校验子套餐；首单不填写子套餐，排餐配置使用订单上的菜品规格。

**餐数与暂停：**

- 早餐本次不导入；纯早餐行跳过并给出原因。
- 导入日期及之前的午晚餐视为历史已核销：`imported_verified_count = 午晚餐购买数 - 导入后可用餐数`。订单 `verified_count` 以此为初值，`remaining_count` 为导入后可用餐数；历史基数不生成系统内逐餐核销日志。工作簿中导入日期及之前的非零午晚餐格同时按日期、餐次、份数保存到 `customer_meal_schedule_addition`，来源备注为“客户用餐计划表历史导入”；数量日历标为“历史导入（只读）”，不伪造已生成或逐餐核销事实，不参与未来可用餐池和排餐。订单 `start_date` 取成交时间的日期，单独记录 `import_date`；未来排餐从 `max(start_date, import_date + 1日)` 承接，避免成单日至导入日之间缺少历史格时占用未来余额；保存未来覆盖时保留历史记录。完整导入支持原订单月度续导及历史补录；仅第二页仍只补资料。
- 「剩余餐数」为 0 的午晚餐客户仍可建档。来源午晚餐购买数也为 0 时只创建客户档案和地址；购买数大于 0 且没有未来可用餐数时，创建历史已核销的已完成首单。成功提交后在后端记录零来源剩余餐数，不向页面返回额外提示。
- 电话列与地址列的号码可以不同：前者写入客户手机号，后者的多条电话原文写入 `delivery_phone_info`；不因两列不一致而提示。编辑客户时该字段可查看、修改，旧调用方省略字段则保持原值。
- 部署此导入字段前，先执行 `eladmin/sql/20260925_customer_profile_delivery_phone_info.sql`，为现有客户主档新增可空列。
- 部署饮食导入前，备份 `customer_profile.production_date` 的旧值并按主键保留记录身份，然后执行 `eladmin/sql/20260928_customer_diet_items.sql`。迁移将旧日期原样转成文本写入 `postoperative_info` 供人工核对，不推算术后天数；不在本功能中直接执行迁移。
- H 送餐描述含「等通知」时，不论是否同时写有午餐或晚餐，订单均创建为暂停、送餐模式为 `SCHEDULE`、餐次留空；同一客户多行中任一行命中亦如此。E/F 含「等通知」时也创建为暂停。
- H 送餐描述缺失（空白）时不再阻塞，默认餐次按「午餐+晚餐」处理，并在预览中给出提示；送餐模式留空，排餐按每日送处理。
- 暂停订单仍占用编号池、计入客户用餐统计并保留余额和日期计划，但不能自动/人工排餐或核销，可按剩余餐数退餐；恢复时未指定餐次的订单必须先由操作人确认餐次。
- 零金额和零单价是本次导入的合法值；导入后的未来每一份仍须单独核销并扣减一餐。
- 现有订单表部署前须执行 `eladmin/sql/20260925_customer_order_imported_verified_count.sql`；旧订单该字段默认为 0。
- 部署成单日期作为订单开始日的调整前，执行 `eladmin/sql/20261001_customer_order_import_date.sql` 新增可空 `import_date`。该字段由首单与被采用的月度快照维护；普通订单为空，既有订单开始日期不自动改写。
- 未来同一餐次份数为 2 时，只有「特殊要求」给出与有效编号一致的「编号-2含汤」且「含汤」列为 `不含汤` 才认定第二份含汤；无法确定的多份描述逐行报错，**不按客户编号写特例**。历史多份格原样保存数量；只在规则能明确第二份含汤时保存含汤份数，否则沿用订单配置，不阻止历史数量导入。

**跨月续导与月份优先级：**

- 来源月份取预览显示的年月；订单 `import_month` 保存当前餐数快照的来源月份（月首日），`import_date` 保存其历史/未来截止日。不能用确认时间代替来源月份，空日历月份也必须保存来源月份。
- 新月份更新原订单，餐数取该表午晚餐 I 列之和；可用餐数 `R=J列之和+该表导入日之后的未来份数`。例如 J=20、未来5份，R=25。各月份餐数不累加，原订单ID、成单时间及开始日期不改变。
- 旧月份只补录/修正对应月份的数量记录，不更新最新餐数、余额、核销基数、采用月份或日级边界；同月同日期同内容重复确认不重复记录、累计或扣减餐数。同月修订按本次确认文件更新，日期边界不允许回退。
- 来源累计消费 `V表=T-(J+未来)`；表期内真实核销S内已经包含在来源消费里，历史基数 `H=V表-S内`。表期以外的真实核销S外仍保留扣减，最终余额 `J+未来-S外`，不能因重传返还；负基数或负余额提示冲突，不改写核销日志。
- 仅维护本订单、本来源月份的导入记录，不夺取人工来源数量；移除或调低份数不能侵害已核销份。超额未核销结果复用日历清理能力按日期餐次限定删除，其他月份和订单不清理。
- 进入历史期间的原导入未来格转为只读历史。日历保留其真实已生成、失败及核销进度；没有真实进度的历史格不生成或伪造核销日志。
- 已有档案无订单时按首单规则创建，不重复地址；来源购买数为0时只处理客户资料。普通手工订单不能按同编号自动续导；多个匹配订单、缺少日期不能唯一定位时预览标错，不猜目标订单或创建月份。已唯一定位的旧导入订单，来源月份为空时优先从有效导入日格推断；没有导入日格时允许直接导入历史文件，以首次通过现有餐数、真实核销、人工数量及状态保护校验并确认的文件建立月份基线，不要求人工回填。预览当前采用月份为空，确认后保存本表来源月份、日期边界和日格；之后继续按最大来源月份更新餐数，旧月只补数量。
- 进行中订单余额归零时完成。暂停、已取消、已退餐状态不由导入自动改变；已完成订单出现正余额时提示核对，不自动恢复。价格、金额与既有金额流水不由无金额列的工作簿覆盖。
- 部署月度续导前，在 `20261001_customer_order_import_date.sql` 已执行的基础上执行 `eladmin/sql/20261001_customer_order_import_month.sql`。两份增量脚本仅添加可空字段，不自动回填或修改业务订单。旧导入订单的空月份不阻止历史文件导入；月份基线由已有导入日格或首次通过校验并确认的文件建立，不从订单创建日期推测。

**安全与不可信输入：**

- 预览不写库，也不生成临时 Excel、排餐或核销数据。
- 有实际取值的公式缓存须与逐日格交叉核对一致；空白「合计餐数」按 0 处理，文本、负数和非整数日格仍按错误处理。
- 日志不打印完整手机号与地址；预览中的手机号按前 3 位 + `****` + 后 4 位脱敏。
- 工作簿解析、逐客户提交结果、提交汇总及导入异常写入配置日志目录下的 `customer-import.log`，按天归档并保留 30 天。
- 表头、月份与日期餐次结构不符合模板时整体拒绝，不进入逐行解析。

接口字段和响应详见 `doc/apidoc/客户档案管理接口文档.md`。
