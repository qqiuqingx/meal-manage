# 客户管理

## 业务定位

客户管理是系统的前台业务入口，管理客户档案、地址、签约套餐、孕周信息等。一个客户档案对应一个活客户，客户档案关联多笔订单（增购时新建订单）。客户管理是连接套餐管理、配菜管理、核销管理的枢纽模块。

---

## 核心概念

### 客户档案（customer_profile）

主档，记录客户基本信息。每个客户有唯一编号（`customer_code`），支持手动输入或系统自动分配。编号格式：`{poolPrefix}{序号}`，如 `A11001`、`A11002`。

档案字段分为两类：
- **固定字段**：姓名、手机号、孕周、过敏标签、医嘱要求、排除菜品、排除日期
- **计算字段**（非数据库存储，查询时实时计算）：剩余早餐数、剩余午餐晚餐数

### 套餐分类（customer_package_category）

与套餐管理模块（`parent_package`）是**两套独立的分类体系**，设计目的不同：

| 维度 | 模块 | 表 | 用途 |
|------|------|-----|------|
| 套餐分类 | 客户档案页 | `customer_package_category` | 客户档案页联动选择，父子两级树形结构 |
| 父子套餐 | 套餐管理 | `parent_package` / `sub_package` | 订单核心，决定餐数规格和编号池 |

`customer_package_category` 在客户档案页用于选择"月子餐 → 两荤一素"这样的分类路径，最终通过该分类关联到具体父套餐生成客户编号。`parent_package` 是底层商品配置，包含编号池、菜品线等运营数据。

### 地址管理

每个客户支持三个地址槽位：

| 地址类型 | code | 用途 |
|---------|------|------|
| 默认地址 | `DEFAULT` | 主要送餐地址 |
| 工作日地址 | `WORKDAY` | 工作日送餐地址 |
| 周末地址 | `WEEKEND` | 周末送餐地址 |

业务规则：三个槽位中**至少有一个非空**。地址随客户档案一并创建/编辑，整体覆盖。

### 过敏标签（allergy_tags）

JSON 数组格式，存储客户的过敏食物列表，如 `["牛奶", "海鲜"]`。在配菜管理中用于过滤/替换菜品。

### 排除菜品（excluded_dish_ids）

JSON 数组格式，存储客户明确要求不要在餐单中出现的菜品ID列表。在排餐时被标记为过敏过滤菜品。

### 排除日期（exclude_dates）

JSON 数组格式，支持按日期+餐次排除配送。格式：
```json
[
  {"date": "2026-04-15", "mealTypes": ["LUNCH", "DINNER"]},
  {"date": "2026-04-20", "mealTypes": ["DINNER"]}
]
```

客户用餐统计页的“排餐日历”保存时会直接维护该字段：

- 点击取消基础应排餐餐次时，新增对应 `date + mealTypes`。
- 点击恢复被取消餐次时，仅移除该餐次；同一天无剩余餐次时删除该日期对象。
- 保存前后端会校验已生成排餐记录：未核销记录可同步软删除；已核销记录会拒绝取消，避免核销数据与排餐日历不一致。
- 排餐日历数量为 0 时使用该排除日期；正数份数通过订单级人工数量覆盖保存，排除日期仍优先。

## 数据模型

### customer_profile — 客户主档

| 字段 | 类型 | 说明 |
|------|------|------|
| `customer_code` | VARCHAR | 客户编号，唯一，由系统自动生成 |
| `customer_name` | VARCHAR | 客户姓名 |
| `phone` | VARCHAR | 电话列中的客户手机号 |
| `delivery_phone_info` | TEXT | 地址列电话标签中的配送电话原文，可保留多条号码，与客户手机号独立 |
| `gestational_week` | INT | 孕周（正整数） |
| `allergy_tags` | JSON Array | 过敏食物标签 |
| `excluded_dish_ids` | JSON Array | 排除菜品ID列表 |
| `exclude_dates` | JSON Array | 排除日期列表（带餐次） |
| `medical_requirements` | TEXT | 医嘱要求（如"少盐少油"） |
| `special_requirements` | TEXT | 特殊要求 |
| `production_date` | DATE | 生产日期 |
| `remark` | TEXT | 备注 |

### customer_profile_address — 客户地址

| 字段 | 类型 | 说明 |
|------|------|------|
| `customer_id` | BIGINT | 客户档案ID |
| `address_type` | VARCHAR | 地址类型：DEFAULT / WORKDAY / WEEKEND |
| `address_detail` | VARCHAR | 详细地址 |
| `contact_name` | VARCHAR | 联系人姓名 |
| `contact_phone` | VARCHAR | 联系人电话 |

### customer_profile_package — 签约记录

客户档案与父套餐的签约关联表（区别于 `customer_order` 的订单记录）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `customer_id` | BIGINT | 客户档案ID |
| `parent_package_id` | BIGINT | 父套餐ID |
| `start_date` | DATE | 签约开始日期 |
| `end_date` | DATE | 签约结束日期 |

### customer_package_category — 套餐分类

| 字段 | 类型 | 说明 |
|------|------|------|
| `category_name` | VARCHAR | 分类名称 |
| `category_code` | VARCHAR | 分类编码，全局唯一 |
| `parent_id` | BIGINT | 父级分类ID（顶级为 NULL） |
| `level` | INT | 层级：1=父级，2=子级 |
| `sort` | INT | 排序值 |
| `enabled` | BOOLEAN | 是否启用 |
| `code_prefix` | VARCHAR | 编号前缀（仅父级使用，单个大写字母） |

## 核心业务流程

### 1. 创建客户（销售录入）

```
POST /api/customerProfile
{
  "customerName": "张三",
  "phone": "138xxxx",
  "gestationalWeek": 32,
  "allergyTags": ["牛奶"],
  "excludedDishIds": [1, 5, 12],
  "excludeDates": [{"date": "2026-04-15", "mealTypes": ["LUNCH"]}],
  "medicalRequirements": "少盐少油",
  "specialRequirements": "米饭加量",
  "addresses": [{ "addressType": "DEFAULT", "addressDetail": "北京市..." }],
  "orderInfo": {
    "parentPackageId": 1,
    "childPackageId": 3,
    "breakfastCount": 10,
    "lunchDinnerCount": 20,
    "startDate": "2026-04-01",
    "startMealType": "DINNER",
    "endDate": "2026-06-30",
    "mainDishCount": 2,
    "sideDishCount": 1,
    "vegCount": 1,
    "riceCount": 1,
    "soupCount": 1
  }
}
```

**后端自动执行以下步骤：**

1. **参数校验**
   - 客户姓名、手机号（非空、格式校验）、地址（非空、类型校验）
   - 首单信息校验（父套餐存在且启用、餐数非负；`startMealType` 与 `mealType` 兼容；主菜/副菜/素菜/汤数量不能为负数；米饭数量不能为负数且不能超过10）
   - 排除日期格式校验

2. **生成客户编号**
   - 优先使用前端传入的手动编号（需校验前缀、数字部分、范围、唯一性；数字部分不限制固定位数）
   - 无手动编号时调用编号池服务自动分配（`poolPrefix + 序号`）
   - 编号池支持并发，使用 `SELECT FOR UPDATE` 保证唯一性

3. **创建客户档案**
   - 写入 `customer_profile` 表

4. **创建地址记录**
   - 批量写入 `customer_profile_address` 表

5. **创建首笔订单**
   - 自动生成订单编号 `ORD{yyyyMMdd}{NNN}`
   - 状态默认为"进行中"（status=1）
   - 写入 `customer_order` 表
   - 若当前账号无 `customerOrder:amount:edit` 权限，首单金额、单价字段由后端统一按 `0` 处理

### 1.1 试餐客户简化建档

当新增客户选择的父套餐名称包含 `试餐` 时，允许走简化建档：

```json
POST /api/customerProfile
{
  "phone": "13800000000",
  "orderInfo": {
    "parentPackageId": 1
  }
}
```

**试餐判定口径**

- 根据 `orderInfo.parentPackageId` 查询 `parent_package`
- `parent_package.package_name` 包含 `试餐` 即视为试餐套餐

**试餐简化建档默认值**

- `customerName` 自动补为 `试餐客户` + 手机号后 4 位
- 地址仍按普通建档规则校验，至少需要一个有效地址
- 首单默认创建 `0` 份早餐 + `1` 份午晚餐，`totalCount = 1`
- 金额字段默认 `0`
- `scheduleMode = SCHEDULE`
- `startDate = 服务端当天`
- `startMealType = LUNCH`
- `mealType = LUNCH_DINNER`
- 菜品配置默认 `mainDishCount=0`、`sideDishCount=0`、`vegCount=0`、`riceCount=1`、`riceType=白米饭`、`soupCount=0`
- `trialConverted = false`，`trialOrderId = null`

**仍然保留的校验**

- 手机号必填且必须满足大陆手机号格式
- 父套餐必须存在且启用
- 客户编号仍按父套餐编号池或顺序兜底规则生成
- 若前端额外提交地址、过敏、排除菜品、排除日期等字段，仍按普通建档的字段合法性校验

**编号生成机制**：

| 模式 | 说明 |
|------|------|
| 手动编号 | 前端传入，需校验：① 以 `poolPrefix` 开头 ② 前缀后为纯数字 ③ 数字值在 `[poolStart, poolEnd]` 范围内 ④ 唯一。数字部分不限制固定位数 |
| 自动编号 | 调用编号池服务，根据 `poolPrefix`、`poolStart`、`poolEnd` 分配下一个可用号 |

### 2. 编辑客户档案

仅修改客户基本资料 + 地址。**不操作套餐/订单**，不走套餐变更流程。

### 3. 批量删除客户

仅允许删除**无未完订单**的客户：
- 检查 `customer_order` 表 `status=1`（进行中）和 `status=4`（暂停）的记录
- 有进行中或暂停订单 → 拒绝删除，返回被拦截的客户姓名
- 已取消、已完成或已退餐订单不影响删除

级联删除：`customer_profile_address`（地址）、`customer_profile_package`（签约记录）。**不删除** `customer_order`（订单独立管理）。

### 4. 剩余餐数计算

不存储在数据库，查询时实时计算，**汇总该客户所有未完有效订单**（`status IN (1,4)` 且 `remaining_count > 0`）：

```
总早餐数 = Σ 所有有效订单的 breakfast_count
总午晚餐数 = Σ 所有有效订单的 lunch_dinner_count
总已核销早餐 = Σ 各订单已核销的 BREAKFAST 数
总已核销午晚餐 = Σ 各订单已核销的 LUNCH 数 + DINNER 数

剩余早餐数 = max(0, 总早餐数 - 总已核销早餐)
剩余午晚数 = max(0, 总午晚餐数 - 总已核销午晚餐)
```

数据来源：
- 订单表：`customer_order` 的 `breakfast_count`、`lunch_dinner_count`
- 核销记录：`meal_verification_log` 按 `order_id` + `meal_type` 分组统计（排除已退餐的记录）

### 5. 客户用餐统计页展示口径

客户用餐统计页参考运营 Excel 的第一页展示方式，按“客户 + 餐池明细行”返回数据，而不是简单按客户一行展示。

**按月查询口径：**

- 页面按月份查询，参数格式为 `yyyy-MM`
- 例如选择 `2026-04` 时，统计开始送餐时间早于 `2026-05-01` 的订单客户，即 `start_date < 2026-05-01`
- 其他月份同理，例如选择 `2026-05` 时，统计 `start_date < 2026-06-01` 的订单客户
- 订单必须满足 `status = 1` 且 `remaining_count > 0`
- 不按订单结束时间过滤

**拆行规则：**

- 只有早餐：展示 1 行，`送餐情况 = 早餐`
- 只有午晚餐：展示 1 行，`送餐情况 = 排餐模式 + 午/晚餐类型`
- 同时有早餐和午晚餐：展示 2 行，早餐行在前，午晚餐行在后

**数量展示说明：**

- 客户用餐统计页的表格行数和分页总数按“餐池明细行”统计，不等同于订单管理页的订单条数
- 同一笔订单如果同时包含早餐和午晚餐，会在本页面拆成 2 行，因此本页面总数可能大于订单管理页符合条件的订单数
- 例如 12 笔符合条件订单中有 5 笔同时包含早餐和午晚餐，则本页面展示为 `12 + 5 = 17` 条餐池明细行

**典型示例：**

- 若客户同时有 `breakfast_count > 0` 和 `lunch_dinner_count > 0`
- 页面会拆成：
  - 早餐行：展示早餐餐数、早餐剩余数
  - 午晚餐行：展示午晚餐数、午晚餐剩余数

**字段口径：**

- 编号：`customer_profile.customer_code`
- 电话：`customer_profile.phone`
- 地址：优先取 `DEFAULT` 地址，没有则依次取 `WORKDAY`、`WEEKEND`
- 备注信息：`customer_profile.remark`
- 特殊要求：`customer_profile.special_requirements` + `medical_requirements`
- 汤品：午晚餐订单任一订单 `soup_count >= 1` 时显示 `含汤`
- 购买时间：该餐池对应进行中订单的最早成交时间
- 开始时间：该餐池对应进行中订单的最早开始日期

**剩余餐数口径：**

- 早餐行：`Σ breakfast_count - Σ BREAKFAST 已核销数`
- 午晚餐行：`Σ lunch_dinner_count - Σ LUNCH 已核销数 - Σ DINNER 已核销数`

### 6. 客户话术解析建档

客服可在新增客户弹窗中粘贴客户沟通文本，先调用解析预览接口生成“客户档案 + 首单”草稿，再由客服确认并继续走现有新增客户接口保存。

**解析链路：**

1. 前端调用 `POST /api/customerProfile/intake/parse`
2. 后端按规则解析文本，返回 `CustomerProfileSaveDto` 兼容草稿
3. 客服应用草稿后，可继续在表单中手工调整
4. 最终仍调用 `POST /api/customerProfile` 创建客户和首单

### 首单金额权限控制

- 新增客户页首单金额展示受 `customerOrder:amount:view` 控制。
- 新增客户页首单金额录入受 `customerOrder:amount:edit` 控制。
- 文本解析草稿即使识别出金额，无金额查看权限时前端也不会展示这些字段。
- 无金额编辑权限时，后端仍会创建首单，但金额相关字段统一落为 `0`。

**关键规则：**

- 解析服务只生成草稿，不直接写入客户、地址、订单数据。
- 未传开始日期时，默认使用解析当天作为 `orderInfo.startDate`。
- 未传排餐模式时，默认 `orderInfo.scheduleMode = SCHEDULE`，`deliveryDates = null`。
- 未传米饭类型时默认 `普通杂粮米饭`；若“不能吃的/特殊要求”中明确提到“糙米”，则优先回填 `糙米`。
- `来源/客户来源/销售渠道` 会忽略括号或方括号内的候选提示，按括号外真实选择匹配渠道。例如 `来源：（小红书or抖音or推荐）抖音个人搜索` 识别为 `抖音`；`来源：（小红书·抖音·推荐）` 因无真实选择默认 `其他`。
- `套餐/父套餐` 优先按系统父套餐名称或编码映射 `orderInfo.parentPackageId`；若未填写或未匹配成功，可从 `餐别` 按分隔符拆出的完整片段中兜底匹配已启用父套餐名称或编码，例如 `餐别：小月子餐、两荤一素一汤` 可匹配父套餐 `小月子餐`，不会误匹配内部的 `月子餐`。
- `餐别：孕期营养餐不含汤（两荤一素）` 这类未命中系统父套餐的模糊描述仍仅作参考，不能替代套餐字段。
- `菜品配置` 推荐使用 `2主1副1素0汤` 这类规范格式，解析后回填主菜、副菜、素菜、汤数。
- 当解析出的父套餐名称包含 `试餐` 时，按试餐简化建档规则生成草稿：联系人可为空，系统自动补 `试餐客户` + 手机号后 4 位；未写餐数时默认 1 次午晚餐；未写菜品配置时主菜、副菜、素菜、汤默认 0；米饭类型默认 `白米饭`。
- `不能吃的` 整段进入 `specialRequirements`，不会强制拆成过敏标签或排除菜品；整段为 `无`、`没有`、`暂无` 等空值表达时忽略。
- `过敏食物` 会按逗号拆分回填 `allergyTags`；整段为 `无`、`没有`、`无过敏` 等空值表达时回填空数组。
- `排除菜品` 仅提示客服确认，不直接匹配菜品 ID。

**阻塞保存的问题：**

- 联系人为空（试餐套餐除外，系统会自动补默认姓名）。
- 电话为空或手机号格式不正确。
- 地址为空。
- 套餐为空，或没有匹配到系统父套餐。
- 普通套餐餐数为空或小于等于 0。
- 普通套餐菜品配置未解析成功，导致主菜、副菜、素菜数量仍全部为 0。

### 7. 客户与首单 Excel 批量导入

业务现场用「客户用餐计划表」逐位建档过慢，改为上传工作簿后先预览逐行转换结果与错误，操作人核对套餐编号池、日期、备份后确认提交。预览接口只读；确认接口按客户独立事务创建档案、地址，有待导入餐数时一并创建首单和未来逐餐数量计划。

**使用方式：**

1. 在客户档案页上传「客户用餐计划表」工作簿（`.xlsx`）。
2. 系统只读取名称形如 `26年9月` 的月份工作表；`客户禁忌` 工作表与 WPS 保留页本次完全忽略。
3. 返回逐位客户的转换草稿：有效编号、父套餐、送餐模式与餐次、待导入午晚餐数、未来日期逐餐计划、规格、警告与跳过原因。
4. 操作人核对文件摘要、导入日期、套餐编号池和业务备份，再明确确认提交；提交时服务端重读文件并重算摘要与数据库状态。
5. 页面按客户显示新建、幂等跳过、资料错误和事务失败原因，并可下载不含完整手机号或地址的异常清单。

**输入列与转换规则：**

| 列 | 含义 | 转换规则 |
|---|---|---|
| A / B | 原编号 / 新编号 | B 非空取 B，否则取 A 作为有效编号；有效编号同时作为客户姓名与地址联系人名 |
| C | 电话 | 只做分隔符与空白规范化；仍不合规的整位客户跳过并报告 |
| D | 地址 | 至少一个可用送餐地址；解析默认 / 工作日 / 周末槽位；电话标签中的多条配送电话完整写入客户主档 `delivery_phone_info`，地址单值联系电话取首条可用号码 |
| E / F | 备注信息 / 特殊要求 | 分别写入客户备注与特殊要求；任一列含「等通知」则该客户订单记为暂停 |
| F / G | 规格 / 含汤 | 含「无副菜」→ 主菜 1、副菜 0、素菜 1，否则 1/1/1；`含汤` → 汤数 1，`不含汤` → 汤数 0；米饭固定一份白米饭 |
| H | 送餐描述 | 含「等通知」→ 订单暂停、送餐模式 SCHEDULE、餐次留空；否则按「工作日 / 周末 / 每日」确定模式，按「午餐 / 晚餐」确定餐次 |
| I / J | 餐数 / 剩余餐数 | 逐行核对公式；午晚餐购买数取午晚餐明细行 I 列合计，早餐行不计入。导入后可用餐数 = J 列合计 + 导入日期之后非零午晚餐格之和 |

「合计餐数」单元格为空时按 0 读取，不因空值向页面报告问题；有实际取值时继续与逐日日格交叉核对。

**编号与套餐：**

- 同编号、同电话、同地址的续行合并为一位客户；同编号出现不同电话或地址时整位拒绝，不在导入器内生成后缀编号。
- 编号映射和编号池均须匹配：A → 月子餐、B → 孕期餐、C → 小月子餐、D/F → 营养餐；编号的数字部分还须落入对应已启用父套餐的编号池范围。
- 必须匹配到**唯一的已启用父套餐**，且编号的数字部分落在该父套餐的编号池范围内；落在多个池、无对应前缀映射、系统缺少该名称父套餐时逐行报错。
- 批量导入不匹配或校验子套餐；首单不填写子套餐，排餐配置使用订单上的菜品规格。

**餐数与暂停：**

- 早餐本次不导入；纯早餐行跳过并给出原因。
- 导入日期及之前的午晚餐视为历史已核销：`imported_verified_count = 午晚餐购买数 - 导入后可用餐数`。订单 `verified_count` 以此为初值，`remaining_count` 为导入后可用餐数；历史基数不生成系统内逐餐核销日志。订单从导入日期次日开始承接未来排餐。
- 「剩余餐数」为 0 的午晚餐客户仍可建档。来源午晚餐购买数也为 0 时只创建客户档案和地址；购买数大于 0 且没有未来可用餐数时，创建历史已核销的已完成首单。成功提交后在后端记录零来源剩余餐数，不向页面返回额外提示。
- 电话列与地址列的号码可以不同：前者写入客户手机号，后者的多条电话原文写入 `delivery_phone_info`；不因两列不一致而提示。编辑客户时该字段可查看、修改，旧调用方省略字段则保持原值。
- 部署此导入字段前，先执行 `eladmin/sql/20260925_customer_profile_delivery_phone_info.sql`，为现有客户主档新增可空列。
- H 送餐描述含「等通知」时，不论是否同时写有午餐或晚餐，订单均创建为暂停、送餐模式为 `SCHEDULE`、餐次留空；同一客户多行中任一行命中亦如此。E/F 含「等通知」时也创建为暂停。
- 暂停订单仍占用编号池、计入客户用餐统计并保留余额和日期计划，但不能自动/人工排餐或核销，可按剩余餐数退餐；恢复时未指定餐次的订单必须先由操作人确认餐次。
- 零金额和零单价是本次导入的合法值；导入后的未来每一份仍须单独核销并扣减一餐。
- 现有订单表部署前须执行 `eladmin/sql/20260925_customer_order_imported_verified_count.sql`；旧订单该字段默认为 0。
- 同一餐次份数为 2 时，只有「特殊要求」给出与有效编号一致的「编号-2含汤」且「含汤」列为 `不含汤` 才认定第二份含汤；无法确定的多份描述逐行报错，**不按客户编号写特例**。

**安全与不可信输入：**

- 预览不写库，也不生成临时 Excel、排餐或核销数据。
- 有实际取值的公式缓存须与逐日格交叉核对一致；空白「合计餐数」按 0 处理，文本、负数和非整数日格仍按错误处理。
- 日志不打印完整手机号与地址；预览中的手机号按前 3 位 + `****` + 后 4 位脱敏。
- 表头、月份与日期餐次结构不符合模板时整体拒绝，不进入逐行解析。

接口字段和响应详见 `doc/apidoc/客户档案管理接口文档.md`。

## 与其他模块的关系

```
客户管理（customer_profile）
  │
  ├── 套餐管理（parent_package / sub_package）
  │     ├── 通过订单关联，查到父套餐的 code_prefix → 生成客户编号
  │     └── 通过 customer_profile_package 查到签约套餐
  │
  ├── 配菜管理（dish / dish_ingredient）
  │     ├── allergy_tags → 配菜时过滤/替换菜品
  │     └── excluded_dish_ids → 标记为排除菜品
  │
  ├── 核销管理（meal_verification_log）
  │     └── 影响剩余餐数计算
  │
  └── 排餐管理（meal_plan / meal_plan_customer）
        ├── 客户档案 + 订单 → 确定生效客户 → 生成排餐计划
        ├── exclude_dates → 过滤指定日期+餐次的排餐
        └── customer_meal_schedule_addition → 记录基础计划外的人工新增餐次
```
